Tests use [pytest-homeassistant-custom-component](https://github.com/MatthewFlamm/pytest-homeassistant-custom-component), which runs a real Home Assistant (the pinned version) in the test process. There are no mocks of Home Assistant itself: a test sets pururu up from a `pururu:` block, plays the real entities' states, moves the clock and reads the resulting states.

## The `ha` fixture

Every test that needs Home Assistant takes `ha` (from `tests/conftest.py`) instead of the plugin's `hass`. It:

- **Freezes time** at a fixed Wednesday, 16 September 2026, 10:00, in Home Assistant's time zone. The few hours a test simulates then never cross a day, week, month or year by accident.
- **Puts the repository's `custom_components`** on Home Assistant's loader path.

It also marks lingering timers as expected: the carrier's next delay (a detected program's `on_delay`/`off_delay`, its phases' too) may still be pending when a test ends.

Load the integration's modules with `helpers.module("<name>")` **after** the fixture, the name dotted from the package root (`"core.feature"`, `"setup.lifecycle"`), not with a top-level import. The loader path only includes the repository once `ha` has run.

```python
from helpers import module

def test_something(ha: HomeAssistant) -> None:
    FEATURES = module("features").FEATURES
```

An autouse fixture, `no_step_failed` in `tests/conftest.py`, fails any test in which a set-up step logged `Step <name> failed`, or the registry listener `Listener failed`: the guard in `setup/lifecycle.py` keeps the entry loaded, so their bug would otherwise pass silently. A test that makes one fail on purpose clears `caplog` once it has checked the log.

## Helpers (`tests/helpers.py`)

| Helper | What it does |
|---|---|
| `setup(hass, devices, *, floors=, areas=, events=, config=)` | Sets pururu up from a `pururu:` block: `events=` is `config: events:`, `config=` the rest of `config:`. Returns `False` when Home Assistant refuses the configuration. |
| `reload(hass, devices, *, floors=, areas=, events=, config=)` | Calls `pururu.reload` with a `configuration.yaml` that holds this block (`events=` and `config=` as for `setup`). |
| `restart(hass, devices, *saved, config=)` | Starts as after a restart. `saved` is what `.storage` held, as `(State, extra data)` pairs. |
| `fake(hass, entity_id, state, attributes=None)` | Plays a real device: sets its state and lets pururu react. |
| `tick(hass, freezer, seconds)` | Moves the clock forward and runs whatever became due. |
| `settle()` | Lets every ready callback run. |
| `device_of(hass, key)` | The device registry entry of a device key, or `None`. |
| `held(hass, key)` | The entity IDs in a device, from the entity registry. |
| `capture(hass, *event_types)` | Records events in the order they're fired. |
| `snapshot(since, *, since_energy=, until=, **phases)` | The carrier's restored extra data: a program run from `since` (`None`: not running), and phases' runs by key. Every `restart` of a running `running` needs it. |

A typical test:

```python
from helpers import fake, setup, tick

WASHER = {"clothes_washer": {"name": "Washer", "appliance": {
    "power": "sensor.plug_power",
    "running_program": {"above": 4, "on_delay": {"minutes": 1}, "off_delay": {"minutes": 2}},
}}}


async def test_starts_after_on_delay(ha: HomeAssistant, freezer: Any) -> None:
    await fake(ha, "sensor.plug_power", "0")
    assert await setup(ha, WASHER)
    await fake(ha, "sensor.plug_power", "500")
    await tick(ha, freezer, 59)
    assert ha.states.get("binary_sensor.pururu_clothes_washer_appliance_running").state == "off"
    await tick(ha, freezer, 1)
    assert ha.states.get("binary_sensor.pururu_clothes_washer_appliance_running").state == "on"
```

## `test_code.py`: core's checks

`uv run pytest` also runs the tools Home Assistant core runs on its own integrations, at the pinned version:

- `ruff check` and `ruff format --check`, with `ruff.toml`.
- `mypy`, strict, with `mypy.ini`.
- **hassfest**, which validates the manifest, services, translations, icons and config flow. It comes from the pinned release's source. `fetch_hassfest.py` downloads it once into `.hassfest/`, before the HA plugin blocks sockets, and you can run it by hand with `uv run fetch_hassfest.py`.
- **The quality scale**: `quality_scale.yaml` must list every rule of the pinned hassfest. A rule that isn't `done` needs a comment with the reason.

## Docs tests

The tests that read `docs/` live in `tests/docs/`. `tests/conftest.py` marks each of them `docs`, and the `addopts` in `pyproject.toml` pass `-m "not docs"`, so `uv run pytest` leaves them out. Run them with:

```sh
uv run pytest -m docs
```

CI runs them in the Docs workflow, beside docs.page's check, on a pull request that changes docs or code. A guard in `tests/test_code.py` (`test_no_test_outside_tests_docs_reads_docs`) fails when a test outside `tests/docs/` names `docs/`, so a new test that reads a page has to go there. Only `tests/conftest.py` (it marks the folder) and `tests/test_changes.py` (it holds paths as data and reads no file) may name it; docstrings don't count.

## The layer table

`tests/test_code.py` maps every module to a layer and fails on any import the table doesn't allow (`test_each_module_imports_only_what_its_row_allows`). It's the spec's ["Layers"](/develop/architecture#layers) as code: each folder, and each module at the root, gets a row of what it may import of the integration (`homeassistant` and the stdlib aside). A prefix ending in `.` is a module *inside* that package, never the package itself: only `setup/` reads a folder's `__init__` (`FEATURES`, `ASPECTS`, `DEVICE_KEYS`). An absolute self-import (`from custom_components.pururu.outputs import dashboard`) is checked like the relative one, and importing the package itself (`from custom_components import pururu`) is refused in every folder.

| Folder (or root module) | May import |
|---|---|
| `core/` | `core.`, `const` |
| `features/` | `core.`, `const`, `features.cycle`, `features.standing`, and its own package (`features/<x>/`, or itself for a module `features/<x>.py`) |
| `aspects/` | `core.`, `const`, `features.cycle`, another `aspects.` module |
| `device_keys/` | `core.`, `const`, `features.cycle`, another `device_keys.` module |
| `outputs/` | `core.`, `const`, `aspects.problem` (Alert2's file and the alert lights read `ProblemAlert`), `features.lights` (the alert lights lend `Borrowable` lights) |
| `setup/` | `const`, `core`, `features`, `aspects`, `device_keys`, `outputs`, `setup` |
| `__init__.py` | `setup.`, `const` |
| `config_flow.py` | `const` |
| `const.py` | nothing of pururu |
| `sensor.py`, `binary_sensor.py`, `button.py`, `switch.py`, `light.py` | `core.runtime` |

Five named allowances, for one module each, not their whole folder (`ALSO` in `tests/test_code.py`):

- `features/__init__` → every `features.` package: it lists `FEATURES`.
- `device_keys/__init__` → `aspects.alerts` and `aspects.programs`: the hand-written alerts' and the executable programs' device keys.
- `device_keys/reactions` → `aspects.programs`: a reaction's `then` names an executable program (`programs.executable`) and starts its script (`programs.script_id`).
- `features/buttons` → `aspects.programs`: a button's `program` names an executable program and starts its script. It imports the module (`from ..aspects import programs`) and reads it only inside functions: the package import reaches `features/` while `aspects.programs` is still loading, so importing its names fails.
- `__init__` → `core.runtime`, directly, not through `setup.`: Home Assistant's entry points and the platforms take the typed entry, and hassfest's strict-typing check wants it named `*ConfigEntry` — `PururuConfigEntry`, in `core/runtime.py`.

Only `aspects/statistics.py` imports Home Assistant's `utility_meter` (`test_only_the_statistics_aspect_imports_utility_meter`): the meters are written once.

A new folder needs a row here, in `ALLOWED` (`tests/test_code.py`), or the import test fails with `no row in ALLOWED`.

## Running tests

```sh
uv run pytest                                      # everything but the docs tests, 4 processes
uv run pytest -m docs                              # the docs tests
uv run pytest tests/test_appliance.py -n 0 -q      # one file, one process
uv run pytest "tests/test_places.py::test_name[param id]" -n 0
PURURU_SHARD=2/3 uv run pytest --ignore=tests/test_code.py   # the second of CI's three shards
```

Use `-n 0`, not `-p no:xdist`, to run in a single process (see [Getting set up](/develop#commands)).

`PURURU_SHARD=i/N` keeps one of N sets of whole test files (`tests/sharding.py`): the files with the most tests go first, each to the lightest set, so the sets depend only on the files selected: every run of the same selection, and every xdist worker, gets the same sets. CI's Build workflow runs the tests as three shards in parallel, without `tests/test_code.py` (it runs in Build's lint job), so a shard matches CI's only with `--ignore=tests/test_code.py`, as above. A value other than `i/N` with `1 <= i <= N` stops the run before collection.
