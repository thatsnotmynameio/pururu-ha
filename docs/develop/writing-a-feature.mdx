---
title: Writing a feature
description: Add a new feature a device can have. The contract test in tests/test_features.py checks most of the wiring for you.
---

A feature is a configuration block under a device, plus the entities it creates from that block. This page adds a made-up feature, `openings`, which counts how many times a door or window sensor opened. It isn't in the repository; it only shows the steps.

```yaml
pururu:
  devices:
    front_door:
      name: Porta da frente
      openings:
        sensor: binary_sensor.front_door_contact
```

## 1. The module

Create `custom_components/pururu/features/openings.py`, or a package if the feature grows, as `appliance/` did.

```python title="features/openings.py"
"""How many times a contact sensor opened, all time."""

from collections.abc import Mapping
from decimal import Decimal
from typing import Any, override

import voluptuous as vol

from homeassistant.components.sensor import RestoreSensor, SensorStateClass
from homeassistant.const import STATE_OFF, STATE_ON, Platform
from homeassistant.core import Event, EventStateChangedData, HomeAssistant, callback
from homeassistant.helpers import config_validation as cv
from homeassistant.helpers.event import async_track_state_change_event

from ..core.entity import PururuEntity
from ..core.feature import Device, Feature

# vol.Schema refuses unknown keys by default: keep it that way
SCHEMA = vol.Schema({vol.Required("sensor"): cv.entity_id})


class Openings(PururuEntity, RestoreSensor):
    """Times `sensor` went from off to on."""

    _attr_state_class = SensorStateClass.TOTAL_INCREASING

    def __init__(self, device: Device, sensor: str) -> None:
        """Count `sensor`'s openings as the device's total."""
        self._identify(device, Platform.SENSOR, "total")
        self._sensor = sensor
        self._count = 0

    @property
    @override
    def native_value(self) -> int:
        """The count."""
        return self._count

    @override
    async def async_added_to_hass(self) -> None:
        """Restore the count, then count."""
        await super().async_added_to_hass()
        last = await self.async_get_last_sensor_data()
        if last is not None and isinstance(last.native_value, int | float | Decimal):
            self._count = int(last.native_value)
        self.async_on_remove(
            async_track_state_change_event(self.hass, self._sensor, self._changed)
        )

    @callback
    def _changed(self, event: Event[EventStateChangedData]) -> None:
        old, new = event.data["old_state"], event.data["new_state"]
        if (
            old is not None
            and old.state == STATE_OFF
            and new is not None
            and new.state == STATE_ON
        ):
            self._count += 1
            self.async_write_ha_state()


def build(
    hass: HomeAssistant,
    device: Device,
    config: dict[str, Any],
    inputs: Mapping[str, str],
) -> list[PururuEntity]:
    """The openings counter."""
    return [Openings(device, config["sensor"])]


OPENINGS = Feature(
    schema=SCHEMA,
    entity_keys={"total": Platform.SENSOR},
    build=build,
    example={"sensor": "binary_sensor.demo_contact"},
    namespace="openings",
)
```

The pieces:

- **`schema`** validates the block. Use `vol.Schema(...)` for every nested mapping that must refuse unknown keys (see [`ALLOW_EXTRA` leaks](/develop/architecture#voluptuous-allowextra-leaks)). For numbers, use `finite_float` from `core/feature.py`, which refuses `nan` and infinities.
- **`entity_keys`** lists **every** entity key the feature can create, even those that only exist with some settings, mapped to its platform.
- **`build()`** returns the entities for one device's validated block. Each entity calls `self._identify(device, platform, entity_key)`, which gives it its entity ID, unique ID, device and translated name.
- **`example`** is a minimal valid block. The contract test validates it.
- **`namespace`** is where the feature's entity keys live in an entity ID: `total` becomes `sensor.pururu_front_door_openings_total`. It's a slug no other feature uses, and not another feature's namespace followed by `_`. There's no exception for an entity key that is the same word as the namespace, so don't name one that way: `phases`' only entity key is `current` (`sensor.pururu_<key>_phase_current`), not `phase`. `build()` gets a `device` already in this namespace, so the feature only ever writes its own entity keys.

## 2. Register it

```python title="features/__init__.py"
"""Every feature a device can have, by its key in the device's configuration."""

from ..core.feature import Feature
from .appliance import APPLIANCE
from .openings import OPENINGS
from .phases import PHASES

FEATURES: dict[str, Feature] = {
    "appliance": APPLIANCE,
    "phases": PHASES,
    "openings": OPENINGS,
}
```

The key is the configuration key under a device. The device schema picks it up from `FEATURES` automatically.

## 3. Names and icons

For every entity key, add a name to **both** `translations/en.json` and `translations/pt-BR.json`, and an icon to `icons.json`, under the key in its namespace, `<namespace>_<entity key>`:

```json title="translations/en.json"
"entity": {
  "sensor": {
    "openings_total": {"name": "Openings"}
  }
}
```

```json title="icons.json"
"entity": {
  "sensor": {
    "openings_total": {"default": "mdi:door-open"}
  }
}
```

If an entity key's platform isn't in `PLATFORMS` (`const.py`), add it there, and add a platform module like `sensor.py` that adds `entry.runtime_data[Platform.X]`.

## 4. Depending on another entity

**On an entity of the same device:** set `sources` on the entity to the entity keys of its own feature it reads. If one of those isn't created because its ID is taken, this entity is dropped too, with a logged error. When you read another entity key's entity, use `device.current_entity_id(hass, platform, entity_key)`, never the default ID, so that you follow a rename. `RuntimeTotal` in `features/cycle/totals.py` is an example.

**On another feature:** declare it as a capability instead of hard-coding the other feature's name. What a feature is beyond its five fields goes in its `roles` (`core/roles.py`):

- The provider names the entity key that carries the capability: `roles=(Provides("cycle", "running"),)`.
- The consumer has `Requires("cycle")`. Its schema then **must** have a `cycle_from` key (use `cv.slug`), and its `example` must include it.
- `build()` receives the providing entity's current ID in `inputs["cycle"]`, and the consumer's entities depend on it automatically.
- The device schema checks that `cycle_from` names a feature of the same device that provides `cycle`.

`phases.py` is the example to copy.

**On one entity of another feature, named in the configuration:** add `Refers(of)`, `of` a function that returns, from the validated block, a `Ref` (`core/resolve.py`) for each entity key it names, in their namespace: `Ref(None, "appliance_power")` on this device. `checks.references` checks each is another feature's entity key, and `build()` receives its current ID in `inputs` under the reference as written (`Ref.text`, `appliance_power`). Set `follows` on each entity to the keys it reads. [`alerts`](/concepts/alerts) (`aspects/alerts.py`, the device key `ALERTS`) is the example.

**Being acted on:** a feature whose entities a [program](/concepts/programs) can act on has `Actions(...)`, the services of its platform they take: `SWITCHES` and `LIGHTS` have `Actions(("turn_on", "turn_off", "toggle"))`.

## 5. Entity keys from the configuration

Some features create one entity per key the user writes, such as [`switches`](/features/switches). Their entity keys aren't known in the code, so they aren't in `entity_keys`, and they have no translation:

- Add `Configured(<platform of those entities>)`, and leave `entity_keys` empty.
- The schema is a `vol.Schema({cv.slug: ...})` of its own, with a required `name`. A feature whose entities stand for real entities uses `standing.schema(*domains)` (`features/standing.py`): `{key: {entity, name}}`, `entity` one of those domains and not pururu's own. In `build()`, `standing.is_pururu(hass, entity)` catches a pururu entity renamed in the UI; log it and skip that entity.
- Each entity calls `self._identify(device, platform, entity_key, name)`: it's named by `name`, with no translation key.
- It can't `Provides` a capability: a capability points to a fixed entity key.

For a feature that stands for real entities of one domain, build each entity on Home Assistant's group entity of that domain, with the real entity as its only member: `Switch` in `features/switches.py` is a `SwitchGroup` of one, and `Light` in `features/lights.py` a `LightGroup` of one, as `Mirror` is a `SensorGroup` of one. The group already follows the real entity's state and passes every command on, with everything its domain offers. One feature per domain of the entity pururu creates: a light gets `lights`, not a place in `switches`. When a feature takes several domains of real entity, a mapping from each domain to its class (`KINDS` in `lights.py`) gives both the schema's domains and the class to build: `lights` takes a `switch.*` as a `SwitchLight`, on `GroupEntity`, on and off only. In one device, a real entity is in one configured feature at most.

**Entity keys repeated per item.** Some features create the same set of entities for every item of their block: [`modes`](/features/modes) gives each mode its own last cycle, totals and meters. Add `Items(keys, of)`: `keys` the suffixes (suffix → platform), `of` a function that returns, from the validated block, its items as `Item(slug, name)` (`core/feature.py`). `Configured` and `Items` never go together:

- An item's entity key is `<slug>_<suffix>` (`gelar_cycles_total`), so `sensor.pururu_<key>_mode_gelar_cycles_total`. The device schema, references, reactions and stale removal see them as any other entity key.
- Each is named by its suffix's translation, `<namespace>_<suffix>` (`mode_cycles_total`), with the item's `name` as the placeholder named after the namespace: `"{mode} cycles"`, `"Ciclos de {mode}"`.
- Each entity calls `self._identify(device, platform, suffix, item=item)`.

The cycle code `appliance`, `modes`, `door`, `window` and the programs' statistics share (the last cycle's sensors, the totals, a cycle's energy) is in `features/cycle/`, and takes `item`. A feature with its own words for them passes its own `LastCycleDescription`s and an `entity_key` to `CyclesTotal` and `RuntimeTotal`, as `door` does (`last_opened`, `openings_total`).

**Offering statistics.** A feature whose totals (`<counter>_total`, built with `CyclesTotal`, `RuntimeTotal` and the like) should have a per-period meter adds `Counters(needs, mount)` (`core/roles.py`): `needs` maps each counter to the setting it needs before it can be metered (`None` for none, `"energy"` for `appliance`'s `idle_energy` and `modes`' `energy`), and `mount` says only where `statistics:` sits, `"block"` (the default) or `"item"`: with `Items`, the meters repeat per item either way, as `core/roles.py`'s `Counters` docstring says (`modes` mounts in the block, once for every mode; `programs` and `reactions` mount in each item). The feature builds only its totals; the statistics aspect (`aspects/statistics.py`) builds the meters from them, one `Meter` (a `UtilityMeterSensor`) per counter and period asked for, and owns their translation keys, `<counter>_<period>` for the block's own, `item_<counter>_<period>` (with the `{item}` placeholder) for a per-item one. See [Statistics](/concepts/statistics).

A feature whose entity carries a cycle (`Provides`) builds it as a `CycleSource` (`features/cycle/__init__.py`): call `_cycle_signals(device, item)` once to set up its signals, and `_send(cycle)` when the cycle ends, which writes the state, then sends the cycle on its own signal, then on the end signal. `Running`, `Open` and `Runs` are the example; `modes`' `Current` calls `_cycle_signals` again for each item it sends. The contract test checks the entity a builder `Provides` is a `CycleSource`.

**Ready-made alerts.** A feature can offer alerts for what usually goes wrong with it, off until its block's `alerts` enables them. Add `Presets(<name → Preset>)` (`Preset` in `core/feature.py`), as `features/appliance/` does with `features/appliance/alerts.py`'s `PRESETS`:

- `watches`: the entity key, in the feature's namespace, it watches.
- `kind`: a `Condition`, as a hand-written alert's `is`/`above`/`below`, or an `Elapsed`: a state of the watched entity and a milestone, either an entity key whose state is a datetime (`since_key`) or an attribute of the watched entity (`since_attribute`), with `or_since_created` to count from the alert's creation until there's one. A condition alert is an `Alert` (`aspects/problem.py`); an elapsed one an `ElapsedAlert` (`aspects/elapsed.py`), which survives restarts.
- `priority` and `hold` (the default `for`, or `None` when the user must give it).

The `Presets` role is enough: **don't** put the alert keys in `entity_keys`. The alerts aspect (`aspects/alerts.py`, `ASPECT`) sees the role, adds the `alert_<name>` keys itself (`catalogue.aspects_of`, `catalogue.keys`), validates the block's `alerts` and builds the enabled ones. Add each one's name and icon under `<namespace>_alert_<name>`, and its default texts under `<namespace>_alert_<name>_message` and `_done_message` in the translations' `common` block; nothing else is needed.

**Ready-made notifications.** A feature can offer notifications for what happens to it, off until its block's `notifications` enables them, as `alerts` enables its ready-made alerts. Add `Happenings(<name → Happening>)` (`Happening` in `core/feature.py`): the entity key it watches and the state it goes `to` (and `from_`), as `features/appliance/notifications.py`'s `HAPPENINGS` does. It creates no entity: `device_keys/notifications.py` validates that key of the block (`catalogue._feature_block` takes it out before the feature's schema) and generates an automation per enabled one. Add its name and default message under `<namespace>_notification_<name>_name` and `_message` in the translations' `common` block, and a row to the table of [Notifications](/concepts/notifications#ready-made-notifications).

## 6. What the contract test checks

`tests/test_features.py` runs over every entry in `FEATURES`, and in `DEVICE_KEYS` (`device_keys/__init__.py`: `programs` and `reactions`, whose statistics a `Feature` each builds, and `alerts` (`aspects/alerts.py`'s `ALERTS`, the hand-written alerts), none of them a feature of a device), so your feature is covered without changing the test:

| Test | Checks |
|---|---|
| `test_translation_files_match` | `pt-BR.json` has exactly `en.json`'s keys |
| `test_namespaces_are_distinct_slugs` | Every namespace is a slug, no two are equal, and none is another's followed by `_` |
| `test_no_entity_key_repeats_its_namespace` | No fixed entity key is its feature's namespace, which would read `…_phase_phase` |
| `test_every_entity_key_is_named_and_has_an_icon` | A name in both languages and an `mdi:` icon for every entity key, under its key in its namespace |
| `test_every_translated_entity_key_is_created` | Every name and icon is under a key some feature creates |
| `test_example_is_valid_and_unknown_keys_are_refused` | `example` passes `schema`, and `example` plus an unknown key fails |
| `test_every_platform_is_set_up` | Every entity key's platform, and a configured feature's platform, is in `PLATFORMS` |
| `test_capabilities_line_up` | `Provides` points to a real entity key and a configured feature provides nothing, every `Requires` is provided by some feature, and the example has `<capability>_from` |
| `test_refers_names_entity_keys_as_in_an_entity_id` | What `Refers` returns for the example names slugs, as entity keys in their namespace |
| `test_every_action_is_a_service_of_its_platform` | A feature with `Actions` is configured, and its platform has a service for each action |
| `test_it_takes_turn_on_turn_off_and_toggle` | `switches` and `lights` have exactly `("turn_on", "turn_off", "toggle")` |
| `test_items_have_suffixes_and_slugs` | `Items` has suffixes, and the example's items are slugs |
| `test_every_per_item_name_has_its_placeholder` | Every suffix's name has the `{<namespace>}` placeholder, in both languages |
| `test_ready_made_alerts_line_up` | Every ready-made alert's key is the alerts aspect's, not the builder's own (`entity_keys` lacks it, `by == "alerts"`), it watches (and counts from) its own feature's entity keys, has both default texts in both languages, and its settings validate |
| `test_ready_made_alerts_are_offered_only_with_one` | The alerts aspect is offered only for at least one ready-made alert, the rule `presets_of` gives `alert_lights`: an empty `Presets` offers nothing |
| `test_every_alert_takes_the_shared_keys` | The hand-written alert's schema and every ready-made alert's settings take `problem.shared`'s keys (`priority`, `notify`, `lights`); a ready-made alert adds only `for`, and only the default priority differs |
| `test_alerts_is_a_device_key_not_a_feature` | `alerts` is in `DEVICE_KEYS`, not in `FEATURES`: it never counts as a device's feature |
| `test_ready_made_notifications_line_up` | Every ready-made notification watches its own feature's entity key, has its name and message in both languages, and validates |
| `test_each_role_at_most_once` | No role twice in `roles` |
| `test_configured_and_items_never_together` | A block's keys are either its entity keys or its items |
| `test_a_device_key_neither_provides_requires_nor_acts` | No device key (`programs`, `reactions`, `alerts`) has `Provides`, `Requires` or `Actions` |
| `test_ready_made_watch_the_builders_keys` | What a ready-made alert or notification watches, or counts from, is one of its builder's entity keys |
| `test_a_generating_builder_generates_from_its_example` | What `Generates` writes carries its device's pururu pattern |
| `test_a_capability_is_carried_by_a_cycle_source` | What a builder `Provides` is a `CycleSource` |
| `test_the_other_cycle_sources_are_pinned_too` | `modes`' `Current` and the programs' `Runs` are `CycleSource` too, though no `Provides` names them |
| `test_the_aspects_each_builder_offers` | Which aspects (`statistics`, `alerts`) each builder offers, pinned: `appliance` offers both, the rest at most `statistics` |
| `test_an_aspects_keys_are_named_once` | Every key an offered aspect adds has a name and icon in both languages, under the translation key the aspect names it (`Aspect.named`): statistics' outside every namespace (`item_<key>` with `{item}` for an `Items` builder), ready-made alerts' under the builder's |
| `test_an_offered_aspect_validates_and_builds` | The builder's example with the aspect's own example goes through `mount`, and the aspect builds only the entity keys it lists |
| `test_a_builders_own_schema_refuses_an_aspects_key` | The builder's own schema, without `mount`, refuses the aspect's key where it sits: only `mount` may take it out first |
| `test_a_configured_builder_offers_no_block_aspect` | A `Configured` feature's block is its entity keys, so it offers no aspect |
| `test_mount_leaves_an_items_key_alone` | In a block of items (`Configured`, or an aspect placed `"item"`), a key alike an aspect's is an item, not the aspect's |
| `test_mount_refuses_a_block_or_item_that_isnt_a_map` | A block, or an item, that isn't a map is refused with a path, a `vol.Invalid`, not a `KeyError` or `TypeError` |
| `test_an_absent_aspect_key` | Absent, statistics is mounted as `{}` and ready-made alerts are left out (`mount_absent`); a block that isn't a map gets only the builder's own refusal |
| `test_mount_skips_an_aspect_without_a_check` | An aspect without a `check` still mounts |
| `test_a_counter_is_totalled` | Each of a `Counters` feature's needed counters has a `<counter>_total` entity key (per item, with `Items`) for the statistics aspect to meter |
| `test_a_counter_without_its_setting_is_refused` | A counter needing a setting takes no periods without it (`statistics.idle_energy needs energy`); asking for none passes regardless |

The name, icon, platform and namespace checks above cover `Items`' suffixes and an aspect's keys too.

The contract test doesn't check **behaviour**. Write that in `tests/test_<feature>.py` with the [helpers](/develop/testing): set it up, `fake` the real entity's states, `tick` the clock, and assert the states. Cover a restart (`restart`), a reload (`reload`), a renamed entity and an ID that's already taken, as `test_appliance.py` and `test_phases.py` do.

## 7. Document it

- Add `docs/features/<feature>.mdx` with its settings (`<Property>`), its entities and its rules, following [`appliance`](/features/appliance).
- Add the page to the `Features` group in `docs.json`.
- If it adds log messages, add them to [Troubleshooting](/reference/troubleshooting).
- Add it to the table in [Devices and features](/concepts/devices-and-features#a-feature).
