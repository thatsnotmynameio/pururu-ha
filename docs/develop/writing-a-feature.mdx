---
title: Writing a feature
description: Add a new feature a device can have. The contract test in tests/test_features.py checks most of the wiring for you.
---

A feature is a configuration block under a device, plus the entities it creates from that block. This page adds a made-up feature, `openings`, which counts how many times a door or window sensor opened. It isn't in the repository; it only shows the steps.

```yaml
pururu:
  devices:
    front_door:
      name: Porta da frente
      openings:
        sensor: homeassistant.binary_sensor.front_door_contact
```

## 1. The module

Create `custom_components/pururu/features/openings.py`, or a package if the feature grows, as `appliance/` did.

```python title="features/openings.py"
"""How many times a contact sensor opened, all time."""

from collections.abc import Mapping
from decimal import Decimal
from typing import Any, override

import voluptuous as vol

from homeassistant.components.sensor import RestoreSensor, SensorStateClass
from homeassistant.const import STATE_OFF, STATE_ON, Platform
from homeassistant.core import Event, EventStateChangedData, HomeAssistant, callback
from homeassistant.helpers.event import async_track_state_change_event

from ..core.entity import PururuEntity
from ..core.feature import Device, Feature
from ..core.resolve import homeassistant_entity

# vol.Schema refuses unknown keys by default: keep it that way. A Home
# Assistant entity is written homeassistant.<domain>.<object_id>; the field
# hands build() the bare entity ID
SCHEMA = vol.Schema({vol.Required("sensor"): homeassistant_entity(Platform.BINARY_SENSOR)})


class Openings(PururuEntity, RestoreSensor):
    """Times `sensor` went from off to on."""

    _attr_state_class = SensorStateClass.TOTAL_INCREASING

    def __init__(self, device: Device, sensor: str) -> None:
        """Count `sensor`'s openings as the device's total."""
        self._identify(device, Platform.SENSOR, "total")
        self._sensor = sensor
        self._count = 0

    @property
    @override
    def native_value(self) -> int:
        """The count."""
        return self._count

    @override
    async def async_added_to_hass(self) -> None:
        """Restore the count, then count."""
        await super().async_added_to_hass()
        last = await self.async_get_last_sensor_data()
        if last is not None and isinstance(last.native_value, int | float | Decimal):
            self._count = int(last.native_value)
        self.async_on_remove(
            async_track_state_change_event(self.hass, self._sensor, self._changed)
        )

    @callback
    def _changed(self, event: Event[EventStateChangedData]) -> None:
        old, new = event.data["old_state"], event.data["new_state"]
        if (
            old is not None
            and old.state == STATE_OFF
            and new is not None
            and new.state == STATE_ON
        ):
            self._count += 1
            self.async_write_ha_state()


def build(
    hass: HomeAssistant,
    device: Device,
    config: dict[str, Any],
    inputs: Mapping[str, str],
) -> list[PururuEntity]:
    """The openings counter."""
    return [Openings(device, config["sensor"])]


OPENINGS = Feature(
    schema=SCHEMA,
    entity_keys={"total": Platform.SENSOR},
    build=build,
    example={"sensor": "homeassistant.binary_sensor.dummy_contact"},
    namespace="openings",
)
```

The pieces:

- **`schema`** validates the block. Use `vol.Schema(...)` for every nested mapping that must refuse unknown keys (see [`ALLOW_EXTRA` leaks](/develop/architecture#voluptuous-allowextra-leaks)). For numbers, use `finite_float` from `core/feature.py`, which refuses `nan` and infinities.
- **`entity_keys`** lists **every** entity key the feature can create, even those that only exist with some settings, mapped to its platform.
- **`build()`** returns the entities for one device's validated block. Each entity calls `self._identify(device, platform, entity_key)`, which gives it its entity ID, unique ID, device and translated name.
- **`example`** is a minimal valid block. The contract test validates it.
- **Paths.** Every entity key gets a path, how the YAML names it: the feature's key in the device, then where the key sits in its block. A fixed key sits at the block under its own name unless the feature says otherwise, so `total` is `openings.total`, `sensor.pururu_front_door_openings_total`'s path. A fixed key that belongs under a node of the block, as the appliance's cycle entities under `running_program`, is placed by `Nodes(of)` (`core/roles.py`: entity key → its path from the block; a written setting's entity at the setting, `energy_total` at `energy`). `setup/catalogue.keys` gives every key its path, the index is keyed by it, and `build.build` stamps it on each built entity (`PururuEntity.path`, shown in the `reference` attribute): the contract test checks each key has one, distinct within its device. See [References](/concepts/entity-ids#references).
- **`namespace`** is where the feature's entity keys live in an entity ID: `total` becomes `sensor.pururu_front_door_openings_total`. It's a slug no other feature uses, and not another feature's namespace followed by `_`. There's no exception for an entity key that is the same word as the namespace, so don't name one that way: an entity key `appliance` under the `appliance` namespace would read `sensor.pururu_<key>_appliance_appliance`. `build()` gets a `device` already in this namespace, so the feature only ever writes its own entity keys.

## 2. Register it

```python title="features/__init__.py"
"""Every feature a device can have, by its key in the device's configuration."""

from ..core.feature import Feature
from .appliance import APPLIANCE
from .openings import OPENINGS

FEATURES: dict[str, Feature] = {
    "appliance": APPLIANCE,
    "openings": OPENINGS,
}
```

The key is the configuration key under a device. The device schema picks it up from `FEATURES` automatically.

## 3. Names and icons

For every entity key, add a name to **both** `translations/en.json` and `translations/pt-BR.json`, and an icon to `icons.json`, under the key in its namespace, `<namespace>_<entity key>`:

```json title="translations/en.json"
"entity": {
  "sensor": {
    "openings_total": {"name": "Openings"}
  }
}
```

```json title="icons.json"
"entity": {
  "sensor": {
    "openings_total": {"default": "mdi:door-open"}
  }
}
```

If an entity key's platform isn't in `PLATFORMS` (`const.py`), add it there, and add a platform module like `sensor.py` that adds `entry.runtime_data[Platform.X]`.

## 4. Depending on another entity

**On an entity of the same device:** set `sources` on the entity to the entity keys of its own feature it reads (entity keys, not paths: they're its own). If one of those isn't created because its ID is taken, this entity is dropped too, with a logged error. When you read another entity key's entity, use `device.current_entity_id(hass, platform, entity_key)`, never the default ID, so that you follow a rename. `RuntimeTotal` in `features/cycle/totals.py` is an example.

A feature reads another feature's entity only through `Refers`, never by hard-coding its name or taking a capability from it.

**On one entity of another feature, named in the configuration:** validate the field with `core/resolve.py`'s `path` (a path of this device, `device.<device>.…` or `homeassistant.…`), and add `Refers(of)`, `of` a function that yields, from the validated block, `(the field's path in the block, Ref)` for each reference it names: `(("stuck", "when"), Ref.parse("appliance.power"))`. `checks.references` refuses, at that field, one that isn't another feature's entity of this device: another device's and a Home Assistant entity are never one. `build()` receives its current ID in `inputs` under the reference as written (`Ref.text`, `appliance.power`). Set `follows` on each entity to the paths it reads. [`alerts`](/concepts/alerts) (`aspects/alerts.py`, the device key `ALERTS`) is the example.

**Entity keys the block adds.** A feature whose validated block decides more entity keys than `entity_keys` lists (the appliance's phases, from its `running_program`'s `phases`) adds `Derived(of)` (`core/roles.py`): `of` takes the validated block and returns the entity keys it adds, each a `Born` (`core/feature.py`: its platform and its path from the block, `running_program, phases, warming` for `phase_warming`). `setup/catalogue.keys` lists them too, so an alert, a reaction or a `when:` can name one; they're never in `entity_keys` itself, since they depend on the block. `program.keys_of` is the example: every entity key a program block's phases create, `other`'s too, none without phases.

**Detected programs.** A feature reading a sensor can take `programs: detected:` by adding `Programs(reading, energy)` (`core/roles.py`: the settings of its block giving the reading and each cycle's kWh, `energy` `None` for none; the appliance's `Programs("power", "energy")`) and `*program.counted_each(program.DETECTED_AT)` to its `Counters`: the programs aspect (`aspects/programs.py`, `ASPECT`) does the rest. It mounts `programs:` (its schema, each program a band with a `name`, phases and `other`), lists each program's keys (`Place.derived`: `<key>`, `<key>_<suffix>`, `<key>_phase_…`, each with its `Born` path under `programs.detected.<key>`, in the feature's namespace, so `checks.keys_distinct` refuses one the feature or another program creates) and builds each (`program.build_detected`). Their names and icons are the detector's, once for every builder (`DETECTED_NAMED`, with `{item}`): nothing to add to the translations. The contract test checks both (`test_a_programs_builder_counts_its_detected_programs`, `test_a_detected_programs_keys_are_named`).

**Being acted on:** a feature whose entities a [program](/concepts/programs) can act on has `Actions(...)`, the services of its platform they take: `SWITCHES` and `LIGHTS` have `Actions(("turn_on", "turn_off", "toggle"))`.

## 5. Entity keys from the configuration

Some features create one entity per key the user writes, such as [`switches`](/features/switches). Their entity keys aren't known in the code, so they aren't in `entity_keys`, and they have no translation:

- Add `Configured(<platform of those entities>)`, and leave `entity_keys` empty.
- The schema is a `vol.Schema({cv.slug: ...})` of its own, with a required `name`. A feature whose entities stand for real entities uses `standing.schema(*domains)` (`features/standing.py`): `{key: {entity, name}}`, `entity` one of those domains and not pururu's own. In `build()`, `standing.is_pururu(hass, entity)` catches a pururu entity renamed in the UI; log it and skip that entity.
- Each entity calls `self._identify(device, platform, entity_key, name)`: it's named by `name`, with no translation key.

`buttons` (`features/buttons.py`) is a configured feature that doesn't stand for its real entity: each button reads a sensor and is pressed when the sensor changes to its `state`, so it's a `ButtonEntity`, not a group. Its item schema extends `standing.real_entity` with `state` and `program`, and it keeps `standing.is_pururu` in `build()`.

For a feature that stands for real entities of one domain, build each entity on Home Assistant's group entity of that domain, with the real entity as its only member: `Switch` in `features/switches.py` is a `SwitchGroup` of one, and `Light` in `features/lights.py` a `LightGroup` of one, as `Mirror` is a `SensorGroup` of one. The group already follows the real entity's state and passes every command on, with everything its domain offers. One feature per domain of the entity pururu creates: a light gets `lights`, not a place in `switches`. When a feature takes several domains of real entity, a mapping from each domain to its class (`KINDS` in `lights.py`) gives both the schema's domains and the class to build: `lights` takes a `switch.*` as a `SwitchLight`, on `GroupEntity`, on and off only. In one device, a real entity is in one configured feature at most.

**Entity keys repeated per item.** Some features create the same set of entities for every item of their block: the executable programs (`programs: executable:`) give each program its own last cycle, totals and meters. Add `Items(keys, of)`: `keys` the suffixes (suffix → platform), `of` a function that returns, from the validated block, its items as `Item(slug, name, path)` (`core/feature.py`; `path` where the item sits in the block, `("executable", "clean")`, its keys' paths under it: `programs.executable.clean.cycles_total`). With `Configured`, items only add keys beside the block's own, one item per block key, its slug the key (a button's `<key>_triggered_total`):

- An item's entity key is `<slug>_<suffix>` (`executable_clean_cycles_total`), so `sensor.pururu_<key>_program_executable_clean_cycles_total`, and its path the item's then the suffix (`programs.executable.clean.cycles_total`). The device schema, references, reactions and stale removal see them as any other entity key.
- Each is named by its suffix's translation, `<namespace>_<suffix>` (`program_cycles_total`), with the item's `name` as the placeholder named after the namespace: `"{program} cycles"`, `"Ciclos de {program}"`.
- Each entity calls `self._identify(device, platform, suffix, item=item)`.

The cycle code the appliance (its running program and phases), `door`, `window` and the programs' statistics share (the last cycle's sensors, the totals, a cycle's energy) is in `features/cycle/`, and takes `item`. A feature with its own words for them passes its own `LastCycleDescription`s and an `entity_key` to `CyclesTotal` and `RuntimeTotal`, as `door` does (`last_opened`, `openings_total`).

**Offering statistics.** A feature whose totals (`<counter>_total`, built with `CyclesTotal`, `RuntimeTotal` and the like) should have a per-period meter adds `Counters(places)` (`core/roles.py`): `places` a tuple of `Counted(needs, at, item, named)`, one per place `statistics:` can sit. `needs` maps each counter to the setting it needs before it can be metered, looked up in the builder's whole block (`None` for none, `"energy"` for `appliance`'s `idle_energy`), for counters at the block itself: `Counters((Counted(needs={"openings": None, "open_time": None}),))`, the door's (`at=()` is the default). A place deeper in the block, such as a phase's, gives `at` the path to it: `Counted(needs=PHASE_COUNTERS, at=("running_program", "phases", EACH), item=_phase_item)` meters each phase's counters, where `EACH` (`core/feature.py`) stands for every key of a map, and `item(block, path)` gives the item a container there is, from the builder's validated block and the container's path (`feature.ItemOf`; `feature.at(block, path)` is the container). `program.counted(where)` is the example: the program's own place, then each phase's, then `other`'s. The feature builds only its totals, at each place; the statistics aspect (`aspects/statistics.py`) builds the meters from them, one `Meter` (a `UtilityMeterSensor`) per counter and period asked for, and owns their translation keys, `<counter>_<period>` for the block's own, `item_<counter>_<period>` (with the `{item}` placeholder) for an item's, or `Counted.named`'s own prefix (`other`'s). See [Statistics](/concepts/statistics).

An entity that sends cycles — what a `LastCycleValue`, `CyclesTotal` or `RuntimeTotal` follows — is a `CycleSource` (`features/cycle/__init__.py`): call `_cycle_signals(device, item)` once to set up its signals, and `_send(cycle)` when the cycle ends, which writes the state, then sends the cycle on its own signal, then on the end signal. `Open`, `Runs`, the carrier (a detected program's, `features/cycle/program/entities.py`) and `PhaseRunning` are the examples; the carrier sets its signals for its own key, and each `PhaseRunning` for its phase's item. The contract test (`test_what_a_last_cycle_follows_is_a_cycle_source`) checks what every last cycle follows is a `CycleSource`.

**Ready-made alerts.** A feature can offer alerts for what usually goes wrong with it, off until its block's `alerts` enables them. Add `Presets(<name → Preset>)` (`Preset` in `core/feature.py`), as `features/appliance/` does with `features/appliance/alerts.py`'s `PRESETS`:

- `watches`: the entity key, in the feature's namespace, it watches.
- `kind`: a `Condition`, as a hand-written alert's `state`/`above`/`below` (`equals`, a number, only in code: `no_power`), or an `Elapsed`: a state of the watched entity and a milestone, either an entity key whose state is a datetime (`since_key`) or an attribute of the watched entity (`since_attribute`), with `or_since_created` to count from the alert's creation until there's one. A condition alert is an `Alert` (`aspects/problem.py`); an elapsed one an `ElapsedAlert` (`aspects/elapsed.py`), which survives restarts.
- `priority` and `hold` (the default `for`, or `None` when the user must give it).

The `Presets` role is enough: **don't** put the alert keys in `entity_keys`. The alerts aspect (`aspects/alerts.py`, `ASPECT`) sees the role, adds the `alert_<name>` keys itself (`catalogue.aspects_of`, `catalogue.keys`), validates the block's `alerts` and builds the enabled ones. Add each one's name and icon under `<namespace>_alert_<name>`, and its default texts under `<namespace>_alert_<name>_message` and `_done_message` in the translations' `common` block; nothing else is needed.

**Ready-made notifications.** A feature can offer notifications for what happens to it, off until its block's `notifications` enables them, as `alerts` enables its ready-made alerts. Add `Happenings(<name → Happening>)` (`Happening` in `core/feature.py`): the entity key it watches and the state it goes `to` (and `from_`), as `features/appliance/notifications.py`'s `HAPPENINGS` does. The `Happenings` role is enough: the builder then offers the notifications aspect (`aspects/notifications.py`, `ASPECT`), which takes the block's `notifications` out before the feature's schema, validates it, and generates an automation per enabled one; it creates no entity. Add its name and default message under `<namespace>_notification_<name>_name` and `_message` in the translations' `common` block, and a row to the table of [Notifications](/concepts/notifications#ready-made-notifications).

## 6. What the contract test checks

`tests/test_features.py` runs over every entry in `FEATURES`, and in `DEVICE_KEYS` (`device_keys/__init__.py`: `programs` (`aspects/programs.py`'s `PROGRAMS`, the executable programs) and `reactions`, whose statistics a `Feature` each builds, and `alerts` (`aspects/alerts.py`'s `ALERTS`, the hand-written alerts), none of them a feature of a device), so your feature is covered without changing the test:

| Test | Checks |
|---|---|
| `test_translation_files_match` | `pt-BR.json` has exactly `en.json`'s keys |
| `test_namespaces_are_distinct_slugs` | Every namespace is a slug, no two are equal, and none is another's followed by `_` |
| `test_no_entity_key_repeats_its_namespace` | No fixed entity key is its feature's namespace, which would read `…_appliance_appliance` |
| `test_every_entity_key_is_named_and_has_an_icon` | A name in both languages and an `mdi:` icon for every entity key, under its key in its namespace |
| `test_every_translated_entity_key_is_created` | Every name and icon is under a key some feature creates |
| `test_the_detectors_keys_are_named` | The detector's own keys (`NAMED`) are counted among the created keys, each named in both languages with an icon; `phase_current` and `phase_last` translate only the states it shows by itself (`idle`, `other`) |
| `test_a_detected_programs_keys_are_named` | Each key a detected program is named by (`DETECTED_NAMED`) has `{item}` in both languages and an icon; `detected_phase_current` and `detected_phase_last` translate the same states as `phase_current` and `phase_last` |
| `test_example_is_valid_and_unknown_keys_are_refused` | `example` passes `schema`, and `example` plus an unknown key fails |
| `test_every_platform_is_set_up` | Every entity key's platform, and a configured feature's platform, is in `PLATFORMS` |
| `test_what_a_last_cycle_follows_is_a_cycle_source` | Each `LastCycleValue`'s source is a `CycleSource`, built by the builder and its aspects from the full example: the appliance's `running` and each phase, a detected program's carrier and its phases, a door's or a window's `open`, an executable program's `executable_<key>_cycles_total` (`Runs`) |
| `test_a_derived_key_is_in_the_index` | What a validated block adds (`Derived`) is listed by `catalogue.keys`, and the example builds only listed keys |
| `test_refers_names_paths_as_written` | What `Refers` returns for the example is a path that reads back as written (`path`, `Ref.parse`), each at a field |
| `test_every_listed_key_has_one_path` | Each key `catalogue.keys` lists for the full example has one path of dotted slugs, distinct within the device, never at a setting's value |
| `test_every_built_entity_carries_its_path` | Set up as a device, every entity carries the path `build.build` stamped from the index, which resolves back to its key, and shows it in its `reference` attribute, from inside and from another device |
| `test_every_action_is_a_service_of_its_platform` | A feature with `Actions` is configured, and its platform has a service for each action |
| `test_it_takes_turn_on_turn_off_and_toggle` | `switches` and `lights` have exactly `("turn_on", "turn_off", "toggle")` |
| `test_items_have_suffixes_and_slugs` | `Items` has suffixes, and the example's items are slugs |
| `test_every_per_item_name_has_its_placeholder` | Every suffix's name has the `{<namespace>}` placeholder, in both languages |
| `test_ready_made_alerts_line_up` | Every ready-made alert's key is the alerts aspect's, not the builder's own (`entity_keys` lacks it, `by == "alerts"`), it watches (and counts from) its own feature's entity keys, has both default texts in both languages, and its settings validate |
| `test_ready_made_are_offered_only_with_one` | The alerts aspect is offered only for at least one ready-made alert (the rule `presets_of` gives `alert_lights`), the notifications aspect only for at least one `Happening`: an empty `Presets` or `Happenings` offers nothing |
| `test_every_alert_takes_the_shared_keys` | The hand-written alert's schema and every ready-made alert's settings take `problem.shared`'s keys (`priority`, `message`, `done_message`, `lights`); a ready-made alert adds only `for`, and only the default priority differs |
| `test_alerts_is_a_device_key_not_a_feature` | `alerts` is in `DEVICE_KEYS`, not in `FEATURES`: it never counts as a device's feature |
| `test_ready_made_notifications_line_up` | Every ready-made notification watches its own feature's entity key, has its name and message in both languages, and validates through the notifications aspect, which adds no entity key |
| `test_each_role_at_most_once` | No role twice in `roles` |
| `test_a_configured_builders_items_are_its_keys` | A `Configured` block's keys are its entity keys: its items, if any, are one per key, slug the key |
| `test_a_device_key_neither_acts_nor_derives` | No device key (`programs`, `reactions`, `alerts`) has `Actions` or `Derived` |
| `test_ready_made_watch_the_builders_keys` | What a ready-made alert or notification watches, or counts from, is one of its builder's entity keys |
| `test_a_generating_builder_generates_from_its_example` | What `Generates` writes carries its device's pururu pattern |
| `test_the_aspects_each_builder_offers` | Which aspects (`statistics`, `alerts`, `notifications`, `programs`) each builder offers, pinned: `appliance` offers all four, the rest at most `statistics` |
| `test_the_aspects_in_build_order` | `ASPECTS` is the ready-made alerts, then the detected programs, then statistics, then the ready-made notifications |
| `test_an_aspects_keys_are_named_once` | Every key an aspect can add is named and has an icon, at each place (`Place.named`): `{item}` all or none per place, none without an item |
| `test_an_offered_aspect_validates_and_builds` | The builder's full example (each place's example put in, the shallowest first, so it reaches the places inside another aspect's value too) goes through `mount`; it reaches every place, and the aspect builds exactly when it lists a key, fixed or derived, and only the keys it lists (none: the ready-made notifications') |
| `test_a_builders_own_schema_refuses_an_aspects_key` | The builder's own schema, without `mount`, refuses the aspect's key at each place's containers (`put`); a place inside another aspect's value (`statistics:` in a detected program) is that aspect's schema's to refuse |
| `test_a_configured_builder_offers_no_block_aspect` | A `Configured` feature's block is its entity keys, so an aspect it offers sits only inside an item (`EACH`), never at the block |
| `test_mount_leaves_an_items_key_alone` | In a block of items (`Configured`, or an aspect placed at a map's items), a key alike an aspect's is an item, not the aspect's |
| `test_mount_refuses_a_block_or_item_that_isnt_a_map` | A block, or an item, that isn't a map is refused with a path, a `vol.Invalid`, not a `KeyError` or `TypeError` |
| `test_an_absent_aspect_key` | Absent, statistics is mounted as `{}` and ready-made alerts, notifications and detected programs are left out (`mount_absent`), an explicit `{}` or null of theirs still refused; a block that isn't a map gets only the builder's own refusal |
| `test_mount_skips_a_place_without_a_check` | A place without a `check` still mounts |
| `test_a_counter_is_totalled` | Each of a `Counters` feature's needed counters has a `<counter>_total` entity key at each place it counts in the mounted full example (an item's, the builder's own elsewhere), built by the builder or an aspect (a detected program's totals are the programs aspect's), for the statistics aspect to meter |
| `test_a_programs_builder_counts_its_detected_programs` | A builder with `Programs` (the appliance only) lists `program.counted_each(program.DETECTED_AT)` in its `Counters`, and its `reading` and `energy` are settings its schema has |
| `test_a_counter_without_its_setting_is_refused` | A counter needing a setting takes no periods without it, at every place it counts (`statistics.idle_energy needs energy`); asking for none passes regardless |

The name, icon, platform and namespace checks above cover `Items`' suffixes and an aspect's keys too.

The contract test doesn't check **behaviour**. Write that in `tests/test_<feature>.py` with the [helpers](/develop/testing): set it up, `fake` the real entity's states, `tick` the clock, and assert the states. Cover a restart (`restart`), a reload (`reload`), a renamed entity and an ID that's already taken, as `test_appliance.py` and `test_program_entities.py` do.

## 7. Document it

- Add `docs/features/<feature>.mdx` with its settings (`<Property>`), its entities and its rules, following [`appliance`](/features/appliance).
- Add the page to the `Features` group in `docs.json`.
- If it adds log messages, add them to [Troubleshooting](/reference/troubleshooting).
- Add it to the table in [Devices and features](/concepts/devices-and-features#a-feature).
