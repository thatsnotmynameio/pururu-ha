---
title: Troubleshooting
description: What each error pururu logs means, and what to do about it.
---

pururu reports problems in **Settings → System → Logs**, under the **Pururu** integration. Only an invalid configuration, or a failure before its steps (while it builds and hands over the entities), stops it. Anything else is logged, and the rest of the configuration is still applied.

## The reload changed nothing

The configuration is probably invalid. Home Assistant logs the reason as `Invalid config for 'pururu'`, and pururu keeps everything as it was. Common causes:

- A typo in a key, such as `floor:` for `floors:` or `running:` for `running_program:` (an old key is `'running' is an invalid option`), or the appliance's `statistics: runtime`/`cycles` still in the block instead of in `running_program` (`'cycles' is an invalid option`).
- A key that isn't a slug, such as `Laundry Washer:` instead of `clothes_washer:`.
- A device's `area` that isn't a key of `areas:`, or an area's `floor` that isn't a key of `floors:`.
- A device with no feature: `reactions`, `programs` and `alerts` don't count, so a device with only `alerts` (and, maybe, `programs` or `reactions`) is refused too (`a device needs at least one feature`).
- A `running_program` with a `name` (`running_program takes no name: it is the appliance running`), or with neither `above` nor `below` (`a program needs above, below or both`).
- A phase without `name`, keyed `idle` (`idle is a reserved phase key: name the phase otherwise`), keyed `current` or `last`, or whose entities another phase's or the detector's would be (`phase resfriar_cycles_total would create phase_resfriar_cycles_total, phase resfriar's`).
- A phase keyed `other` or `other_…`, the built-in phase's, whether `other:` is written yet or not: its meters would be the phase's entities once it is (`other_cycles_today is reserved for the built-in phase other (other, other_…): name the phase otherwise`). Pick a key that doesn't begin with `other_`.
- `other:` without `phases` (`other is the program outside every phase: it needs phases`).
- Two entities of one device with one unique ID, such as a phase's key and another phase's meter (`device clothes_washer: pururu_clothes_washer_appliance_phase_resfriar_cycles_today would be two entities`).
- `statistics.energy` on a phase or a detected program without the appliance's `energy` (`statistics.energy needs energy`).
- A switch whose `entity` isn't a `switch.*` entity, is a pururu switch, or has no `name` or an empty one.
- A door or window whose `contact` isn't a `binary_sensor.*` entity (`sensor.x is not a binary_sensor`) or is a pururu binary sensor (`binary_sensor.pururu_… is a pururu binary_sensor: name the real one`); an event whose `entity` isn't an `event.*` entity, whose `types` is empty or means something other than `opening`, `denied` or `ring`, or whose `fields` names something other than `who`, `how` or `direction`.
- A light whose `entity` isn't a `light.*` or `switch.*` entity (`sensor.x is not a light or switch`), is a pururu light or switch, or has no `name` or an empty one.
- A real entity in both `switches` and `lights` of one device: `switches: switch.sonoff_abajur is already in lights`. Keep it in one of them.
- An alert whose `when` isn't an entity of another feature of the device: `alerts: appliance_nothing is not an entity key of another feature of this device`. Write it as the entity ID ends after the device key, with its namespace (`appliance_power`, not `power`).
- An alert with both `is` and `above`/`below`, with neither, with `above` not lower than `below`, or with an unknown `priority`.
- An alert's `notify` without `message` or `done_message`, with an empty one, or with another key.
- A ready-made alert the feature doesn't offer (`nope is not a ready-made alert: offline, no_power, long_cycle, no_cycle`), `long_cycle` or `no_cycle` without `for`, or `lasts` (`'lasts' is an invalid option`).
- A ready-made notification the feature doesn't offer: `nope is not a ready-made notification of appliance: finished`. A feature that offers none takes no `notifications` (`'notifications' is an invalid option`).
- A message that goes nowhere: `device clothes_washer: reactions: door_open: message needs notify, here or in config.notify`. Add `config.notify`, or a `notify` to that reaction or notification. A reaction's `notify` without `message` is refused too, and so is a `notify` that isn't `notify.<name>`.
- An alert whose `when` is a ready-made alert: `alerts: appliance_alert_offline is an alert: an alert can't watch another`.
- A program step naming something that isn't an entity of another feature of the device: `programs: switch_greenhouse_sprinkler is not an entity key of another feature of this device`. Write it as the entity ID ends after the device key (`switch_sprinkler`), not as an entity ID.
- A program step whose entity doesn't take the action: `programs: appliance_power does not take turn_on`. Only switches and lights can be turned on, off or toggled.
- A program step with an unknown key (such as `action:`), with two keys, or a program with no `name` or an empty `sequence`. An executable program takes no `phases` yet (`'phases' is an invalid option`), nor a band (`'above' is an invalid option`).
- A device's `programs:` written as a flat map, as before 0.2.0, or with no group: `a device's programs sit under executable: (programs: executable: <key>: …) for dictionary value 'pururu->devices->greenhouse->programs'`. Indent its programs under `executable:`.
- `detected:` in a device's `programs:` (`a device's programs are executable: a detected program sits in the block of the feature whose reading it reads`): move it into the appliance's block. `executable:` in a feature's `programs:` (`a feature's programs are detected: executable programs are the device's`): move it to the device.
- A feature's `programs:` without `detected:`, such as `programs: {}` or a flat map: `a feature's programs needs detected`.
- A detected program without `name`: `a detected program needs a name: it names its entities`.
- A reaction's `then` naming a detected program, which can't be started: `reactions: <reaction>: cotton is not an executable program of this device`.
- A detected program keyed as one of the appliance's entities, such as `idle`, `running` or `cycles_total`: `device clothes_washer: pururu_clothes_washer_appliance_idle_energy_total would be two entities`. Pick another key: see [More detected programs](/concepts/programs#more-detected-programs).
- A detected program keyed as phases' keys begin, whether those phases exist yet or not: `phase` or `phase_…` (the running program's phases: `phase_warming is reserved for the running program's phases (phase, phase_…): name the program otherwise`), or `cotton_phase` or `cotton_phase_…` beside a detected program `cotton` (`cotton_phase_warming is reserved for detected program cotton's phases (cotton_phase, cotton_phase_…): name the program otherwise`). Pick a key no phase could take.
- A reaction with no source or two (`a reaction needs one source: when, entity, at or sun`), with both `to` and `above`/`below` or neither (`a reaction on a state needs to, or above and/or below, not both`), with `from` without `to`, `device` without `when`, `offset` without `sun`, or `to`, `from`, `above`, `below` or `for` on `at` or `sun`. A `retry` on a reaction to an entity (`a reaction's retry goes with at or sun`), with `times × every` over 12 hours (`a reaction's retries must end within 12 hours`), with `every` under a minute or not in whole seconds (`a reaction's retry every must be whole seconds`), or with `times` not a whole number (`a reaction's retry times must be a whole number`).
- A reaction whose `when` isn't an entity of its device (`reactions: door: appliance_power is not an entity key of this device`: add `device:` to point at another device), or of the device it names (`device laundry_lights: reactions: washer_done: light_teto is not an entity key of device clothes_washer`), or whose `device` isn't a device (`device laundry_lights: reactions: washer_done: device dryer is not in devices`).
- Two reactions whose automations would share an ID: `device lights_reaction_b: automation.pururu_lights_reaction_b_reaction_c is already a reaction of device lights`. Rename a device key or a reaction key.
- Two devices that would give an entity the same ID: `device greenhouse_switch: pururu_greenhouse_switch_switch_sprinkler is already an entity of device greenhouse`. Rename a device key or a switch key.

**Developer tools → YAML → Check configuration** shows the same error before you reload.

## I changed something in the UI and it came back

That's expected for what the YAML describes. Floors, areas and a device's `area` follow the YAML at every start and reload. Change the YAML instead. Renaming a device or an entity in the UI, or changing an entity ID, is kept. See [Floors and areas: YAML wins](/concepts/floors-and-areas#yaml-wins).

## `Step … failed`

```
Step dashboard failed
Traceback (most recent call last):
  …
```

Once the entities are created, pururu does the rest in steps: `events`, `devices`, `generate`, `alert2`, `alert lights` and `dashboard`. One that fails is logged with its traceback, and the others still run. The entities stay; only what that step makes is missing until the next reload:

- `events`: the `pururu_state_changed` and `pururu_reading` events.
- `devices`: devices put in their areas, and what the configuration dropped removed.
- `generate`: the programs' scripts, or the automations (the reactions' and the notifications' together, one file), from the part that failed on.
- `alert2`: Alert2's alerts file.
- `alert lights`: lights lent to the alerts.
- `dashboard`: the `/pururu` dashboard.

`Listener failed`, logged the same way after the steps, is the listener that follows renames in the UI: until the next reload, renaming one of pururu's entities, scripts or automations, or disabling an entity a program or an alert's lights follow, doesn't rebuild the entry.

**Fix:** this is a bug in pururu. [Open an issue](https://github.com/thatsnotmynameio/pururu-ha/issues) with the traceback and the configuration of the device it names, if any. A reload tries the step, or the listener, again.

## `Error setting up entry Pururu for pururu`

```
Error setting up entry Pururu for pururu
Traceback (most recent call last):
  …
```

Home Assistant logs this when pururu fails before its steps: while it syncs the floors and areas, builds the devices' entities, or hands them to Home Assistant. The integration shows **Failed to set up**, and none of the steps runs. If the entities were already handed over, pururu takes them back: they show as unavailable until the entry sets up again.

**Fix:** this is a bug in pururu, or in something it relies on. [Open an issue](https://github.com/thatsnotmynameio/pururu-ha/issues) with the traceback. Once the cause is fixed, run `pururu.reload` (**Developer tools → Actions**) or restart Home Assistant: the entry sets up again from scratch.

Home Assistant logs `Setup of config entry 'Pururu' for pururu integration cancelled` instead when the setup was cancelled, for example a `pururu.reload` called by a script or automation that was stopped or restarted meanwhile. pururu takes the entities back all the same: run `pururu.reload` again.

If `Unloading the platforms of a failed setup …` follows it, taking some entities back didn't work:

- `… left some`, after Home Assistant's `Config entry was never loaded!` errors: those platforms never got the entities, so nothing was left behind. A reload sets the entry up.
- Otherwise, run `pururu.reload`. If it logs `has already been setup`, the entities stayed: restart Home Assistant.

## Entities

### `… is already taken by …; not creating it`

```
sensor.pururu_clothes_washer_appliance_power is already taken by the template integration; not creating it
```

Another integration's entity, or an entity without a unique ID, already has that ID. pururu [never takes an ID](/concepts/entity-ids#an-id-already-taken) that belongs to someone else, and it never suffixes one with `_2`.

**Fix:** rename or delete the other entity in **Settings → Entities**, then reload pururu.

### `… follows …, which is not created; not creating it`

```
sensor.pururu_clothes_washer_appliance_phase_current follows binary_sensor.pururu_clothes_washer_appliance_running, which is not created; not creating it
```

This entity depends on one that couldn't be created, usually because of the error above. Fix that one and this one comes back. An [executable program](/concepts/programs#executable-programs) acting on a switch that isn't created isn't created either.

### `automation.… runs script.…, which is not generated; not generating it`

```
automation.pururu_greenhouse_reaction_morning runs script.pururu_greenhouse_program_executable_clean, which is not generated; not generating it
```

A [reaction](/concepts/reactions#starting-a-program)'s `then` names a program whose script isn't generated: an entity it acts on isn't created or is disabled, or its ID is taken. The line logged just before says which. The reaction's automation isn't generated either, since it would start a missing script. When the program is only waiting for a disabled entity, the reaction waits with it and comes back as you left it.

**Fix:** fix the program, and the reaction comes back with it.

### `… watches …, which this device's settings don't create …`

```
binary_sensor.pururu_clothes_washer_alert_month watches sensor.pururu_clothes_washer_appliance_runtime_month, which this device's settings don't create (turn it on, or watch another entity); not creating it
```

An [alert](/concepts/alerts)'s `when` names an entity its feature can create, but not with this device's settings, such as `appliance_runtime_month` without `month` in `statistics.runtime`. The configuration is valid, so that turning the setting on later never breaks the alert, but the alert isn't created until it is.

**Fix:** turn on the setting that creates the entity, or point `when` at another entity, then reload pururu.

### `… has notify, but Alert2 isn't set up to deliver it`

```
binary_sensor.pururu_clothes_washer_alert_long_cycle has notify, but Alert2 isn't set up to deliver it
```

An alert with `notify` is delivered by [Alert2](/concepts/alerts#getting-notified), which isn't installed, or failed to set up. The alert still works as a binary sensor; nobody is told. A [ready-made alert](/features/appliance#ready-made-alerts)'s own texts never log this: only a `notify` you wrote does.

**Fix:** install Alert2 and add [the include](/concepts/alerts#getting-notified) to its `alert2:` block, or remove `notify` from the alert.

### Alert2 doesn't run pururu's alerts

**Settings → Repairs** shows it, and the log says:

```
Alert2 doesn't run pururu's alerts: add "alerts: !include_dir_merge_list pururu/alert2" to the alert2: block of configuration.yaml
```

**Fix:** add that line as the `alerts` of your `alert2:` block, then reload Alert2 in **Developer tools → YAML → Alert2**. See [Getting notified](/concepts/alerts#getting-notified).

### `Duplicate declaration of alert for domain=pururu …`

Alert2 reports it when its old pururu `generator` is still in its `alerts` next to the include. **Fix:** remove the generator. See [Coming from the generator](/concepts/alerts#coming-from-the-generator).

### `Alert2 is not reloaded…`

pururu couldn't reload Alert2. The alerts keep working as binary sensors; Alert2 keeps what it had. pururu tries again the next time it's set up (its reload, or a restart).

- **With a reason** (`Alert2 is not reloaded: …`): Alert2 refused, or isn't there anymore. The reason says why.
- **With a traceback** (`Alert2 is not reloaded` alone): Alert2 failed on its own. Reload Alert2 in **Developer tools → YAML → Alert2** to see whether it happens again, and report the traceback to [Alert2](https://github.com/redstone99/hass-alert2/issues).

### `The Alert2 alerts are not written to pururu/alert2/alerts.yaml: …`

pururu couldn't write the file, usually because of permissions on the configuration folder. Alert2 keeps the last written alerts.

### `… is a pururu switch (or light): name the real one; not creating …`

```
switch.aquecedor is a pururu switch: name the real one; not creating switch.pururu_greenhouse_switch_sprinkler
light.teto is a pururu light: name the real one; not creating light.pururu_biblioteca_light_abajur
```

A switch's or a light's `entity:` names one of pururu's own entities that you renamed in the UI, so it no longer starts with `switch.pururu_` or `light.pururu_`. A [switch](/features/switches) or a [light](/features/lights) stands for a real one.

**Fix:** point `entity:` at the real switch or light, then reload pururu.

### `… is this switch itself: name the real one` (or light)

```
switch.aquecedor is this switch itself: name the real one
light.biblioteca_luminaria is this light itself: name the real one
```

You renamed a pururu switch or light in the UI to the entity its own `entity:` names, so it stands for itself. It's kept, with your rename, but it's `unavailable`: there's nothing real to follow.

**Fix:** point `entity:` at the real switch or light, or rename the pururu one back, then reload pururu.

### `… is a pururu binary sensor: name the real contact; … stands for nothing`

```
binary_sensor.lavadora_rodando is a pururu binary sensor: name the real contact; binary_sensor.pururu_cercado_frente_door_open stands for nothing
```

A door's or window's `contact:` names one of pururu's own binary sensors that you renamed in the UI, so it no longer starts with `binary_sensor.pururu_`. The door is kept, but its `open` is `unavailable` and it records no openings.

**Fix:** point `contact:` at the real contact sensor, then reload pururu.

### `…: Already running`

```
Estufa Limpar: Already running
```

An [executable program](/concepts/programs#executable-programs) was started while it was still running, for example during its `delay`. The start is ignored; the running program goes on. `script.turn_on` returns at once when it starts the program, but not when it's ignored: an automation calling it then stays on that action until the running program's next step or its end, up to its longest `delay` — Home Assistant's behaviour for any single-mode script.

### An entity stays `unknown`

- The `last_cycle_*` sensors are `unknown` until the first cycle **ends**.
- `last_cycle_energy` is `unknown` for a cycle when the energy counter had no value at the start or end of the cycle, or when its unit isn't an energy unit.
- A period sensor (`runtime_month`, `cycles_year`…) starts from its total's current value. If the total has no value yet, the period sensor waits for it.
- A door's `last_opened_by`, `last_opened_via` and `last_direction` are `unknown` after an opening no event described: no `opening` event came within `match` of it. Check that the event's `types` names its `event_type` exactly, and widen `match` if your controller reports late.

### A switch is `unavailable`

A [switch](/features/switches) shows its real switch. It's `unavailable` when the real one is, or when it doesn't exist: check that `entity:` still names it, for example after renaming the real switch, and reload pururu.

### A light is `unavailable`

A [light](/features/lights) shows its real light or switch. It's `unavailable` when the real one is, or when it doesn't exist: check that `entity:` still names it, for example after renaming the real entity, and reload pururu.

### `light.… is not created: the alert lights group … goes without it`

A light of an [alert lights](/concepts/alert-lights) group isn't created, usually because its ID is taken (see `… is already taken by …`). The group's other lights still show its alerts. Free the ID, or take the light out of the group.

### `The alert lights couldn't call light.… on …: …`

Turning a borrowed light on or off failed: its integration refused the call. Followed by a traceback instead of a reason, the light's integration hit a bug of its own: report it there. An `unavailable` light isn't called at all. Either way, a light handed back is still announced (`pururu_alert_lights_released`), and the alert lights go on: the next `repeat`, or the next change of the light or its alerts, tries again.

### The cycle ends too early, or never starts

- **Ends in the middle of a wash:** the appliance paused for longer than `off_delay`. Increase `off_delay`.
- **Never starts:** the power never stays above `above` for `on_delay`. Check the power sensor's history, and lower `above` or shorten `on_delay`.
- **Starts on its own:** standby spikes last longer than `on_delay`, or `above` is below the standby power.

See [Picking the numbers](/getting-started/first-device#picking-the-numbers).

## Devices

### `Device … is not placed: its area … is not created`

```
Device clothes_washer is not placed: its area despensa is not created
```

The device's area exists in the YAML, but Home Assistant refused to create it (see [Floors and areas](#floors-and-areas) below). The device and its entities are still created, in the area they already had. Fix the area's error and reload.

## Floors and areas

### `Floor … is left out: …` and `Area … is left out: …`

```
Area atelie is left out: The name Ateliê (atelie) is already in use
```

Home Assistant refused to create a **new** floor or area, because its name, or its key, is already the name of a floor or area that isn't in the YAML. Nothing is created for it.

**Fix:** rename or delete the other floor or area in the UI, or choose another `name` or key. Then reload.

### `Floor … is not synced: …` and `Area … is not synced: …`

The same refusal for a floor or area that **already exists**. It keeps its current settings and is still managed by pururu.

### `Area … is not synced: its floor … is not created`

```
Area atelie is not synced: its floor terreo is not created
```

The area's floor was left out (see above), so the area isn't created or updated either. Fix the floor and the area follows.

## Dashboard

### `The dashboard is not created: /pururu is already taken`

Another panel or dashboard already uses `/pururu`. pururu adds no dashboard, and everything else works. Remove or move the other dashboard (**Settings → Dashboards**), then reload pururu.

### `The dashboard is not created: lovelace is not set up`

pururu found Home Assistant's dashboards (`lovelace`) not loaded. That shouldn't happen, because pururu requires `lovelace` and Home Assistant loads it first. Please [open an issue](https://github.com/thatsnotmynameio/pururu-ha/issues) with the log and your Home Assistant version.

### `The dashboard is not created: lovelace's or frontend's API changed`

HA has no public way for an integration to add a dashboard, so pururu relies on Home Assistant internals. This error means a newer Home Assistant changed them. Everything else still works. Please [open an issue](https://github.com/thatsnotmynameio/pururu-ha/issues) with the log's traceback and your Home Assistant version.

## Reactions

### The reactions' and notifications' automations aren't loaded

**Settings → Repairs** shows it, and the log says:

```
The automations of pururu's reactions and notifications are not loaded: add "automation pururu: !include_dir_merge_list pururu/automations" to configuration.yaml
```

The reactions' and the ready-made notifications' automations are one file, `pururu/automations/automations.yaml`, so one line loads both and one issue says it's missing.

**Fix:** add that line to `configuration.yaml`, then reload automations in **Developer tools → YAML → Automations**. See [The include](/concepts/reactions#the-include) and [Notifications: the file and the include](/concepts/notifications#the-file-and-the-include).

### `automation.… follows …, which is not created; not generating it`

```
automation.pururu_laundry_lights_reaction_month follows sensor.pururu_clothes_washer_appliance_runtime_month, which is not created; not generating it
```

The reaction's `when` names a pururu entity that isn't created: its ID is taken, or the device's settings don't create it. Fix that entity, or point `when` at another one, then reload pururu.

### `automation.… is already taken by …; not generating it`

```
automation.pururu_laundry_lights_reaction_door is already taken by automation.mine, an automation with the same ID; not generating it
```

Another automation already has the entity ID the reaction's automation would have, or one of your own automations has the same `id`. pururu never takes over an automation it didn't write. Rename or delete that one in **Settings → Entities** (or change its `id`), then reload pururu.

### `The automations are not written to pururu/automations/automations.yaml: …`

pururu couldn't write the file, usually because of permissions on the configuration folder. The devices keep working; the reactions and the ready-made notifications keep their last written automations.

## Executable programs

### The programs' scripts aren't loaded

**Settings → Repairs** shows it, and the log says:

```
The scripts of pururu's programs are not loaded: add "script pururu: !include_dir_merge_named pururu/scripts" to configuration.yaml
```

**Fix:** add that line to `configuration.yaml`, then reload scripts in **Developer tools → YAML → Scripts**. See [The include](/concepts/programs#the-include).

### `script.… follows …, which is not created; not generating it`

```
script.pururu_greenhouse_program_executable_clean follows switch.pururu_greenhouse_switch_sprinkler, which is not created; not generating it
```

An entity the program acts on isn't created, usually because its ID is taken. Fix that entity, then reload pururu.

### `script.… acts on …, which is disabled; not generating it`

```
script.pururu_greenhouse_program_executable_clean acts on switch.pururu_greenhouse_switch_sprinkler, which is disabled; not generating it
```

You disabled an entity the program acts on. Until you enable it again, the script is `unavailable` and starting it does nothing. Enable it again and the program comes back, with what you set on its script (disabled, entity ID, area).

### `script.… is already taken by …; not generating it`

```
script.pururu_greenhouse_program_executable_clean is already taken by script.mine, a script with the same ID; not generating it
```

A script of your own, or of another integration, has the program's ID. pururu never takes it over: rename or remove the other script, or give the program another key.

## Still stuck?

[Open an issue](https://github.com/thatsnotmynameio/pururu-ha/issues) with your `pururu:` block, the errors from the log and your Home Assistant version.
