title: Entity IDs
description: Every entity pururu creates has a predictable ID. pururu follows your renames and never takes an ID that belongs to someone else.
---

## The pattern

Every entity pururu creates has the ID

```
<platform>.pururu_<device key>_<namespace>_<entity key>
```

- **platform**: `sensor`, `binary_sensor`, `switch` or `light`.
- **device key**: the device's key under `devices:`.
- **namespace**: the feature or device key that creates the entity. Each has its own, so two features never give two entities one ID.
- **entity key**: which of the feature's entities it is. Each feature's page lists its entity keys. An entity key counted per period ends with that period, as in `runtime_month`.

| Feature or device key | Namespace | Example |
|---|---|---|
| [`appliance`](/features/appliance) | `appliance` | `binary_sensor.pururu_clothes_washer_appliance_running`, `sensor.pururu_clothes_washer_appliance_phase_warming_cycles_total`, `binary_sensor.pururu_clothes_washer_appliance_cotton` (a detected program) |
| [`door`](/features/door) | `door` | `binary_sensor.pururu_porta_cercado_frente_door_open` |
| [`window`](/features/window) | `window` | `binary_sensor.pururu_janela_quarto_window_open` |
| [`lights`](/features/lights) | `light` | `light.pururu_biblioteca_light_teto` |
| [`switches`](/features/switches) | `switch` | `switch.pururu_greenhouse_switch_sprinkler` |
| [`alerts`](/concepts/alerts) | `alert` | `binary_sensor.pururu_clothes_washer_alert_long_cycle` |
| [`programs`](/concepts/programs) | `program` | `script.pururu_greenhouse_program_executable_clean` (a Home Assistant script), `sensor.pururu_greenhouse_program_executable_clean_cycles_total` |
| [`reactions`](/concepts/reactions) | `reaction` | `automation.pururu_greenhouse_reaction_morning` (a Home Assistant automation), `sensor.pururu_greenhouse_reaction_morning_triggered_total` |

There's no exception, even when an entity key is the same word as its namespace: a switch keyed `switch` is `switch.pururu_greenhouse_switch_switch`.

So the `running` entity of the device `clothes_washer` is always `binary_sensor.pururu_clothes_washer_appliance_running`. You can write automations and dashboards against it before the device even exists.

A [detected program](/concepts/programs#more-detected-programs)'s key is an entity key of the appliance's namespace (`cotton` → `binary_sensor.pururu_clothes_washer_appliance_cotton`), so it can't be one the appliance already creates, such as `running` or `cycles_total`, nor one a phase could take later (`phase_…`, or `cotton_phase_…` beside a program `cotton`): that's a configuration error, told at once.

The entity's **unique ID** is the same text without the platform: `pururu_clothes_washer_appliance_running`. That's what Home Assistant uses to remember the entity's settings and history across restarts.

## Names

An entity's name comes from its entity key, in Home Assistant's language: English and Portuguese are translated. It's shown after the device's name, so `running` on **Tanquinho** is **Tanquinho Running**, or **Tanquinho Em funcionamento** in Portuguese. You can rename any entity in the UI as usual.

A [switch](/features/switches)'s, a [light](/features/lights)'s, or an [alert](/concepts/alerts)'s entity key is the key you gave it, so its name is the `name:` you wrote, the same in every language. An [executable program](/concepts/programs#executable-programs)'s script is named `<device name> <name:>` too.

## Renaming an entity ID

You can change an entity ID in the UI, as with any entity. pururu handles it this way:

- The entity **stays in its device** and keeps its history.
- Everything that reads it **follows the new ID**. For example, a phase's runtime reads its binary sensor, and a monthly counter reads its total. pururu reloads itself when you rename one of its entities, so this happens straight away.
- The rename **survives restarts and reloads**. pururu finds the entity by its unique ID, not by its ID.

<Info>
  Automations and dashboards you wrote yourself don't follow a rename. Home Assistant doesn't update them for any integration. Update them or keep the original ID.
</Info>

## An ID already taken

pururu **never** creates an entity whose ID already belongs to someone else, whether that's another integration's entity or an entity without a unique ID. It also never falls back to `…_2`. A suffixed ID would silently break every automation written against the predictable one. Instead:

1. The log shows an error: `sensor.pururu_clothes_washer_appliance_power is already taken by the template integration; not creating it`.
2. The entity isn't created.
3. Anything that depends on it isn't created either, each with its own error: `… follows …, which is not created; not creating it`. For example, if `running` can't be created, the whole cycle goes with it: the last cycle sensors, the counters and the phases.

The rest of the device is still created. To fix it, free the ID (rename or delete the other entity) and reload pururu.

## Entities pururu removes

At every start and reload, pururu deletes the entities and devices that the YAML no longer creates. For example:

- If you remove `energy` (and `statistics.idle_energy`, which needs it), then `energy_total`, `last_cycle_energy` and `idle_energy_total` go away.
- If you remove `month` from `statistics.cycles`, then `cycles_month` goes away.
- If you remove a device, the device and all its entities go away.

Their history stays in the recorder until it's purged, as with any deleted entity.
