title: Entity IDs
description: Every entity pururu creates has a predictable ID. pururu follows your renames and never takes an ID that belongs to someone else.

## The pattern

Every entity pururu creates has the ID

```
<platform>.pururu_<device key>_<namespace>_<entity key>
```

- **platform**: `sensor`, `binary_sensor`, `switch` or `light`.
- **device key**: the device's key under `devices:`.
- **namespace**: the feature or device key that creates the entity. Each has its own, so two features never give two entities one ID.
- **entity key**: which of the feature's entities it is. Each feature's page lists its entity keys. An entity key counted per period ends with that period, as in `runtime_month`. The YAML doesn't name an entity by its entity key, but by its path: see [References](#references).

| Feature or device key | Namespace | Example |
|---|---|---|
| [`appliance`](/features/appliance) | `appliance` | `binary_sensor.pururu_clothes_washer_appliance_running`, `sensor.pururu_clothes_washer_appliance_phase_warming_cycles_total`, `binary_sensor.pururu_clothes_washer_appliance_cotton` (a detected program) |
| [`door`](/features/door) | `door` | `binary_sensor.pururu_porta_frente_door_open` |
| [`window`](/features/window) | `window` | `binary_sensor.pururu_janela_quarto_window_open` |
| [`lights`](/features/lights) | `light` | `light.pururu_biblioteca_light_teto` |
| [`switches`](/features/switches) | `switch` | `switch.pururu_greenhouse_switch_sprinkler` |
| [`buttons`](/features/buttons) | `button` | `button.pururu_biblioteca_button_ler`, `sensor.pururu_biblioteca_button_ler_triggered_total` |
| [`alerts`](/concepts/alerts) | `alert` | `binary_sensor.pururu_clothes_washer_alert_long_cycle` |
| [`programs`](/concepts/programs) | `program` | `script.pururu_greenhouse_program_executable_clean` (a Home Assistant script), `sensor.pururu_greenhouse_program_executable_clean_cycles_total` |
| [`reactions`](/concepts/reactions) | `reaction` | `automation.pururu_greenhouse_reaction_morning` (a Home Assistant automation), `sensor.pururu_greenhouse_reaction_morning_triggered_total` |

There's no exception, even when an entity key is the same word as its namespace: a switch keyed `switch` is `switch.pururu_greenhouse_switch_switch`.

So the `running` entity of the device `clothes_washer` is always `binary_sensor.pururu_clothes_washer_appliance_running`. You can write automations and dashboards against it before the device even exists.

A [detected program](/concepts/programs#more-detected-programs)'s key is an entity key of the appliance's namespace (`cotton` → `binary_sensor.pururu_clothes_washer_appliance_cotton`), so it can't be one the appliance already creates, such as `running` or `cycles_total`, nor one a phase could take later (`phase_…`, or `cotton_phase_…` beside a program `cotton`): that's a configuration error, told at once.

The entity's **unique ID** is the same text without the platform: `pururu_clothes_washer_appliance_running`. That's what Home Assistant uses to remember the entity's settings and history across restarts.

## References

The entity ID is how Home Assistant names an entity. The `pururu:` YAML names it another way, by its **reference**: what you wrote, read from the YAML itself, without knowing how pururu builds its IDs. A reference's first word says whose the entity is:

| First word | Whose | Reference |
|---|---|---|
| a block of this device (`appliance`, `switches`, `alerts`…) | this device's | its path: `appliance.running_program` |
| `device` | another device's | `device.`, its device key, then the path as that device writes it: `device.clothes_washer.appliance.running_program` |
| `homeassistant` | Home Assistant's | `homeassistant.`, then its entity ID: `homeassistant.binary_sensor.porta_despensa` |

Anything else is refused, with its place in the YAML.

### The path

An entity's **path** is the way down through its device's YAML to it, from the block you wrote under the device, each level separated by a dot:

- **Every level you wrote is in it**, the words that only give the YAML its shape too: the cotton program's `other` phase is `appliance.programs.detected.cotton.other`.
- **What you declared is its own entity**: a switch `switches.sprinkler`, a light `lights.teto`, a button `buttons.ler`, an alert `alerts.long_cycle`, a ready-made one `appliance.alerts.offline`, a phase `appliance.running_program.phases.warming`. `appliance.running_program` is the appliance running, and `appliance.programs.detected.cotton` the cotton program running. `power` and `energy` name the entity made from them: `appliance.power`, `appliance.energy`.
- **What pururu creates on its own sits under what it belongs to**, by the name its feature's page gives it: the running program's last cycle is `appliance.running_program.last_cycle_end`, a door's `open` is `door.open`, a program's runs `programs.executable.clean.cycles_total`, a reaction's triggers `reactions.washer_done.triggered_total`.
- **A period of `statistics:` is the last word**: `cycles: [month]` in the cotton program is `appliance.programs.detected.cotton.statistics.cycles.month`.

The path is written in full, always: no level is skipped, and a dot separates levels, never the words of one key (`last_cycle_end` is one key).

### Path and entity key

The entity ID's **entity key** (`running`, `phase_warming_cycles_total`) is how pururu names the entity inside its namespace; the **path** is how you write it in the YAML. They differ wherever the YAML's levels aren't in the ID:

| Entity ID | Path |
|---|---|
| `binary_sensor.pururu_clothes_washer_appliance_running` | `appliance.running_program` |
| `sensor.pururu_clothes_washer_appliance_phase_warming_cycles_total` | `appliance.running_program.phases.warming.cycles_total` |
| `sensor.pururu_clothes_washer_appliance_cotton_phase_other_energy_month` | `appliance.programs.detected.cotton.other.statistics.energy.month` |
| `switch.pururu_greenhouse_switch_sprinkler` | `switches.sprinkler` |
| `sensor.pururu_greenhouse_program_executable_clean_cycles_total` | `programs.executable.clean.cycles_total` |

Each feature's page gives every entity's path next to its ID. Renaming an entity in the UI changes its ID, never its path.

### Which form each field takes

| Field | Takes | Example |
|---|---|---|
| An [alert](/concepts/alerts)'s `when`, a [program](/concepts/programs#steps)'s steps | a path of this device | `when: appliance.running_program` |
| A [reaction](/concepts/reactions)'s `when` | any reference, or an [executable program](/concepts/reactions#an-executable-program) running | `when: device.clothes_washer.appliance.running_program`, `when: programs.executable.clean` |
| A group of [alert lights](/concepts/alert-lights) | a light, as from another device | `default: [device.biblioteca.lights.teto]` |
| `power`, `energy`, `contact`, the `entity` of a switch, a light, a button or an event entity, `notify` | Home Assistant's, only | `power: homeassistant.sensor.washer_plug_power`, `notify: homeassistant.notify.mobile_app_phone` |
| A device's `area`, an area's `floor`, a reaction's `then`, a button's `program`, an alert's `lights` | one kind of thing, so its key alone | `area: despensa`, `then: clean`, `lights: default` |

Inside a device, `device.` names another device only: a device naming itself that way is refused with the form to write (`alerts: device.clothes_washer.appliance.running_program is this device's: write appliance.running_program`). An entity pururu creates is never written as Home Assistant's: in a reaction's `when`, `homeassistant.binary_sensor.pururu_clothes_washer_appliance_running` is refused, saying to write `device.clothes_washer.appliance.running_program`.

### The `reference` attribute

Every entity pururu creates shows its reference in its `reference` attribute, in both forms: `inside`, its path, as its own device writes it, and `outside`, as another device writes it.

```yaml
reference:
  inside: appliance.running_program.last_cycle_end
  outside: device.clothes_washer.appliance.running_program.last_cycle_end
```

So an entity seen in Home Assistant, in its details or in **Developer tools → States**, tells you what to write. It's there even while the entity is `unavailable`, when you're most likely to write an alert on it. It never changes, so Home Assistant's history doesn't record it. The [events](/concepts/events) pururu fires carry the same two forms, as `key` and `event_name`.

## Names

An entity's name comes from its entity key, in Home Assistant's language: English and Portuguese are translated. It's shown after the device's name, so `running` on **Tanquinho** is **Tanquinho Running**, or **Tanquinho Em funcionamento** in Portuguese. You can rename any entity in the UI as usual.

A [switch](/features/switches)'s, a [light](/features/lights)'s, a [button](/features/buttons)'s, or an [alert](/concepts/alerts)'s entity key is the key you gave it, so its name is the `name:` you wrote, the same in every language. An [executable program](/concepts/programs#executable-programs)'s script is named `<device name> <name:>` too.

## Renaming an entity ID

You can change an entity ID in the UI, as with any entity. pururu handles it this way:

- The entity **stays in its device** and keeps its history.
- Everything that reads it **follows the new ID**. For example, a phase's runtime reads its binary sensor, and a monthly counter reads its total. pururu reloads itself when you rename one of its entities, so this happens straight away.
- The rename **survives restarts and reloads**. pururu finds the entity by its unique ID, not by its ID.

<Info>
  Automations and dashboards you wrote yourself don't follow a rename. Home Assistant doesn't update them for any integration. Update them or keep the original ID.
</Info>

## An ID already taken

pururu **never** creates an entity whose ID already belongs to someone else, whether that's another integration's entity or an entity without a unique ID. It also never falls back to `…_2`. A suffixed ID would silently break every automation written against the predictable one. Instead:

1. The log shows an error: `sensor.pururu_clothes_washer_appliance_power is already taken by the template integration; not creating it`.
2. The entity isn't created.
3. Anything that depends on it isn't created either, each with its own error: `… follows …, which is not created; not creating it`. For example, if `running` can't be created, the whole cycle goes with it: the last cycle sensors, the counters and the phases.

The rest of the device is still created. To fix it, free the ID (rename or delete the other entity) and reload pururu.

## Entities pururu removes

At every start and reload, pururu deletes the entities and devices that the YAML no longer creates. For example:

- If you remove `energy` (and `statistics.idle_energy`, which needs it), then `energy_total`, `last_cycle_energy` and `idle_energy_total` go away.
- If you remove `month` from `statistics.cycles`, then `cycles_month` goes away.
- If you remove a device, the device and all its entities go away.

Their history stays in the recorder until it's purged, as with any deleted entity.
