---
title: Events
description: pururu fires an event on Home Assistant's bus for every change of its entities, so an automation can send it anywhere, such as a webhook.
---

Everything pururu knows ends up in the state of one of its entities: a cycle's end is `last_cycle_end`, who opened a door is `last_opened_by`, an alert is its binary sensor. With `config: events:`, pururu also **fires an event on Home Assistant's bus** each time one of those states changes, with the change and a snapshot of the whole device. pururu sends nothing over the network itself: an automation of yours takes the event from the bus and posts it, for example to a webhook.

```yaml title="configuration.yaml"
pururu:
  config:
    events: [state_changed, reading]
  devices:
    clothes_washer:
      name: Tanquinho
      appliance:
        power: homeassistant.sensor.washer_plug_power
        energy: homeassistant.sensor.washer_plug_energy
        running_program: {above: 4, on_delay: {minutes: 1}, off_delay: {minutes: 2}}
```

## Two classes

| Class | Event type | Which changes |
|---|---|---|
| `state_changed` | `pururu_state_changed` | Entities **without** a `state_class`: facts such as `running`, a phase, an alert, a door, `last_opened_by`, the last cycle's values, switches, lights, buttons (each press: its time). |
| `reading` | `pururu_reading` | Entities **with** a `state_class`: series such as the power and energy mirrors, totals and per-period meters. They can change every few seconds. |

`config: events:` lists the classes to fire, each once. Leave it out (the default) and pururu fires nothing. A class you don't list is never fired. **Developer tools → YAML → Pururu** applies a change.

A change is fired when the state itself changes. pururu doesn't fire:

- an entity appearing or going, as at every reload;
- Home Assistant's placeholder (`unavailable` with `restored: true`), written while an entity unloads or hasn't loaded yet;
- a change of attributes alone.

`unavailable` and `unknown` are fired: they are real states. An entity pururu didn't create, because another integration holds its ID, isn't pururu's and is never fired.

## The data

```json
{
  "event_id": "01J8Z3K4QW6N5V2XK0M7T9R8YB",
  "event_name": "device.clothes_washer.appliance.running_program.last_cycle_end",
  "event_class": "state_changed",
  "entity_id": "sensor.pururu_clothes_washer_appliance_last_cycle_end",
  "device": "clothes_washer",
  "device_name": "Tanquinho",
  "key": "appliance.running_program.last_cycle_end",
  "old": "2026-09-27T20:10:00+00:00",
  "new": "2026-09-28T09:52:00+00:00",
  "time": "2026-09-28T09:52:00.123456+00:00",
  "attributes": {"device_class": "timestamp", "friendly_name": "Tanquinho Fim do último ciclo"},
  "states": {
    "appliance.running_program": "off",
    "appliance.running_program.last_cycle_start": "2026-09-28T09:00:00+00:00",
    "appliance.running_program.last_cycle_duration": "52.0",
    "appliance.running_program.last_cycle_energy": "0.42",
    "appliance.running_program.last_cycle_end": "2026-09-28T09:52:00+00:00",
    "appliance.running_program.cycles_total": "12"
  }
}
```

| Field | What |
|---|---|
| `event_id` | A new ID per event (a ULID: unique, sorted by time). Use it to drop duplicates. |
| `event_name` | The entity's reference from another device, `device.<device>.<path>`: what another device's YAML writes to name it. It doesn't change when you rename the entity in the UI. |
| `event_class` | `state_changed` or `reading`, since a webhook gets the data without the event type. |
| `entity_id` | The entity's current ID. |
| `device`, `device_name` | The device's key and its `name`. |
| `key` | The entity's path in its device's YAML, its reference from inside the device: `appliance.running_program`, `appliance.running_program.phases.warming.cycles_total`. It stays the same when you rename the entity. |
| `old`, `new` | The states, as Home Assistant's text. |
| `time` | When the state changed. |
| `attributes` | The new state's attributes, as JSON: a time is ISO text. The entity's `reference` attribute is left out: `event_name` and `key` already carry both its forms. |
| `states` | Every entity of the device that has a state (a disabled one has none), by its path (`key`), when the event was fired. |

A finished cycle comes in one event: `last_cycle_end` is written last, so when it changes, `states` already holds that cycle's start, duration, energy and count.

Every pururu entity shows the same two forms in its `reference` attribute (`inside`, as `key`; `outside`, as `event_name`), so an entity seen in Home Assistant tells you the name its events carry. A path follows the YAML: should a later version of pururu move a block, the events and `states` keys of its entities take the new path, with no error.

### Reading `states`

The keys of `states` are flat strings, each one entity's whole path. `appliance.running_program` and `appliance.running_program.last_cycle_end` are two keys side by side, not one inside the other. Read them with brackets: in a template, `trigger.event.data.states.appliance` is undefined, with no error. A receiver must never expand the dots into nested objects: `appliance.running_program` holds `off`, so it can't also hold `last_cycle_end`.

```yaml title="configuration.yaml"
automation:
  - alias: Washer done
    triggers:
      - trigger: event
        event_type: pururu_state_changed
        event_data:
          event_name: device.clothes_washer.appliance.running_program.last_cycle_end
    actions:
      - action: persistent_notification.create
        data:
          title: Tanquinho
          message: "Done: {{ trigger.event.data.states['appliance.running_program.last_cycle_energy'] }} kWh"
```

## Sending them to a webhook

A `rest_command` posts the data, and an automation calls it for each event:

```yaml title="configuration.yaml"
rest_command:
  webhook_pururu:
    url: !secret webhook_pururu_url
    method: post
    headers:
      X-Webhook-Token: !secret webhook_pururu_token
    content_type: application/json
    payload: "{{ event | tojson }}"

automation:
  - alias: pururu → webhook
    mode: queued        # one at a time, in order
    max: 1000
    triggers:
      - trigger: event
        event_type: [pururu_state_changed, pururu_reading]
    actions:
      - action: rest_command.webhook_pururu
        data:
          event: "{{ trigger.event.data }}"
```

To send only some events, add a condition to the automation, such as `{{ trigger.event.data.device == 'clothes_washer' }}`. To send each class to its own webhook, write two automations.

The receiving side takes them as `POST` requests, checks the `X-Webhook-Token` header against the same token, and can route them on `event_class` or `event_name`. For a finished cycle, match `key` `appliance.running_program.last_cycle_end` and read the values from `states`, each by its whole path as one flat key.

## The recorder

Home Assistant's recorder saves every event on the bus, and readings can change every few seconds. Their values are already saved as the entities' states, so leave the events out of the database:

```yaml title="configuration.yaml"
recorder:
  exclude:
    event_types:
      - pururu_reading
      - pururu_state_changed
```

The automation still gets them: the recorder's `exclude` only stops them being saved.
