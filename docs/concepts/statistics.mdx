---
title: Statistics
description: How much a total grew in the current period. A meter per period, reset by Home Assistant's own utility meter.
---

Several counters keep a running total, all time: an appliance's cycles, a door's openings, a program's runs. `statistics:` asks for the same total **per period**: how much it grew today, this week, this month, this year. Each is a sensor of its own, built on Home Assistant's `utility_meter`, and it resets itself when the period turns over.

```yaml
pururu:
  devices:
    clothes_washer:
      name: Tanquinho
      appliance:
        power: homeassistant.sensor.washer_plug_power
        running_program:
          above: 4
          on_delay: {minutes: 1}
          off_delay: {minutes: 2}
          statistics:
            runtime: [today, week, month, year]
            cycles: [today, week, month, year]
```

## Periods

<Property name="today, week, month, year" type="list of periods">
  Each listed at most once. They reset in Home Assistant's time zone: `today` at midnight, `week` on Monday, `month` on the 1st and `year` on 1 January.
</Property>

An empty list, or leaving the counter out, asks for none: the total, when the builder has it, still exists, just not a per-period meter for it.

## Where it sits

`statistics:` is a key of the block that has the counter, one map of **counter → periods**:

- A feature's own block, for what it counts on its own: `appliance`'s `idle_energy`, [`door`](/features/door#settings)'s and [`window`](/features/window)'s.
- The appliance's `running_program`, once: `runtime` and `cycles`, the appliance's own totals. See [The running program](/concepts/programs#the-running-program).
- Each of `running_program`'s phases, and `other`: `runtime`, `cycles` and `energy`, each with its own meters. See [Phases](/concepts/programs#phases).
- Each detected program in the appliance's `programs: detected:`, inside it, and each of its phases and its `other`: `runtime`, `cycles` and `energy`. See [More detected programs](/concepts/programs#more-detected-programs).
- Each [executable program](/concepts/programs#settings), inside it, next to its `sequence`.
- Each [reaction](/concepts/reactions#settings), inside it, next to its `then`.
- Each [button](/features/buttons#settings), inside it, next to its `state`.

Only a counter the builder actually has takes settings; anything else is an unknown key, a configuration error.

## The counters

| Builder | Counter | Needs | Per |
|---|---|---|---|
| [`appliance`](/features/appliance#settings) | `idle_energy` | `energy` | the device |
| `appliance`'s `running_program` | `runtime`, `cycles` | | the device |
| `running_program`'s phases, `other` | `runtime`, `cycles` | | phase |
| `running_program`'s phases, `other` | `energy` | `energy` | phase |
| a detected program (`programs: detected:`), its phases, `other` | `runtime`, `cycles` | | program, phase |
| a detected program, its phases, `other` | `energy` | `energy` | program, phase |
| [`door`](/features/door#settings), [`window`](/features/window) | `openings`, `open_time` | | the device |
| [`programs: executable:`](/concepts/programs#statistics) | `runtime`, `cycles` | | program |
| [`reactions`](/concepts/reactions#statistics) | `triggered` | | reaction |
| [`buttons`](/features/buttons#statistics) | `triggered` | | button |

A counter under **Needs** takes no periods without that other setting: `appliance`'s `idle_energy` needs `energy`, so does a phase's or a detected program's `energy`, which needs the appliance's own. Asking for it without the setting is a configuration error, `statistics.energy needs energy`; asking for none (`energy: []`) is fine either way.

## Entities

Each meter is `sensor.pururu_<key>_<namespace>_<counter>_<period>`, for a block's own counter, or `sensor.pururu_<key>_<namespace>_<item>_<counter>_<period>` for a phase's, a program's, a reaction's or a button's, `<item>` its slug (`phase_<key>`, `phase_other`; a detected program's phase `<program>_phase_<key>`, `<program>_phase_other`; an executable program `executable_<key>`) or its key (a detected program, a reaction, a button).

It's named after the device, the counter and the period: **Tanquinho Runtime today**. Per item, the item's own name goes between the device's name and the counter's, as in a phase's meters, [`programs`](/concepts/programs#statistics), [`reactions`](/concepts/reactions#statistics) and [`buttons`](/features/buttons#statistics): **Tanquinho Aquecendo cycles today**, or a detected program's, **Tanquinho Algodão cycles today**. `other`'s meters are named by their own translations instead: **Tanquinho Other phase cycles today**; a detected program's `other`'s carry its name: **Tanquinho Algodão other phase cycles today**.

Its [path](/concepts/entity-ids#references), the way an alert or a reaction names it, follows the YAML: the block's path, then `statistics`, the counter and the period, as you wrote them. `runtime: [today]` in the washer's `running_program` is `appliance.running_program.statistics.runtime.today`; the `warming` phase's `cycles: [month]` is `appliance.running_program.phases.warming.statistics.cycles.month`; a reaction's `triggered: [month]` is `reactions.<reaction>.statistics.triggered.month`.

Every meter's unique ID is its entity ID without the platform, and it survives restarts and reloads: it's Home Assistant's `utility_meter`, seeded from the total's current value the first time it's added, so it doesn't sit at `unknown` until the total next changes.

## Removing it

Dropping a period, a counter, or `statistics:` itself from the YAML removes that meter, as any entity a setting stops creating. The total it metered keeps counting; only the per-period sensor goes.
