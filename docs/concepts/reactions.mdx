---
title: Reactions
description: How a device behaves. Each reaction listens to one thing, can start one of the device's programs, and becomes a Home Assistant automation.
---

A device **reacts** to what happens around it: one of its own entities changing, another device's, any entity in Home Assistant, a time of day, or the sun. When it fires, it can start one of the device's [programs](/concepts/programs): the reaction decides **when**, the program **what**. It can also tell a [message](/concepts/notifications#a-reactions-message) to your phone. Each reaction you declare becomes a real **Home Assistant automation**. It shows up in **Settings → Automations & scenes** with its traces and its on/off toggle.

```yaml title="configuration.yaml"
pururu:
  devices:
    laundry_washer:
      name: Máquina de lavar
      appliance:
        power: sensor.washer_plug_power
        running: {threshold: 4, on_delay: {minutes: 1}, off_delay: {minutes: 2}}
    laundry_lights:
      name: Luzes da lavanderia
      lights:
        teto: {entity: light.lavanderia_teto, name: Teto}
      programs:
        blink:
          name: Piscar
          sequence: [{turn_on: light_teto}, {delay: 2}, {turn_off: light_teto}]
      reactions:
        teto_on:     {name: Teto acendeu, when: light_teto, to: "on"}
        washer_done: {name: Lavadora terminou, device: laundry_washer, when: appliance_running, from: "on", to: "off", then: blink}
        door:        {name: Porta abriu, entity: binary_sensor.porta_lavanderia, to: "on", for: {minutes: 5}}
        night:       {name: Noite, at: "22:00"}
        dusk:        {name: Anoitecer, sun: sunset, offset: {minutes: -30}}

automation pururu: !include_dir_merge_list pururu/automations
script pururu: !include_dir_merge_named pururu/scripts   # the programs a reaction starts
```

This creates `automation.pururu_laundry_lights_reaction_washer_done`, shown as **Luzes da lavanderia Lavadora terminou**, which blinks the ceiling light when the washer finishes, and one automation for each other reaction.

## The include

pururu writes the automations to `pururu/automations/reactions.yaml`, in a `pururu` folder next to `configuration.yaml`. Home Assistant only loads automations its configuration names, so add this line **once** to `configuration.yaml`:

```yaml title="configuration.yaml"
automation pururu: !include_dir_merge_list pururu/automations
```

The line goes in `configuration.yaml` itself, not in a package: an include's path is relative to the file that contains it. It includes the folder, not the file, so Home Assistant still starts when the folder isn't there yet (before pururu first runs): a missing folder is no automations. pururu always writes the file, even without reactions: then it's an empty list. It lives next to your own `automation: !include automations.yaml`, which it doesn't touch. After adding it, restart Home Assistant, or reload automations in **Developer tools → YAML → Automations**.

Until the line is there, the automations exist only in the file. **Settings → Repairs** shows **The reactions' automations aren't loaded**, with the line to add, and the log says the same. The repair goes away once the automations load.

<Warning>
  Don't edit `pururu/automations/reactions.yaml`, and don't put your own files in `pururu/automations`: the include loads every file there. pururu rewrites it whenever the configuration changes. The automations show as read-only in the editor because they come from YAML. Change the reaction instead.
</Warning>

## Settings

`reactions` is a key of a device, next to `name` and `area`. It's a map of **reaction key → reaction**, with at least one reaction. The key is a slug, and it ends the automation's ID after the namespace `reaction`: `washer_done` → `automation.pururu_laundry_lights_reaction_washer_done`. `reactions` isn't a feature: a device still needs at least one feature.

<Property name="name" type="string" required>
  Shown after the device's name, as the automation's name. It can't be empty, and it's the same in every language.
</Property>

A reaction listens to **exactly one** of these sources.

### An entity of the device

<Property name="when" type="entity key">
  An entity of **this device**, written as its entity ID ends after the device key: `light_teto`, `appliance_running`, `alert_overload`. See [Entity IDs](/concepts/entity-ids#the-pattern).
</Property>

### An entity of another device

<Property name="device" type="device key">
  The key of another device under `devices:`, with `when` naming one of **its** entities: `device: laundry_washer`, `when: appliance_running`.
</Property>

### Any entity

<Property name="entity" type="entity ID">
  Any entity in Home Assistant: `binary_sensor.porta_lavanderia`.
</Property>

### What an entity must do

For `when` and `entity`, give **either** `to` **or** `above`/`below`:

<Property name="to" type="state" optional>
  The state it changes to: `"on"`, `"off"`, `spinning`. `on` and `off` work with or without quotes. Any other value is compared as text, as Home Assistant does: `to: 1` matches a state of `1`, not `1.0`.
</Property>

---

<Property name="from" type="state" optional>
  The state it must change from. Only with `to`.
</Property>

---

<Property name="above, below" type="number" optional>
  Fires when a number crosses into the range: strictly above `above`, strictly below `below`. Give one or both; `above` must be lower than `below`.
</Property>

---

<Property name="for" type="time period" optional>
  How long the new state must hold before the reaction fires, such as `{minutes: 5}`. A [time period](/features/appliance#settings).
</Property>

### A time of day

<Property name="at" type="time">
  `"22:00"` or `"22:00:30"`, every day.
</Property>

### The sun

<Property name="sun" type="sunrise | sunset">
  Fires at sunrise or sunset, where Home Assistant says your home is.
</Property>

---

<Property name="offset" type="time period" optional>
  Before (negative) or after the sun event: `{minutes: -30}` is half an hour before sunset. Only with `sun`.
</Property>

### Retry

<Property name="retry.times" type="integer" optional>
  How many more tries after the time or the sun event, at least 1. Only with `at` or `sun`. See [Trying again](#trying-again).
</Property>

---

<Property name="retry.every" type="time period" optional>
  The interval between tries, at least a minute, in whole seconds: the first try is `every` after the occurrence, the second `2 × every`, and so on. `times × every` can't go over 12 hours.
</Property>

### What it does

<Property name="then" type="program key" optional>
  A key of **this device's** [`programs`](/concepts/programs): the reaction starts it when it fires, unless it's already running. Without `then`, the reaction fires and does nothing: its trace still shows when and why. Another device's program, a script's entity ID or a list is a configuration error: `reactions: morning: clean is not a program of this device`.
</Property>

---

<Property name="message" type="string" optional>
  What to tell when the reaction fires: its device's name is the title. It can't be empty, and it's shown as you wrote it, not as a template. See [Notifications](/concepts/notifications#a-reactions-message).
</Property>

---

<Property name="notify" type="notify action or list" optional>
  Where this message goes, such as `notify.mobile_app_phone`, instead of `config.notify`. Only with `message`: `a reaction's notify goes with message`. A message with neither is a configuration error.
</Property>

With `then` and `message`, the program starts first, then the message is told.

---

<Property name="statistics.triggered" type="list of periods" optional>
  For each period, a sensor with the reaction's triggers in the current period. It sits inside the reaction, next to `then`. See [Statistics](/concepts/statistics) for the periods and how they reset, and [below](#statistics) for this reaction's own sensor.
</Property>

## Starting a program

A reaction with `then` starts its program's script, but only if it isn't running:

```yaml title="pururu/automations/reactions.yaml"
- id: pururu_laundry_lights_reaction_washer_done
  alias: Luzes da lavanderia Lavadora terminou
  triggers: [...]
  actions:
    - if:
        - condition: state
          entity_id: script.pururu_laundry_lights_program_blink
          state: "off"
      then:
        - action: script.turn_on
          target: {entity_id: script.pururu_laundry_lights_program_blink}
```

| When | What happens |
|---|---|
| The reaction fires, the program isn't running | The program starts, and the automation's run ends at once |
| The reaction fires while the program runs | Nothing: the trace shows the `if` not taken. The reaction still counts as triggered |
| The program was started elsewhere (the UI, a voice assistant, another reaction) | The same script: the `if` sees it running |
| An entity the program acts on isn't created, or its script's ID is taken | Neither the program nor the reaction is generated, and the log says why |
| An entity the program acts on is disabled | Both wait, and both come back as you left them once it's enabled again |
| You disabled the program's script | The reaction still fires, and the `if` isn't taken |
| You renamed the program's script | Followed: pururu reloads and rewrites the automation with its new ID |

A reaction always runs its **own** device's program, even when it listens to another device (`device: laundry_washer`). Programs run one at a time for now: a program already running isn't started again, nor queued.

## Trying again

A reaction on a time or on the sun fires once a day. If it didn't run then (Home Assistant was restarting, the automation was off, its program was already running), `retry` tries again:

```yaml title="configuration.yaml"
reactions:
  afternoon:
    name: Tarde
    at: "13:00"
    then: water
    retry: {times: 3, every: {hours: 1}}
```

The automation triggers at 13:00, and again at 14:00, 15:00 and 16:00. A try runs only if **nothing ran since 13:00**:

- **With `then`**, running means the program started: from this reaction, the UI, a voice assistant, anything.
- **Without `then`**, it means the automation fired, including a run by hand.

```yaml title="pururu/automations/reactions.yaml"
- id: pururu_garden_reaction_afternoon
  alias: Jardim Tarde
  triggers:
    - {trigger: time, at: "13:00:00"}
    - {trigger: time, at: "14:00:00", id: retry_1, variables: {since: 3660}}
    - {trigger: time, at: "15:00:00", id: retry_2, variables: {since: 7260}}
    - {trigger: time, at: "16:00:00", id: retry_3, variables: {since: 10860}}
  conditions:
    - condition: template
      value_template: "{{ since is not defined or as_timestamp(state_attr('script.pururu_garden_program_water', 'last_triggered'), 0) < now().timestamp() - since }}"
  actions: [...]
```

`since` is how far back a try looks, in seconds: the time since the occurrence, plus a minute.

| When | What happens |
|---|---|
| It ran at 13:00 | Every try is skipped: its trace shows the condition failing |
| Home Assistant was down at 13:00, back at 13:30 | 14:00 runs; 15:00 and 16:00 are skipped |
| The automation was off at 13:00, turned on at 14:30 | 15:00 runs; 16:00 is skipped |
| With `then`, the program was already running at 13:00 | 14:00 starts it if it has ended by then, or 15:00 tries |
| With `then`, you started the program by hand at 13:20 | Every try is skipped |
| Every try missed | Nothing more until tomorrow |

- **A restart** doesn't lose it: Home Assistant keeps `last_triggered` of automations and scripts. It saves them every 15 minutes and when it stops cleanly, though: if it stopped abruptly (a crash, a power cut) less than 15 minutes after a run, that run can be forgotten, and a try runs it again.
- **A minute of margin:** a try looks back to a minute before the occurrence, so that a try firing a few seconds late still sees the occurrence's own run. A run in that minute (the program started by hand at 12:59:30) counts as the occurrence's, and the tries are skipped: running twice is the worse mistake.
- **A new reaction** has never run: added at 20:30 with `at: "19:00"` and hourly tries, it runs at the 21:00 try, the same day. So does one whose program has never run.
- **Past midnight** is fine: `at: "23:00"` with three tries every hour tries at 00:00, 01:00 and 02:00.
- **The sun:** a try is the same event with its offset moved: sunset, then sunset + 1 h, and so on.
- **Daylight saving:** a try at a time the clock skips doesn't run that day. Going back an hour, Home Assistant fires a repeated time twice, the occurrence's as any automation's, and a try may run once more.
- **A message is told once per occurrence:** with `then` and `message`, a try that starts a program that was busy at the occurrence doesn't tell the message again. The occurrence told it. A try tells it only when the occurrence didn't run, as when Home Assistant was down.
- **Only a time or the sun:** a reaction on an entity is an event. Home Assistant down when it happens never sees it, and a later try would miss it too. `retry` there is a configuration error: `a reaction's retry goes with at or sun`.

## When a reaction fires

The automation follows Home Assistant's own triggers, so it behaves exactly like an automation you'd write yourself:

- **`to` without `from`** doesn't fire when the entity comes back from `unavailable` or `unknown`. A plug reconnecting (`unavailable → off`) is no "turned off". pururu adds `not_from: [unavailable, unknown]` for you.
- **A change passing through `unavailable`** (`on → unavailable → off`) isn't seen as `on → off`. That's Home Assistant's rule for `from`.
- **`above`/`below`** fires when the number crosses into the range, not while it stays there.
- **A pending `for`** is lost on a restart.

## Statistics

Every reaction counts its triggers, with no setting: `sensor.pururu_<key>_reaction_<reaction>_triggered_total`, named **Luzes da lavanderia Lavadora terminou triggers**. It survives restarts and is `total_increasing`. With `statistics.triggered`, one [statistics](/concepts/statistics) sensor per period: `…_triggered_month`.

- **Every trigger counts**, including one whose program was already running and so didn't start.
- **A try skipped** because the reaction already ran isn't a trigger: its condition failed. A try that runs counts.
- **The automation turned off** in the UI doesn't fire, so it counts nothing.
- **Renaming the automation** in the UI is followed: pururu reloads and counts under its new ID.
- **An automation ID someone else holds**: the reaction isn't generated, and it counts nothing. It never counts an automation pururu doesn't manage.
- **A reaction can't watch its own counter** (`when: reaction_morning_triggered_total` in `morning`): `reactions: morning: reaction_morning_triggered_total is its own statistic`. It can watch another reaction's, or a program's.

## The automation

| | |
|---|---|
| Entity ID | `automation.pururu_<device key>_reaction_<reaction key>` |
| Name | `<device name> <reaction name>` |
| ID | `pururu_<device key>_reaction_<reaction key>`: its traces are under this ID |
| Actions | starts the program named by `then` with `script.turn_on`, unless it's running; none without `then` |

- **Renaming** the automation's entity in the UI is kept.
- **An ID already taken:** if another automation already has `automation.pururu_…`, or one of your own automations has the same `id`, pururu leaves it alone and logs it. It never suffixes one with `_2`, and never takes over an automation it didn't write.
- **Two reactions with one ID:** device `lights` with the reaction `b_reaction_c` and device `lights_reaction_b` with the reaction `c` would both be `automation.pururu_lights_reaction_b_reaction_c`. That's a configuration error: rename a device key or a reaction key.
- **A reload that didn't take:** if reloading automations fails, or the include was missing, pururu reloads them again at its next reload, even when the file hasn't changed. An automation you dropped from the YAML that Home Assistant still runs keeps its ID until a reload drops it.
- **A pururu entity renamed in the UI:** `when` follows it, because pururu writes the entity's current ID into the file at every reload.
- **A pururu entity that isn't created** (its ID is taken, or the device's settings don't create it, as `appliance_runtime_month` without `statistics`): its reactions aren't generated, and the log says why.
- **A reaction removed from the YAML:** its automation leaves the file, and its entity leaves Home Assistant.
- **Removing pururu:** the file becomes an empty list, so its automations go. The line can stay until you remove it. If the file can't be written, its automations keep running with their IDs: delete the file by hand.
