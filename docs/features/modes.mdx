---
title: modes
description: The kinds of an appliance's cycles, such as frosting or warming, each from its own band of a sensor's value, with everything a cycle records, per mode.
---

`modes` tells what **kind** of cycle an appliance runs. A washer goes through [phases](/features/phases) in sequence within one cycle. A water purifier doesn't: it dispenses water, cools, or heats, one at a time, each at its own power. Each of those is a kind of cycle, a **mode**. Everything [`appliance`](/features/appliance) records about its cycles (last start, end, duration and energy, counts, runtime, per-period statistics) `modes` records per mode.

```yaml
pururu:
  devices:
    water_station:
      name: Purificador
      appliance:
        power: sensor.station_plug_power
        energy: sensor.station_plug_energy
        running_program: {above: 2.9, on_delay: {seconds: 1}, off_delay: {minutes: 1}}
      modes:
        cycle_from: appliance
        sensor: sensor.station_plug_power
        energy: sensor.station_plug_energy
        modes:
          bebendo: {name: Bebendo, above: 2.9, below: 4, on_delay: {seconds: 1}, off_delay: {minutes: 1}}
          resfriar: {name: Resfriar, above: 4, below: 150, on_delay: {seconds: 10}, off_delay: {minutes: 3}}
          quente: {name: Água quente, above: 150, below: 400, on_delay: {seconds: 30}, off_delay: {seconds: 30}}
        statistics:
          runtime: [today, month]
          cycles: [today, month]
          energy: [today, month]
```

These numbers come from a real purifier: sips at 3–3.5 W, a chilling cycle that peaks for two seconds and then runs a 3–28 W tail for up to half an hour, and warming at about 250 W.

## Settings

<Property name="cycle_from" type="feature" required>
  The feature of **this device** whose cycle the modes run inside. Today that's `appliance`. See [Features that build on each other](/concepts/devices-and-features#features-that-build-on-each-other).
</Property>

---

<Property name="sensor" type="entity ID" required>
  The sensor whose value picks the mode, usually the plug's power, as `appliance`'s `power`.
</Property>

---

<Property name="energy" type="entity ID" optional>
  The plug's **lifetime** energy counter, as `appliance`'s `energy`. Without it, the modes have no energy entities.
</Property>

---

<Property name="modes" type="ordered map of name → mode" required>
  At least one mode. Its key is any slug you like (`resfriar`, `agua_quente`…), except `idle`, the state with no mode. Each mode has:

  - `name`: required, how the mode's entities are named (`Resfriar`, `Água quente`).
  - `above`: the value must be strictly above this.
  - `below`: the value must be strictly below this.
  - `on_delay`: how long the value must stay in the band before the mode starts. A [time period](/features/appliance#settings), such as `{seconds: 10}`.
  - `off_delay`: how long the value must stay out of the band before the mode's cycle ends.

  A mode needs `above`, `below` or both, and `above` must be lower than `below`. Two modes' bands can't overlap: a reading belongs to one mode at most. Bands that only touch, such as `below: 4` and `above: 4`, are fine.
</Property>

---

<Property name="statistics.runtime" type="list of periods" optional>
  For each period, a sensor per mode with the hours in that mode in the current period. It sits in the `modes` block, once, and applies to every mode. See [Statistics](/concepts/statistics) for the periods and how they reset.
</Property>

---

<Property name="statistics.cycles" type="list of periods" optional>
  For each period, a sensor per mode with the cycles of that mode finished in the current period.
</Property>

---

<Property name="statistics.energy" type="list of periods" optional>
  For each period, a sensor per mode with the kWh that mode used in the current period. It needs `energy`.
</Property>

## When a mode cycle starts and ends

- A mode is **armed** once the value has stayed in its band for its `on_delay`. It stays armed until a reading leaves its band.
- An armed mode **starts** when the appliance's cycle is on (`appliance`'s `running`) and no other mode runs. If the appliance isn't running yet, the mode starts the moment it does, so its cycle isn't late for having waited.
- A running mode **ends** after the value has stayed out of its band for its `off_delay`, or at once when the appliance's cycle ends. A reading back in the band during `off_delay` cancels the end. If `sensor` isn't the appliance's plug and its value is still in the band when the appliance stops, the mode starts again as soon as the appliance runs again.
- As in `appliance`, `off_delay` only confirms the end: a mode cycle's `last_cycle_end` is when the value left its band, or when the appliance's cycle ended if that's earlier, and its duration and runtime leave `off_delay` out.
- **One mode at a time.** A mode armed while another runs **waits**. When the running one ends, the armed one starts, and `current` goes straight from one to the other, never through `idle`. Its cycle starts when it was armed, or when the running one's cycle ended if that's later. A short dip into another band doesn't split a cycle: the purifier's chilling tail drops to about 3 W, a sip's band, for a few seconds, and `resfriar`'s 3-minute `off_delay` carries it through.
- A reading **without a value** (`unknown`, `unavailable`, not a number) cancels every pending start and end. The running mode stays, and the next reading starts counting again, as in `appliance`. A running mode's end keeps the moment its value left its band.
- While the appliance's `running` is `unknown` or `unavailable`, no mode starts. The running one can still end by its `off_delay`.
- A **restart or reload** in the middle of a mode's cycle doesn't lose it: the mode, its start, its energy at the start and, during `off_delay`, when its value left its band are restored, and the cycle is counted once when it ends. If the appliance is already stopped after a restart, the restored mode ends once Home Assistant has started.

The **cycles of any mode** are `appliance`'s: its `cycles_total` counts appliance cycles, which may hold several mode cycles (warming, then frosting, the power never dropping).

## Entities

`<key>` is the device's key and `<mode>` a mode's key.

| Entity | What it is |
|---|---|
| `sensor.pururu_<key>_mode_current` | The running mode, or `idle`. Device class `enum`. While a mode runs, its attribute `cycle_start` is its cycle's start, and `cycle_end`, while its `off_delay` runs, is when the value left its band. |
| `sensor.pururu_<key>_mode_last` | The mode of the last mode cycle that ended. `enum`, kept across restarts, `unknown` until the first. |

Per mode, named after the mode's `name` ("Resfriar cycles" in English, "Ciclos de Resfriar" in Portuguese):

| Entity | Unit | What it is |
|---|---|---|
| `sensor.pururu_<key>_mode_<mode>_last_cycle_start` | timestamp | When this mode's last cycle started |
| `sensor.pururu_<key>_mode_<mode>_last_cycle_end` | timestamp | When it ended. **Written last**: trigger on it. |
| `sensor.pururu_<key>_mode_<mode>_last_cycle_duration` | min | How long it took |
| `sensor.pururu_<key>_mode_<mode>_last_cycle_energy` | kWh | Energy it used. *With `energy`.* |
| `sensor.pururu_<key>_mode_<mode>_cycles_total` | cycles | This mode's cycles, all time |
| `sensor.pururu_<key>_mode_<mode>_runtime_total` | h | Hours in this mode, all time, brought up to date every minute |
| `sensor.pururu_<key>_mode_<mode>_energy_total` | kWh | Energy this mode's cycles used, all time, added exactly (a sip's fraction of a Wh counts, though `last_cycle_energy` shows 0.0). A cycle whose energy is unknown adds nothing. *With `energy`.* |
| `sensor.pururu_<key>_mode_<mode>_<counter>_<period>` | | `runtime`, `cycles` or `energy` this period, one per entry of `statistics` |

- The `last_cycle_*` sensors behave as [`appliance`'s](/features/appliance#last-cycle): they change only when a cycle of their mode ends and keep their values across restarts. `last_cycle_end` is written after the others and after `mode_last`, so an automation triggered on it reads a complete cycle.
- The totals are `total_increasing`, so Home Assistant keeps long-term statistics for them. The per-period sensors are [statistics](/concepts/statistics), one set per mode.

### State names

`current` and `last` show a mode's key. These keys are translated in the UI (English and Portuguese):

| Name | English | Portuguese |
|---|---|---|
| `idle` | Idle | Parado |
| `rinsing` | Rinsing | Enxaguando |
| `drying` | Drying | Secando |

Any other key, such as `resfriar` or `agua_quente`, is shown as written.

## Needs

`modes` needs a **cycle**. If the cycle's entity (`appliance`'s `running`) can't be created, for example because its ID is taken, no entity of `modes` is created either. If you rename `running` in the UI, `modes` follows the new ID.
