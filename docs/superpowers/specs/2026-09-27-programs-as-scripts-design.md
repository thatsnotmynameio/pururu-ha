# Programs as scripts — design

Version: 0.1.12. Builds on reactions (0.1.10), whose generated file this generalises, and replaces how programs (0.1.8) run.

## Goal

A program is a sequence of actions on its device's own entities. Today pururu runs it itself: a `button` holds HA's `Script` helper in memory. HA runs scripts better than pururu can, and it has the UI for them: traces, a state that is `on` while it runs, `script.turn_off` to stop it, and the list of scripts. So pururu writes each program as a real **Home Assistant script** in a generated file, as it already writes reactions as automations, and stays what it's meant to be: a simpler interface over what HA already does.

The configuration doesn't change:

```yaml
pururu:
  devices:
    pool:
      name: Piscina
      switches:
        pump: {entity: switch.pool_pump, name: Bomba}
      programs:
        clean:
          name: Limpar
          sequence:
            - turn_on: switch_pump
            - delay: {hours: 2}
            - turn_off: switch_pump
# → script.pururu_pool_program_clean   "Piscina Limpar", in pururu/scripts/programs.yaml
```

```yaml
# configuration.yaml, once, next to the automations' line
script pururu: !include_dir_merge_named pururu/scripts
```

## Decisions

| Question | Decision |
|---|---|
| What a program becomes | A script, **replacing** the button. `button.pururu_<device>_program_<key>` is gone; `script.pururu_<device>_program_<key>` takes its place, started with `script.turn_on`. Rejected: a script plus a button calling it (two entities per program, and the button stays pururu code to keep). This breaks anything pressing the button; the release notes say so. |
| Its steps | pururu's own closed vocabulary, unchanged: `turn_on`, `turn_off`, `toggle` on an entity key of the device, and `delay`. Only where the translation goes changes: into the file instead of an in-memory `Script`. Rejected: a `native:` escape hatch (it breaks "only its own device", and it is validated only when HA loads the file); HA's syntax in `sequence:` (loses the simpler interface, and entity keys). |
| How the code is shaped | The generated-file machinery leaves `reactions.py` for a new `generated.py`, parametrised by a `Kind` per HA domain; `reactions.py` and `programs.py` keep only their schema and translation. Rejected: a copy of the machinery adapted in `programs.py` (quicker now, but two copies of code whose edge cases each took work to get right, and every later fix twice); one file with automations and scripts (HA reads each domain from its own include). |
| Is `programs` a `Feature` | No longer: it creates no pururu entity, so it's a device key in its own module, as `reactions`. It doesn't count as a feature: a device still needs one, and a program acts only on a switch or a light of its device, so it always has one. |
| Device and area | HA registers a YAML script with `device_id=None` every time it loads it, so the script can't stay in the device. Its `area_id` is a registry setting HA doesn't touch on load: pururu puts the script in its device's area. The dashboard, built by pururu, still shows it under its device. |
| A target disabled in the UI | The program isn't generated while any target is disabled, and the log says why, as for a target not created. HA reloads the entry when an entity of it is disabled or enabled, so it comes back once every target is enabled. Rejected: generating it anyway, the disabled step doing nothing (a program that looks usable and does part of its job misleads, as programs' spec already held). The cost: an automation calling it fails meanwhile. |

## The generated script

One entry per program, in the order of `devices:` then `programs:`, in `pururu/scripts/programs.yaml`:

```yaml
# Generated by pururu from its configuration. Don't edit: it is rewritten on every reload.
pururu_pool_program_clean:
  alias: Piscina Limpar
  description: "pururu: pool, clean"
  mode: single
  sequence:
    - action: switch.turn_on
      target: {entity_id: switch.pururu_pool_switch_pump}
    - delay: "02:00:00"
    - action: switch.turn_off
      target: {entity_id: switch.pururu_pool_switch_pump}
```

- The key is the script's object ID and unique ID (HA sets `entity_id = script.<key>`): `pururu_<device key>_program_<program key>`, the pururu pattern.
- `alias` is `<device name> <program name>`.
- The steps are today's `_translated`, validated with `cv.SCRIPT_SCHEMA`, on the targets' **current** entity IDs. The delay is written as `_period` writes reactions' durations (`HH:MM:SS`, and the fraction of a second if any).
- `mode: single`: a start while it runs is ignored, and HA logs `Already running`.

## Behaviour

| Situation | Before (button) | Now (script) |
|---|---|---|
| Start it | `button.press`, returns at once | `script.turn_on`, returns at once |
| Started while running | ignored, `Already running` in the log | the same (`mode: single`) |
| A step fails | it stops, the log says why | the same, and HA's trace shows the step |
| See what runs, stop it | not there | state `on` while it runs, `script.turn_off` |
| pururu reloads | a running program stops | only a program whose own script changed stops (HA's `script.reload` keeps a script whose config is unchanged); the file unchanged means no reload at all |
| HA restarts | a running program is lost | the same, as any HA script |
| A target renamed in the UI | followed | followed: the entry reloads and the file is rewritten with the new ID |
| The script renamed in the UI | — | kept, as the reactions' automations |
| The script disabled by the user | — | not missing: no Repairs issue |
| A target not created | the program isn't created, logged | not generated, logged: `script.pururu_pool_program_clean follows switch.pururu_pool_switch_pump, which is not created; not generating it` |
| A target disabled | the button is `unavailable` | not generated, logged: `script.pururu_pool_program_clean acts on switch.pururu_pool_switch_pump, which is disabled; not generating it` |
| The include missing | — | a Repairs issue, as the automations' |

After an upgrade the old buttons are stale entities of the entry, removed by `_remove_stale` at the first setup.

## Code

### `generated.py` (new)

The machinery now in `reactions.py`, for any HA domain whose items pururu generates. A frozen dataclass `Kind`:

- `domain`: `automation` or `script` (also the platform of its registry entries);
- `folder`, `file`: `pururu/automations` and `pururu/automations/reactions.yaml`; `pururu/scripts` and `pururu/scripts/programs.yaml`;
- `include`: `automation pururu: !include_dir_merge_list pururu/automations`, `script pururu: !include_dir_merge_named pururu/scripts`;
- `issue`: the Repairs issue key and translation key (`automations_not_included`, `scripts_not_included`);
- `data_key`: where the entry keeps the IDs it tracks (`automations`, as now; `scripts`, new);
- how the file is dumped: a list for automations, a mapping `{id: config}` for scripts.

It keeps, for both domains, what `reactions.py` does now: pre-register each entity ID (`async_get_or_create(domain, domain, id, suggested_object_id=id)`); refuse an ID someone else holds (`_free`, logged, the item not generated); write the file only when its bytes change; after HA has started, in an entry task, reload when the file changed or HA doesn't run it as written (retried at the next reload); drop the registry entry of a removed item once HA no longer runs it; raise the Repairs issue while an item isn't loaded; on entry removal, write an empty file (`[]` or `{}`) and drop what HA no longer runs.

Three changes so it serves both:

- **Running**: today an automation runs if a non-restored state carries its `id` attribute, which scripts don't have. It becomes: the registry maps the unique ID to its entity ID, and that entity has a state which isn't the restored placeholder. For automations it's the same result, since they're pre-registered.
- **Checked again**: today the Repairs issue is checked again on `automation_reloaded`; HA fires no such event for scripts. It becomes: whenever the state of a tracked item changes (`async_track_state_change_event` on their entity IDs). HA loading an item replaces its restored placeholder with a real state, and unloading one removes it, so both domains are covered, a user's own `automation.reload` or `script.reload` included.
- **Area**: each item may carry an area; at pre-registration its registry entry gets that `area_id`, or none. Programs pass their device's `area`; reactions pass none (their automations aren't placed, as today).

### `reactions.py`

Keeps the schema, the checks, `automation_id`, `triggers`, `automation`, and its `Kind`. `async_sync` and `async_remove` go to `generated.py`.

### `programs.py` (moved from `features/`)

Next to `reactions.py`. Keeps `SCHEMA`, `_step`, `_targets`, `_translated`, and gains `script_id(device_key, program_key)`, `script(...)` (the entry above) and its `Kind`. `Program`, `build` and `PROGRAMS` go.

### `__init__.py`

- `programs` leaves `FEATURES` and becomes `vol.Optional(CONF_PROGRAMS): programs.SCHEMA` in the device schema, as `reactions`.
- `_programs_on_this_device(device)`, next to `_reactions_on_this_device`: each entity key a step acts on is an entity key of a feature of the device that takes the action (`Feature.actions`). The messages stay: `programs: <key> is not an entity key of another feature of this device`, `programs: <key> does not take <action>`.
- `_scripts(hass, devices, created)`, as `_automations`: a program is generated if every target is created and none is disabled, on the targets' current entity IDs; otherwise logged.
- `async_setup_entry` generates the automations, then the scripts, each through `generated.async_sync(hass, entry, kind, items)`; `async_remove_entry` removes both.

### Removed

- `Feature.acts`, only programs used it (`refers` stays for alerts; `actions` stays for switches and lights).
- `button.py`, `Platform.BUTTON` in `PLATFORMS`, the `button` entries of `translations/*.json` and `icons.json`, and `button.py`'s suppressions in `sonar-project.properties`.

### Translations

`issues.scripts_not_included` in `en.json` and `pt-BR.json`, as `automations_not_included`, naming the file and the include line.

## Testing

- `tests/test_generated.py` (new): the edge cases in today's reactions tests, parametrised over both kinds: write only on changed bytes; an ID held by an automation or script of the user's, by another integration, by an entity without a unique ID; the Repairs issue with and without the include, cleared once the user adds it and reloads the domain; the reload retried; a removed item HA still runs keeps its entry until a reload drops it; a restored placeholder isn't running; a user-disabled item isn't missing; entry removal leaves an empty, valid file.
- `tests/test_reactions.py` keeps what's reactions' own: schema, triggers, references across devices, the generated automation.
- `tests/test_programs.py` rewritten, with HA loading the generated file for real (the include in the test's configuration): `script.turn_on` turns the pump on, and `tick` past two hours turns it off; `script.turn_off` stops it halfway; a pururu reload with the program unchanged doesn't stop it; a target renamed in the UI is followed; a disabled target drops the script, enabling it brings it back; the script is in its device's area; the old button is removed; every validation error of today keeps its message.
- `tests/test_features.py` needs no change: `programs` leaves `FEATURES`.

## Docs

- `docs/features/programs.mdx` moves to `docs/concepts/programs.mdx`, next to reactions (it's no longer a feature), and `docs.json` follows. Rewritten for the script: the include line, the behaviour table, and a note that the button became a script (`button.press` → `script.turn_on`).
- Getting started: the second include line.
- `docs/concepts/entity-ids.mdx`: `script.pururu_<device>_program_<key>` instead of the `button`.
- Troubleshooting: the new Repairs issue and the two log messages.
- `docs/index.mdx`: a program is a script something starts, no longer a button pressed.
- `CLAUDE.md`: step 6 of the architecture describes `generated.py` and both domains; `acts`, `programs` under Features, and `button.py` go.

## Release

0.1.12 in `manifest.json`. The PR body and release notes lead with the breaking change: programs are scripts, `button.pururu_*_program_*` is removed, use `script.turn_on`, and add `script pururu: !include_dir_merge_named pururu/scripts` to `configuration.yaml`.

## Risks

- **The script can't be in its device.** Only in its area; anything grouping by device in HA's UI won't list it. The dashboard does.
- **A disabled target removes the script**, and an automation calling it fails until the target is enabled again.
- **Refactoring reactions' machinery** touches released, tested code; the parametrised tests must pass for automations before scripts are added.
