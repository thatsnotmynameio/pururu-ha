# Switches Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A pururu device can hold several switches, keyed and named in YAML, each one standing for a real `switch.*` entity: it shows its state and passes commands on to it.

**Architecture:** `Feature` gains `configured: Platform | None`: a configured feature's entity keys are the keys of its YAML block, named by the block's `name` instead of the translations. `_device` refuses two alike entity keys in one device. The `switches` feature builds one `Switch` per key, a `PururuEntity` on top of HA's `SwitchGroup` with the real switch as its only member (as `Mirror` is a `SensorGroup`), served by a new `switch.py` platform.

**Tech Stack:** Home Assistant 2026.9.3 custom integration, voluptuous, `homeassistant.components.group.switch.SwitchGroup`, pytest with `pytest-homeassistant-custom-component`, docs.page MDX.

**Spec:** `docs/superpowers/specs/2026-09-27-switches-design.md`

## Global Constraints

- Version: `custom_components/pururu/manifest.json` `version` becomes `0.1.4`; `iot_class` stays `calculated`.
- Only `switch.*` real entities; one feature per domain. `lights:` is a later PR (0.1.5), not this one.
- Every entity ID is `<platform>.pururu_<device key>_<entity key>`; unique ID is the part after the platform. Never suffix with `_2`.
- A switch's `name` is required and is its name in every language; entity keys from YAML have no translation key.
- Two entity keys alike in one device are a configuration error, message `<feature>: <entity key> is already an entity key of <other feature>`.
- `entity:` must not be a pururu switch (`switch.pururu_…`).
- Run everything from the worktree root with `uv`. Single test file: `uv run pytest tests/<file>.py -n 0 -q` (never `-p no:xdist`). Never leave the shell's cwd inside `.venv/.../homeassistant/helpers/`.
- ruff and mypy (strict) run on `custom_components/pururu` only, through `tests/test_code.py`; tests aren't linted. Match the surrounding code: short docstrings saying what and why, comments only where the code can't speak.
- Docs: `{` and `<` outside code are JSX in MDX; keep them in backticks. Check with `npx --yes @docs.page/cli check`.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

A switch key equal to an `appliance` entity key that its current settings don't create (`runtime_month` with no `statistics`) — a person expects it refused all the same, so turning statistics on later never breaks the switch. 5. The real switch removed after setup, then back — a person expects the pururu switch unavailable, then following it again. Test in Task 2 (`test_follows_the_real_switch_going_and_coming_back`).

```python
"""Real switches inside the device: each shows its switch's state and passes commands on.

A switch is HA's switch group with the real switch as its only member, as a
mirror is a sensor group of one. Only switch.* is taken: a light, fan or cover
gets a feature of its own, on its own group, so it keeps what its domain offers.
"""

from collections.abc import Mapping
from typing import Any

import voluptuous as vol

from homeassistant.components.group.switch import SwitchGroup
from homeassistant.const import Platform
from homeassistant.core import HomeAssistant
from homeassistant.helpers import config_validation as cv

from ..const import ENTITY_PREFIX
from ..entity import PururuEntity
from ..feature import Device, Feature


def _not_pururu(entity_id: str) -> str:
    """A pururu switch standing for itself would call itself forever."""
    if entity_id.startswith(f"{Platform.SWITCH}.{ENTITY_PREFIX}_"):
        raise vol.Invalid(f"{entity_id} is a pururu switch: name the real one")
    return entity_id


SWITCH = vol.Schema(
    {
        vol.Required("entity"): vol.All(
            cv.entity_domain(Platform.SWITCH), _not_pururu
        ),
        vol.Required("name"): cv.string,
    }
)
# A schema of its own: ALLOW_EXTRA would let a key that isn't a slug through
SCHEMA = vol.All(vol.Schema({cv.slug: SWITCH}), vol.Length(min=1))


class Switch(PururuEntity, SwitchGroup):
    """The real switch's state; turning it on or off turns the real one."""

    def __init__(
        self, device: Device, entity_key: str, entity: str, name: str
    ) -> None:
        """Stand for `entity` as `entity_key` of `device`, named `name`."""
        SwitchGroup.__init__(self, None, name, [entity], None)
        self._identify(device, Platform.SWITCH, entity_key, name)


def build(
    hass: HomeAssistant,
    device: Device,
    config: dict[str, Any],
    inputs: Mapping[str, str],
) -> list[PururuEntity]:
    """A switch per key of the block."""
    return [
        Switch(device, entity_key, switch["entity"], switch["name"])
        for entity_key, switch in config.items()
    ]


SWITCHES = Feature(
    schema=SCHEMA,
    entity_keys={},
    build=build,
    example={"sprinkler": {"entity": "switch.dummy_sprinkler", "name": "Sprinkler"}},
    configured=Platform.SWITCH,
)
```

````mdx

`switches` puts real switches in a device, such as a greenhouse's sprinkler and heater on two smart relays. Each one becomes a switch of the device: it shows the real switch's state, and turning it on or off turns the real one.

```yaml
pururu:
  devices:
    greenhouse:
      name: Estufa
      area: estufa
      switches:
        sprinkler: {entity: switch.greenhouse_sprinkler, name: Irrigador}
        heater: {entity: switch.greenhouse_heater, name: Aquecedor}
```

This creates `switch.pururu_greenhouse_sprinkler`, shown as **Estufa Irrigador**, and `switch.pururu_greenhouse_heater`, shown as **Estufa Aquecedor**.

## Settings

`switches` is a map of **entity key → switch**, with at least one switch. The key is a slug, and it becomes the end of the entity ID: `sprinkler` → `switch.pururu_greenhouse_sprinkler`.

<Property name="entity" type="entity ID" required>
  The real switch. It must be a `switch.*` entity, and not one of pururu's own switches.
</Property>

---

<Property name="name" type="string" required>
  The name shown after the device's name. It's the same in every language: unlike other features' entities, a switch's name isn't translated.
</Property>

A switch's key can't be an entity key of another feature of the same device. With `appliance`, `power` or `running` is a configuration error, and so is `runtime_month` even when you don't count runtime per month, so turning a statistic on later never breaks a switch.

## Entity

| The real switch | `switch.pururu_<key>_<entity key>` |
|---|---|
| `on` or `off` | the same |
| `unknown` | `unknown` |
| `unavailable`, or it doesn't exist | `unavailable` |

- **Turning it on or off** turns the real switch on or off. The logbook names whoever did it: you, an automation or a voice assistant.
- If the real switch reports an **assumed state**, the pururu switch does too, and the UI shows on and off buttons instead of a toggle.
- Its attribute **`entity_id`** names the real switch, and its details show it.
- It keeps no state of its own. After a restart, it shows the real switch again.

## Only `switch.*`, for now

A light, a fan or a cover exposed as a switch would only turn on and off: no brightness or colour, no speed, no position, and a voice assistant wouldn't treat it as a light. So each kind of entity gets a feature of its own, whose entity keeps everything its kind offers. `lights` comes next.

## Good to know

- **Two entities for one switch.** The real switch stays in its own device. If that device is in the same area, the area shows the switch twice, and an action on the whole area reaches both. Switching both is harmless, but a count of switches that are on counts two. `appliance`'s `power` already works this way.
- **Renaming the real switch.** Update `entity:` in the YAML and reload. Until then, the pururu switch is `unavailable`.
- **Renaming the pururu switch** in the UI works as for any entity. See [Renaming an entity ID](/concepts/entity-ids#renaming-an-entity-id).
- **The same real switch in two devices** is fine: both follow it.
````
