# Lights Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A pururu device can hold several lights, keyed and named in YAML. Each one stands for a real `light.*` or `switch.*` entity: it shows its state, offers what it offers, and passes commands on to it.

**Architecture:**
- A new module `features/standing.py` holds what `switches` and `lights` share, as functions: the `{key: {entity, name}}` schema over a set of domains, and `is_pururu` (a registry lookup). `switches.py` is refactored onto it with no change in behaviour.
- `features/lights.py` builds one entity per key, picking the class by the real entity's domain:
  - `Light`, a `PururuEntity` on HA's `LightGroup` with the real light as its only member;
  - `SwitchLight`, a `PururuEntity` on HA's `GroupEntity` + `LightEntity` that follows a real switch and is on/off only.
- A new `light.py` platform serves them.
- `_device` refuses a real entity in two configured features of one device.

**Tech Stack:**
- Home Assistant 2026.9.3 custom integration and voluptuous;
- `homeassistant.components.group.light.LightGroup` and `homeassistant.components.group.entity.GroupEntity`;
- pytest with `pytest-homeassistant-custom-component`;
- docs.page MDX, checked with pnpm.

**Spec:** `docs/superpowers/specs/2026-09-27-lights-design.md`

## Global Constraints

- **Version.** `custom_components/pururu/manifest.json` `version` becomes `0.1.6`. `dependencies` and `iot_class` (`calculated`) don't change.
- **The `lights` feature.** Its namespace is `light`, `configured=Platform.LIGHT` and `entity_keys={}`. Every light is `light.pururu_<device key>_light_<entity key>`, with no exception (a key `light` gives `…_light_light`). The unique ID is the part after the platform.
- **`entity:`.** It is singular: one entity ID, never a list. It must be `light.*` or `switch.*`, and not `<domain>.pururu_…`.
- **`name:`.** Required and not blank. It's the entity's name in every language, with no translation key.
- **A pururu entity renamed in the UI and used as `entity:`.** The light isn't created, and the log is `<entity> is a pururu <domain>: name the real one; not creating <light entity ID>` at ERROR.
- **One real entity per configured feature, in a device.** The error is `<feature>: <entity> is already in <other feature>`. The features are met in `FEATURES` order (alphabetical), so a switch in both `lights` and `switches` reads `switches: switch.x is already in lights`. Across devices it is allowed.
- **What a light offers.** It is read from the real entity at run time. Nothing about colour modes or features is hard-coded, except `ColorMode.ONOFF` for a `switch.*`.
- **Behaviour of `switches`.** It doesn't change: `tests/test_switches.py` passes unedited after Task 1.
- **Running things.** Run everything from the worktree root with `uv`. A single test file is `uv run pytest tests/<file>.py -n 0 -q` (never `-p no:xdist`). Never leave the shell's cwd inside `.venv/.../homeassistant/helpers/`. The full suite is `uv run pytest`: ruff, ruff format, mypy strict, hassfest and the quality scale run in `tests/test_code.py`.
- **Code style.** ruff and mypy run on `custom_components/pururu` only, and tests aren't linted. Match the surrounding code: short docstrings saying what and why, and comments only where the code can't speak.
- **Docs.** `{` and `<` outside code are JSX in MDX, so keep them in backticks. Check with `pnpm docs:check` (run `pnpm install` once first). Use pnpm, never npm.
- **Commits.** Every commit message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

```python
"""What the features standing for real entities share: their configuration, and knowing pururu's own.

`switches` and `lights` give each key of their block an entity standing for one
real entity. Their entities differ by domain, each on its HA group entity; what
they share is here, as functions, not a base class.
"""

from collections.abc import Callable
from typing import Any

import voluptuous as vol

from homeassistant.const import Platform
from homeassistant.core import HomeAssistant, split_entity_id
from homeassistant.helpers import config_validation as cv, entity_registry as er

from ..const import DOMAIN, ENTITY_PREFIX


def real_entity(*domains: Platform) -> Callable[[Any], str]:
    """One entity ID of one of `domains`, not one of pururu's own.

    An entity standing for itself would call itself forever, and one standing
    for another pururu entity would stand for what that one already stands for.
    """

    def validate(value: Any) -> str:
        entity_id: str = cv.entity_id(value)
        domain, object_id = split_entity_id(entity_id)
        if domain not in domains:
            raise vol.Invalid(f"{entity_id} is not a {' or '.join(domains)}")
        if object_id.startswith(f"{ENTITY_PREFIX}_"):
            raise vol.Invalid(f"{entity_id} is a pururu {domain}: name the real one")
        return entity_id

    return validate


def schema(*domains: Platform) -> Callable[[Any], Any]:
    """A block of entity key -> the real entity it stands for and its name; at least one."""
    item = vol.Schema(
        {
            vol.Required("entity"): real_entity(*domains),
            # A blank name would show the entity as its device's name alone
            vol.Required("name"): vol.All(cv.string, vol.Strip, vol.Length(min=1)),
        }
    )
    # A schema of its own: ALLOW_EXTRA would let a key that isn't a slug through
    return vol.All(vol.Schema({cv.slug: item}), vol.Length(min=1))


def is_pururu(hass: HomeAssistant, entity_id: str) -> bool:
    """Whether `entity_id` is pururu's: renamed in the UI, it no longer says so."""
    registered = er.async_get(hass).async_get(entity_id)
    return registered is not None and registered.platform == DOMAIN
```

"""Real switches inside the device: each shows its switch's state and passes commands on.

A switch is HA's switch group with the real switch as its only member, as a
mirror is a sensor group of one. Only switch.* is taken: a light, fan or cover
gets a feature of its own, on its own group, so it keeps what its domain offers.
"""

from collections.abc import Mapping
import logging
from typing import Any

from homeassistant.components.group.switch import SwitchGroup
from homeassistant.const import Platform
from homeassistant.core import HomeAssistant

from ..entity import PururuEntity
from ..feature import Device, Feature
from . import standing

_LOGGER = logging.getLogger(__name__)


class Switch(PururuEntity, SwitchGroup):
    """The real switch's state; turning it on or off turns the real one."""

    def __init__(self, device: Device, entity_key: str, entity: str, name: str) -> None:
        """Stand for `entity` as `entity_key` of `device`, named `name`."""
        SwitchGroup.__init__(self, None, name, [entity], None)
        self._identify(device, Platform.SWITCH, entity_key, name)


def build(
    hass: HomeAssistant,
    device: Device,
    config: dict[str, Any],
    inputs: Mapping[str, str],
) -> list[PururuEntity]:
    """A switch per key of the block; none standing for a pururu switch.

    The configuration refuses switch.pururu_…; a pururu switch renamed in the
    UI gets past that, and only the registry still knows it is ours.
    """
    switches: list[PururuEntity] = []
    for entity_key, switch in config.items():
        entity = switch["entity"]
        if standing.is_pururu(hass, entity):
            _LOGGER.error(
                "%s is a pururu switch: name the real one; not creating %s",
                entity,
                device.current_entity_id(hass, Platform.SWITCH, entity_key),
            )
            continue
        switches.append(Switch(device, entity_key, entity, switch["name"]))
    return switches


SWITCHES = Feature(
    schema=standing.schema(Platform.SWITCH),
    entity_keys={},
    build=build,
    example={"pump": {"entity": "switch.demo_pump", "name": "Pump"}},
    namespace="switch",
    configured=Platform.SWITCH,
)
```

## Settings

`lights` is a map of **entity key → light**, with at least one light. The key is a slug, and it ends the entity ID, after the namespace `light`: `teto` → `light.pururu_sala_light_teto`.

<Property name="entity" type="entity ID" required>
  The real light: a `light.*` entity, or a `switch.*` entity that drives a lamp, such as a relay. One entity, not a list. It can't be one of pururu's own lights or switches, even one you renamed in the UI. A renamed one is caught when pururu builds the device: that light isn't created, and the log says so.
</Property>

---

<Property name="name" type="string" required>
  The name shown after the device's name. It can't be empty. It's the same in every language: a light's name isn't translated.
</Property>

A light's key can be one another feature uses, such as `pump` in both `lights` and `switches`: each feature has its own [namespace](/concepts/entity-ids#the-pattern), so `light.pururu_sala_light_pump` and `switch.pururu_sala_switch_pump` are two entities.

## Entity

| The real light or switch | `light.pururu_<key>_light_<entity key>` |
|---|---|
| `on` or `off` | the same |
| `unknown` | `unknown` |
| `unavailable`, or it doesn't exist | `unavailable` |

- **What it offers** is what the real entity offers, read every time it changes:
  - **A `light.*`** passes on its colour modes, brightness, colours, colour temperature and its range, effects, and whether it supports transitions and flashing. A bulb that only turns on and off gives a light that only turns on and off. If the bulb gains colour, after a firmware update for example, the pururu light follows without a reload.
  - **A `switch.*`** only turns on and off, so its light does too. Asking it for a brightness or a colour turns the relay on and ignores the rest.
- **Turning it on or off** does the same to the real entity, with the brightness, colour, effect or transition you asked for. The logbook names whoever did it: you, an automation or a voice assistant.
- If the real entity reports an **assumed state**, the pururu light does too.
- Its attribute **`entity_id`** names the real entity, and its details show it.
- It keeps no state of its own. After a restart, it shows the real entity again.

## A relay is a switch or a light

A relay that drives a lamp goes in `lights`, so voice assistants and area actions treat it as a light. In one device, a real entity can be in `lights` or in `switches`, not both:

```
switches: switch.sonoff_abajur is already in lights
```

Two devices can each use it their own way: a light in `sala` and a switch in `varanda`.

## Good to know

- **Replacing the bulb or the relay.** Point `entity:` at the new one and reload. `light.pururu_sala_light_teto` keeps its ID, name and area, so automations and dashboards keep working.
- **Two entities for one light.** The real light stays in its own device. If that device is in the same area, the area shows the light twice, and "turn off the lights in Sala" reaches both. Turning both off is harmless, but a count of lights that are on counts two.
- **Renaming the real entity.** Update `entity:` in the YAML and reload. Until then, the pururu light is `unavailable`.
- **Renaming the pururu light** in the UI works as for any entity. See [Renaming an entity ID](/concepts/entity-ids#renaming-an-entity-id).
- **The same real light twice**, in one device or two, is fine: each pururu light follows it.
````
