Grounding Context

Codebase Context

  • Cada feature cria entidades <platform>.pururu_<device>_<namespace>_<chave>. Uma referência hoje é a chave "qualificada", o fim do entity ID depois da chave do device: appliance_running, switch_sprinkler. Não existe parser: cada schema valida a string (cv.slug, cv.entity_id) e o código monta um Ref(device, chave) que find procura no índice (core/resolve.py).
  • Na 0.2.1 (depois do PR C), uma referência é a chave qualificada no próprio device (when: appliance_running, turn_on: switch_sprinkler), device.chave para outro device (when: clothes_washer.appliance_running; o próprio device escrito por extenso vale igual), entity: para uma entidade do HA, e os grupos de luz são listas dessas referências (default: [greenhouse.light_lantern]).
  • O _ aparece dentro dos nomes e também entre os níveis, então a fronteira não se vê: appliance_cotton_phase_other_energy_month é appliance / programa detectado cotton / fase other / medidor energy_month.
  • Entidades reais do HA ficam em chaves próprias (power, energy, contact, entity). O pururu segue o rename das próprias entidades, mas não o das entidades do HA que ele lê.
  • Fronteiras (D5, "listen anywhere, act only on yourself"): o when de um alerta escrito à mão vigia só o próprio device; um passo de programa age só no próprio device; uma reação escuta o próprio device, outro device ou qualquer entidade do HA.
  • O PR C (#63, 0.2.1) implementou o D7 do spec docs/superpowers/specs/2026-09-29-yaml-contract-coherence-design.md: chave no mesmo device, device.chave em outro, entity: para o real. O spec rejeitou appliance.running (C6) porque "reads like an entity ID" e deixa de bater com o fim do ID.
  • O event_name dos eventos do barramento já é <device>.<chave> (clothes_washer.appliance_last_cycle_end).

Restrições do usuário

  • Tudo o que é do Home Assistant leva homeassistant., inclusive campos que só aceitam entidade real: power: homeassistant.sensor.washer_plug_power.
  • O when tem que ser ridiculamente fácil de escrever.
  • O esquema com self. em toda referência interna e ponto em todo nível (self.appliance.cotton.phase.current) foi recusado por ser pesado demais.
  • Um usuário só: sem compatibilidade, aliases ou migração.

External Context

Os frameworks convergem num padrão de três degraus: o nome nu é o escopo mais próximo, um qualificador alcança o vizinho, e um marcador explícito indica o dono de fora. Bazel usa :t, //pkg:t e @repo//pkg:t; Terraform deixa o recurso gerenciado sem prefixo e marca o externo com data.; no dbt, ref() é do projeto e source() é de fora, e um ref ambíguo é erro, não palpite. O HA põe o tipo do referente na chave (target: {entity_id, device_id, area_id}), e o ESPHome usa id: local nu e platform: homeassistant para importar uma entidade do HA. Um resolvedor que tenta vários escopos em cascata (o ndots do DNS do Kubernetes) surpreende e precisa de um jeito de desligar.

1. A referência é o caminho no YAML

Description

Decidido com o autor em 2026-10-01. Quem escreve o YAML chega à entidade pelo que escreveu, mais convenções; não precisa saber como a entidade gerada se chama. Esta decisão substitui a forma de referência da 0.2.1 (o D7 do spec de coerência, implementado no PR C) e derruba a recusa do C6. É uma nova mudança de quebra depois da 0.2.1: o YAML migra da forma da 0.2.1 para esta. As regras:

  1. Externo é sempre explícito. Tudo o que é do HA leva homeassistant., em qualquer campo, mesmo nos que só aceitam entidade do HA: power: homeassistant.sensor.washer_plug_power, contact:, o entity: de switches, luzes e botões, when: homeassistant.binary_sensor.porta_despensa, notify: homeassistant.notify.mobile_app_phone. O entity: das reações some: entra no when.
  2. Outro device é sempre explícito: device.clothes_washer.appliance.running_program. Dentro do próprio device se escreve direto (appliance.running_program); escrever device.clothes_washer.… dentro de clothes_washer é recusado, com o erro dizendo o que escrever. Assim, um device copiado com outra chave continua apontando para si mesmo. Hoje (0.2.1) o próprio device escrito por extenso vale igual (laundry_lights.light_teto é light_teto); isso muda.
  3. Campo que só aceita um tipo de coisa interna recebe só a chave, porque o nome do campo já diz o que é: area: despensa, floor: terreo, then: blink, program: ler (botão), lights: externas (alerta). lights: default nomeia o grupo default, que precisa estar declarado; o lights: true já saiu na 0.2.1.
  4. Campo que aceita coisas internas diferentes recebe o caminho completo no YAML, com pontos, começando na chave do bloco dentro do device: when: appliance.running_program, turn_on: switches.sprinkler, appliance.programs.detected.cotton.other.statistics.energy.month. Sempre completo, por enquanto, mesmo quando a referência está escrita dentro de appliance:.
  5. O que o pururu cria sem você escrever fica embaixo do nó onde nasce, e o nó de uma coisa é a própria coisa. Um switch, uma luz, um botão, um alerta, um programa ou uma fase é a própria entidade (switches.sprinkler, appliance.running_program é a lavadora ligada, appliance.programs.detected.cotton é o Algodão ligado). O resto entra com o nome que a documentação usa: appliance.running_program.last_cycle_end, appliance.running_program.phase_current, door.open, programs.executable.clean.cycles_total, reactions.washer_done.triggered_total.
  6. O event_name é a referência de fora: device.clothes_washer.appliance.running_program.last_cycle_end. O campo key do evento e as chaves de states são o caminho dentro do device (appliance.running_program.last_cycle_end); num template, {{ event.states['appliance.running_program'] }}.
  7. Grupos de luz dos alertas continuam em config: alerts: lights: groups, e cada membro é uma referência completa: default: [device.biblioteca.lights.teto].
  8. Cada entidade mostra a própria referência. Um atributo em cada entidade do pururu, fora do recorder, traz o caminho como se escreve no YAML: appliance.running_program.last_cycle_end dentro do device e device.clothes_washer.appliance.running_program.last_cycle_end de fora. É a ponte de quem está olhando uma entidade no HA até o que escrever, e sai junto com as regras acima (a parte da ideia 5 que entra agora).

A primeira palavra de um caminho diz de quem é: homeassistant, device ou uma chave de bloco do próprio device. Nenhuma chave de bloco se chama device ou homeassistant, então a leitura nunca é ambígua, e os pontos depois dela ficam livres para o caminho.

Axis
1. O when dentro do device
Basis
  • direct: hoje a referência é o fim do entity ID, então o usuário precisa conhecer a entidade gerada: docs/reference/troubleshooting.mdx:29 ensina "Write it as the entity ID ends after the device key, with its namespace (appliance_power, not power)".
  • direct: o entity ID tem palavras que o usuário nunca escreveu: "Its entities' keys begin with phase_other" (docs/concepts/programs.mdx:185), embora no YAML o other: fique direto sob o programa, sem nenhum phase.
  • direct: três campos já recebem só a chave porque o campo implica o tipo: then (device_keys/reactions.py:181), o program dos botões (features/buttons.py:90) e area (setup/schema.py:41).
  • direct: device_keys/reactions.py:131, "a reaction's device goes with when": dois campos formam uma referência só.
  • reasoned: toda chave é cv.slug, sem ponto, e a primeira palavra vem de um conjunto fechado (homeassistant, device, as chaves de bloco), então cada ponto é uma fronteira de nível. O _ não consegue isso: o docstring de setup/checks.py:121 cita o caso greenhouse mais greenhouse_switch.
  • external: labels do Bazel, referências do Terraform (data. para o que é de fora), ref e source do dbt; e o caminho pelo próprio documento, como em yq '.appliance.programs.detected.cotton'.
Rationale
Quem escreve o YAML chega à entidade pelo que tem na tela: o caminho é o próprio arquivo, e o externo e o vizinho sempre se anunciam. A chave do bloco no caminho tira a ambiguidade (switches.sprinkler e lights.sprinkler são coisas diferentes) e diz o que é cada coisa. Onde o campo só aceita uma coisa, a chave basta e o YAML fica curto. E as três raízes (bloco, device., homeassistant.) seguem o padrão em que os frameworks convergem.
Downsides
  • Os casos profundos ficam longos: (e) tem oito níveis.
  • A referência espelha a estrutura do YAML: se um bloco muda de lugar no schema, todas as referências a ele mudam. Com um usuário só e sem compatibilidade, isso é aceitável, mas pesa em cada mudança de schema.
  • A referência deixa de bater com o fim do entity ID (o segundo motivo do C6). O HA continua mostrando entity IDs em dashboards, no histórico, nas automações do usuário e no entity_id dos eventos; o atributo da regra 8 é a ponte do entity ID para o caminho.
  • O que é criado sem ser escrito depende de uma convenção por feature, que precisa estar documentada e ser fácil de achar.
  • Quem consome os eventos muda: event_name, key e as chaves de states mudam, e um template passa a usar colchetes (event.states['appliance.running_program']).
  • O pururu indexa inputs "by each reference as written (Ref.text)" (core/roles.py:94). O caminho precisa resolver para o alvo uma vez, ao ler, e virar uma só chave (ideia 5).
  • homeassistant já é domínio de serviço do HA (homeassistant.turn_on), e homeassistant.notify.mobile_app_phone pode ser lido como uma ação desse domínio.

2. homeassistant. como promessa verificada e seguida

Description

Com o prefixo obrigatório, o pururu sabe exatamente o que lê do HA sem conhecer cada campo. A ideia usa isso para três coisas:

  1. Um validador só para todo referente do HA (power, energy, contact, as entidades event, o when das reações), que guarda o caminho no YAML de cada um.
  2. Depois que o HA termina de subir, um issue em Repairs para cada referência que o HA não conhece, com os IDs parecidos do mesmo domínio. O issue some quando a entidade aparece.
  3. Quando o usuário renomeia na UI uma entidade do HA que o pururu lê, o listener reage como já faz com as entidades do pururu: um Repairs com o caminho no YAML e o ID novo para escrever.

Opcional: avisar quando o device_class não combina com o campo, como um power: que aponta para um sensor sem classe power.

Axis
3. Coisas do Home Assistant
Basis
  • direct: setup/listener.py:80-83: ours = registered.config_entry_id == entry_id e return "renamed" if ours or generated_item else None. Renomear sensor.washer_plug_power não dispara nada.
  • direct: features/appliance/__init__.py:43, vol.Required("power"): cv.entity_id: qualquer domínio, nenhuma checagem de existência.
  • direct: o único ir.async_create_issue do código é o de arquivo gerado não incluído (core/generated.py:306).
  • external: external: true do Docker Compose ("não é meu; é erro se faltar"); o "These IDs look similar" do ESPHome; o source() do dbt, que existe para linhagem e frescor do que é de fora.
Rationale
É a única falha de referência que hoje é silenciosa: renomear a tomada deixa a lavadora sem leitura, e nenhuma mensagem diz por quê. Com isso, o prefixo que o usuário exigiu deixa de ser só convenção de escrita: o pururu consegue verificar e seguir tudo o que o leva.
Downsides
  • O HA sobe as integrações em paralelo, então a checagem de existência só pode rodar depois do início, como aviso, nunca na validação do YAML.
  • O YAML continua sendo a verdade: o pururu avisa, não reescreve o arquivo.
  • O notify: também leva o prefixo (ideia 1, regra 1), mas é uma ação (notify.mobile_app_x), não uma entidade, e homeassistant.notify.x pode ser lido como um serviço do domínio homeassistant.
  • Ficou de fora recusar homeassistant.<x> quando uma feature do pururu já representa <x>: o usuário pode querer o estado real mesmo quando o espelho do pururu não foi criado.

3. Reagir ao acontecimento que o device publica

Description

Uma reação pode citar um acontecimento nomeado de uma feature em vez de uma entidade mais a transição. O dono da feature define a transição certa, e quem escuta só cita o nome. O acontecimento fica embaixo do nó que o faz nascer, como toda coisa criada pelo pururu: no próprio device, when: appliance.running_program.finished; em outro, when: device.clothes_washer.appliance.running_program.finished.

Hoje
washer_done:
  name: Lavadora terminou
  when: clothes_washer.appliance_running
  from: "on"
  to: "off"
  then: blink
Com a ideia
washer_done:
  name: Lavadora terminou
  when: device.clothes_washer.appliance.running_program.finished
  then: blink
Axis
2. Atravessar fronteiras
Basis
  • direct: features/appliance/notifications.py:10, "finished": Happening(watches="running", from_=STATE_ON, to=STATE_OFF), com o comentário "from on, so a plug reconnecting (unavailable → off) or a reload tells nobody".
  • direct: o exemplo washer_done de docs/concepts/reactions.mdx reescreve essa transição à mão.
  • direct: o docstring de Happening em core/feature.py já o define como "what happens, as a reaction's trigger".
  • external: de fora de um módulo do Terraform só se alcançam os outputs dele.
Rationale
A reação entre devices mais comum cai de quatro campos para um. Some também o erro de esquecer from: "on", que faz a reação disparar quando a tomada reconecta.
Downsides
  • Hoje existe um só acontecimento (finished). O ganho cresce junto com um vocabulário (started, opened) que ainda não existe.
  • É o primeiro referente que não é entidade, então o índice e as mensagens de erro passam a ter dois tipos de alvo.
  • O nome de um acontecimento pode colidir com uma chave local, e essa colisão precisa ser recusada.

4. Erro de referência que diz o que escrever

Description

Uma função só monta todas as recusas de referência e calcula a correção a partir do índice:

  • a mesma chave em outro bloco (turn_on: sprinkler → switches.sprinkler);
  • o caminho em outro device ("clothes_washer has it: device.clothes_washer.appliance.running_program");
  • a mais próxima por distância de edição entre as que o campo aceita ("did you mean switches.sprinkler?");
  • um entity ID colado ("write it as appliance.running_program");
  • com a regra nova, o homeassistant. esquecido (power: sensor.washer_plug_power → "write homeassistant.sensor.washer_plug_power").

As mensagens novas também aparecem no Check configuration do próprio HA (Ferramentas de desenvolvedor → YAML, o diálogo de reiniciar, e hass --script check_config sem o HA rodando). Ele roda o CONFIG_SCHEMA do pururu e, com ele, todas as verificações de referência; nenhuma ferramenta nova.

Axis
4. Descobrir e errar
Basis
  • direct: nenhum "did you mean" nem difflib no código.
  • direct: find deixa a mensagem para quem chama ("The caller says why, in its own words", core/resolve.py), e a mesma falha tem três redações (device_keys/reactions.py:465 e :476, setup/checks.py:51).
  • direct: docs/reference/troubleshooting.mdx:29, :36 e :47 ensinam à mão a correção que o erro não dá.
  • external: ESPHome, "Couldn't find ID 'relay2'... These IDs look similar: 'relay1'".
Rationale
Sem migração nem aliases (um usuário só), quem paga a troca de gramática é o primeiro reload com o YAML antigo. Um erro que já traz a linha certa torna a troca barata e ensina a gramática nova no lugar onde o usuário está.
Downsides
  • Explicar "o medidor não existe porque o statistics: não pediu esse período" não sai de Counted.needs, que cobre só settings como energy. Essa causa precisaria de outro dado.

5. Uma forma canônica, impressa em todo lugar

Description

Cada alvo tem um endereço canônico, o caminho da ideia 1 visto de fora (device.clothes_washer.appliance.running_program), já decidido como o event_name. Dentro do próprio device, o mesmo alvo se escreve sem o device.clothes_washer. (appliance.running_program). Uma função única de endereço alimenta:

  • o event_name e as chaves de states (decididos na ideia 1);
  • a description dos scripts e automações gerados, que hoje é pururu: biblioteca, washer_done e não diz o que a reação escuta;
  • os logs e os Repairs;
  • um atributo em cada entidade (já decidido junto com a ideia 1, regra 8), fora do recorder, com as duas formas (appliance.running_program dentro do device, device.clothes_washer.appliance.running_program de fora). Ele responde "como escrevo isto no YAML?" mesmo depois de um rename na UI.

Um teste garante que toda forma impressa resolve de volta ao mesmo alvo.

Axis
5. Um nome em todo lugar
Basis
  • direct: outputs/events.py:121, "event_name": f"{device.key}.{key}", e Ref.text em core/resolve.py montam a mesma string em dois lugares.
  • direct: device_keys/reactions.py:316 e aspects/programs.py:208 descrevem só pururu: {device_key}, {reaction_key}.
  • direct: core/roles.py:94 indexa inputs "by each reference as written (Ref.text)".
  • external: o Bazel normaliza :t para o label canônico e imprime esse label em todo erro.
Rationale
É a peça que impede a ideia 1 de criar duas grafias para o mesmo alvo. E dá ao usuário uma ida e volta: o nome que ele vê num evento, num Repair ou num atributo é o que ele cola no YAML.
Downsides
  • O atributo sai com a ideia 1; o resto (descrições, logs, Repairs, o teste de ida e volta) não muda o que o usuário escreve e pode vir depois.
  • Mudar a description muda o texto que aparece no rastro das automações.
