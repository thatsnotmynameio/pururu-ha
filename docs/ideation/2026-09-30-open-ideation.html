Grounding Context

Codebase Context

  • pururu is at 0.2.0. It has about 9.2k lines of Python in six layer folders (core, features, aspects, device_keys, outputs, setup) and 1295 tests. There is one user, the author.
  • Adding something new costs one module plus one line in a list (builders(), ASPECTS, CHECKS, STEPS). A contract test covers every builder, and an ID snapshot (tests/test_ids.py) pins every entity and generated ID.
  • There are five features: appliance, door, window, lights and switches. Ready-made behaviour exists only on the appliance: 4 alerts and 1 notification (finished). Door and window only count.
  • Program steps are delay, turn_on, turn_off and toggle. There is no wait, condition or interlock.
  • Invalid configuration shows up only in the log. The troubleshooting page opens with "The reload changed nothing" and lists about 30 causes.
  • Tuning a detected program means reading the power history by eye. The pure Detector from D1 already replays a real day in the tests (tests/fixtures/purifier_day.csv), but users have no way to run it.
  • The dashboard is an inventory table registered as a sidebar panel on private lovelace API.
  • In flight: D3 (draft PR #60, programs detected and executable), then C, the vocabulary PR for 0.2.1. Deferred to 0.2.2: phases on an executable program, a detected program from another source than a band, and a door's opening as a detected program. Issue #25, unifying native and pururu programs, is open.

Product strategy

  • Purpose: one thing (a gate, a pool) is spread over many integrations, and every derived fact and cross-part automation is written by hand, for each thing.
  • Positioning: "the house is a short file a person or an agent can write, diff and review."
  • What it is not: it never replaces a device's safety logic, is never a panel of its own, composes rather than rebuilds, and is code first with no configuration UI.
  • Three tracks: complex automations made easy (the pool's runtime goal, the gate's airlock), a behaviour catalogue, and inputs from anywhere. Neither metric (hand-written templates removed, time to a new thing) has a measurement yet.

External context

  • Appliance detection in HA is crowded but split up. Threshold blueprints give start and finish only. WashData matches programs by power-curve shape and learns from labelled cycles. None of these ties detection into areas, alerts or scripts, and none tunes from history in a declarative file.
  • HA core is taking over the ground around pururu. 2026.4 added an auto-generated Areas dashboard, 2026.7 lets integrations register named triggers, 2026.8 made entity IDs editable, and the 2026.10 beta shows active alerts on the Home dashboard and adds one-click MCP. What core still lacks is the modelled layer: programs and phases, openings with who and how, and alert priority on lights.
  • Useful analogies are Terraform plan and kubectl diff (see intent against reality before applying), Kubernetes status conditions, and Alertmanager inhibition.

1. A generic debt ledger: a goal any thing can owe and any run can pay

Description
Declare a goal as an account, not a schedule. Each period the goal accrues a debt of some quantity, and modifiers set the rate. Any measured delivery of that quantity pays it down, whoever caused it. The balance is a sensor. When the debt is paid, or runs late, the ledger raises events, and reactions start atomic programs on them. The house stays fully event-driven, with no waiting inside a program. The pool is one instance: filtering hours per day, accrued faster when the water is hot (the pool rule "temperature / 2 = hours" is a degree-day rule), and paid by any pump run, whether pururu started it, someone pressed the button, or the pump's own timer ran it. Other instances use the same piece:
  • Airing the house: minutes of open window per day, paid by the window's open_time_total.
  • An air purifier: hours per day, paid by its runtime_total.
  • A pressure pump or a water heater: runtime or cycles per week.
Basis
  • direct: STRATEGY.md:40: "a runtime goal with modifiers, as the pool's filtering". Track 3: "the pool's modifiers aren't in the pool".
  • direct: the credit side already exists as counters that survive restarts: the appliance's runtime_total (docs/features/appliance.mdx:92) and the opening's open_time_total (features/opening/__init__.py:117).
  • direct: D3 (PR #60) makes a program both detected and executable. Issue #25 asks how pururu's runs and native runs relate, and a ledger answers that: both are credits on the same account.
  • external: growing degree-days in agronomy, and heating-oil delivery by degree-days and a per-house K-factor.
  • reasoned: A schedule double-counts or under-counts whenever a person steps in. An account whose balance is its only state doesn't care who ran the pump. Because the ledger only raises events, each decision about when to pay is a reaction the user reads and reviews. Examples: "solar surplus rose and the debt is above zero" starts the filtering program, and "debt paid" stops it.
Rationale
It turns STRATEGY's hardest track 1 example into a derived fact (the balance) plus events. Because the ledger is generic, every counter pururu already builds can back a goal, and each new feature with a total adds new kinds of goal without new ledger code.
Downsides
The accrual rules are a small new language, so keep it to one or two modifier shapes until a second instance needs more. A debt measured in time only pays while HA is up, as runtime_total already does. There is no pool in the code yet, so the first instance to build is probably one that exists today (airing, the purifier).

2. One input seam for detected programs, to scope 0.2.2

Description
The carrier only consumes Started and Ended from the pure detector, so a power band is one producer among several. Make the input pluggable: a power band as today, a sensor's state (a smart washer's program sensor), an integration's events (WashData's cycle started and ended), or a contact. Three of the 0.2.2 deferrals then become configurations of one seam: another source than a band, a door's opening as a detected program, and program identity from WashData. Every source gets the carrier's phases, statistics, alerts and restore.
Basis
  • direct: the spec's deferred list for 0.2.2 (spec:653-660): "a detected program from another source than a band", "a door's opening as a detected program".
  • direct: issue #25, unify native programs with pururu's programs.
  • direct: STRATEGY: "if Magic Areas is the best presence engine, or WashData the best program recogniser, compose it."
  • reasoned: D1 made read(value, now, kwh) return events. The carrier doesn't care where they come from, so designing the seam before 0.2.2 avoids three parallel paths.
Rationale
It turns four open threads into one decision. It makes track 3 (inputs from anywhere) cheap for every cycle-shaped input, and it composes WashData instead of competing with it. It also pairs with idea 3: whatever the source, the cycle gets the same ready-made behaviour.
Downsides
This is already on the backlog, so the value lies in how it is scoped and not in the idea itself. Energy per cycle (kwh) has no meaning for a contact, and each source needs a clear answer for what it lacks.

3. Door and window get their own ready-made alerts: long_opening and no_opening

Description
Give door and window a Presets role, declared in their own features/opening/alerts.py as the appliance declares its presets. The file holds only data, because the mechanism already lives once in aspects/. The names follow the appliance's long_cycle/no_cycle in the openings' own vocabulary, where a cycle is an opening:
  • long_opening: Condition(state=on) on open, for required.
  • no_opening: Elapsed(state=off, since_key="last_closed", or_since_created=True), for required.
Their IDs carry the feature's namespace: binary_sensor.pururu_<device>_door_alert_long_opening. Only no_opening adds a capability: "not opened for a day" (a mailbox, a pet door, a room nobody airs) needs the time since the last closing, which a hand-written alert can't express. long_opening is a shortcut for a hand-written alert, with a default text in HA's language.
Basis
  • direct: features/opening/__init__.py:134: roles=(Counters((COUNTED,)),),. Door and window declare no presets.
  • direct: features/appliance/alerts.py: no_cycle is Elapsed(state=STATE_OFF, since_key="last_cycle_end", or_since_created=True). The opening's last_closed (features/opening/__init__.py:61) is the same milestone.
  • direct: the contract spec's glossary: a preset is "the definition of a ready-made alert, in its feature's code". And "cycle_start/cycle_end attributes stay … Open gets none", so the appliance's presets can't be shared with openings as is.
  • direct: docs/features/door.mdx:111: a door left open is already a hand-written alert (when: door_open, is: "on", for). A hand-written alert has no time since a milestone.
Rationale
It is the repo's own pattern for a feature's catalogue, costing a few lines of declarations plus the names, icons and docs the contract test requires. no_opening on a window is also a natural input for idea 1 ("the house wasn't aired today").
Downsides
no_opening repeats no_cycle's shape with two names changed. That is a declaration, not logic. A shared function in features/cycle/ waits for a third case, as the spec's "Left out on purpose" rule asks.

4. Calibrate a program from its own history

Description
A pururu.calibrate service reads N days of a program's power sensor from the recorder and runs them through the same pure Detector. It sweeps above, on_delay and off_delay, and reports what each setting would have found: how many cycles, the longest, any wash split by a pause, any start from a standby spike. It returns a YAML snippet to paste in, never a setting pururu keeps. Fitting on last week and checking against this week guards against overfitting, as backtesting does. A saved run can become a test fixture, so each appliance tuned adds a regression test for the detector.
Basis
  • direct: docs/getting-started/first-device.mdx:23: "Open the plug's power sensor in History and look at a full wash:", followed by three rules to apply by eye.
  • direct: docs/reference/troubleshooting.mdx:226-228: "Ends in the middle of a wash: the appliance paused for longer than off_delay. Increase off_delay."
  • direct: detector.py:82 class Detector, read at :165 and advance at :209. tests/test_program.py replays purifier_day.csv through it.
  • external: WashData's Record Mode and retro-labelling learn from curves in a UI. This idea keeps the numbers in the file.
Rationale
Every new appliance on a plug today costs at least one wrong guess that only shows after a real wash. That cost lands on the "time to a new thing" metric. All six lenses reached this idea independently, which is the strongest agreement in the run. The same replay could later check a detected program from idea 2's other inputs.
Downsides
It needs the recorder's history API from inside the integration, and a long history makes the sweep slow. A plug whose history is shorter than one full cycle has nothing to calibrate from.

5. Retire the /pururu panel and write views as a YAML dashboard

Description
Stop injecting a LovelaceConfig and registering a sidebar panel. Write the dashboard as a YAML file through the same writer the scripts, automations and Alert2 already share (core/files.py), included once through HA's public lovelace: dashboards: in YAML mode. The inventory table moves to HA's own Areas dashboard. The freed output becomes the strategy's "generated views": a view per thing (the gate's openings and who, the appliance's phases and last cycle), with each feature adding its cards.
Basis
  • direct: STRATEGY.md:25: "pururu builds entities, automations and views in it, never a panel of its own." Against that, outputs/dashboard.py:199 calls frontend.async_register_built_in_panel(.
  • direct: outputs/dashboard.py:3: "HA has no public API for an integration's dashboard."
  • direct: docs/concepts/dashboard.mdx:10-11: it shows totals and a table of floors, areas and devices, which is an inventory and not a view of a thing.
  • external: HA 2026.4's auto-generated Areas dashboard covers the inventory.
Rationale
It resolves a live contradiction between the code and the strategy. It also removes the one module on private API, which any HA release can break, and the double lovelace_updated workaround.
Downsides
It costs the user one more line in configuration.yaml. How well the Areas dashboard covers the inventory was not checked, and it is still experimental.
