# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

pururu is a Home Assistant custom integration (`custom_components/pururu/`). It reads a `pururu:` YAML block and creates floors, areas and devices from it. It builds each device's entities from real entities and a few settings. The docs site is the user-facing reference for every configuration key and entity (see Docs below); the README is a short entry point that links to it.

## Commands

Run all commands from the repo root with `uv`. Home Assistant is pinned through `pytest-homeassistant-custom-component` in `pyproject.toml`, which pins `homeassistant==2026.9.3`.

```sh
uv run pytest                                   # all tests but the docs tests, plus ruff, ruff format, mypy, hassfest, quality scale (tests/test_code.py)
uv run pytest -m docs                           # the docs tests (tests/docs/): the tests that read docs/
uv run pytest tests/test_places.py -n 0 -q      # one file, single process
uv run pytest "tests/test_places.py::test_name[param id]" -n 0
PURURU_SHARD=1/3 uv run pytest --ignore=tests/test_code.py   # one of CI's three test shards
uv run ruff check --fix custom_components/pururu
uv run ruff format custom_components/pururu
uv run mypy custom_components/pururu
python3 release.py check                        # the manifest version must be semver and not below the latest release
git diff --name-only origin/main... | python3 .github/scripts/changes.py pull_request   # the checks CI runs for these changes: build, docs, hacs, tools true|false
python3 tools/dispatcher/dispatcher.py run      # ready issues become pull requests, one lfg session each
```

- **Running single-process:** `pyproject.toml` addopts already pass `-n 4 --dist loadfile`, so use `-n 0` to run in one process. `-p no:xdist` breaks the run.
- **Lint and type scope:** ruff and mypy run only on `custom_components/pururu`, with core's settings (`ruff.toml`, `mypy.ini`, strict). Tests are not linted.
- **hassfest:** it is downloaded once into `.hassfest/` (`fetch_hassfest.py`).
- **Docs tests:** the tests that read `docs/` live in `tests/docs/`, marked `docs` by `tests/conftest.py`; `addopts`' `-m "not docs"` keeps them out of `uv run pytest`, and `uv run pytest -m docs` runs them. A guard in `tests/test_code.py` fails when a test outside `tests/docs/` names `docs/` (allowed: `tests/conftest.py`, `tests/test_changes.py`).
- **Current working directory:** never leave the shell's cwd inside `.venv/.../homeassistant/helpers/`. That folder contains an `importlib.py` that shadows the stdlib, so any Python started there (hooks included) crashes.

## Architecture

- **One config entry owns everything.**
  - `async_setup` validates `CONFIG_SCHEMA` and stores the validated `pururu:` block in `hass.data[DATA_CONFIG]`. It then creates the single entry through an import flow (`config_flow.py`, `single_config_entry`) when the block declares floors, areas or devices.
  - The `pururu.reload` service re-reads YAML and reloads the entry.
  - Where the code lives, one folder per layer: at the root only what HA looks up (`__init__.py`, `config_flow.py`, `const.py`, the platforms; `tests/test_code.py` pins it, and the whole layer table: what each folder, and each module at the root, may import, with five named allowances for one module each — `features/__init__` → every feature, `device_keys/__init__` → `aspects.alerts` and `aspects.programs` (the hand-written alerts' and the executable programs' device keys), `device_keys/reactions` → `aspects.programs` (a reaction's `then` starts an executable program's script), `features/buttons` → `aspects.programs` (a button's `program` starts one; imported as the module and read only inside functions, as `aspects.programs` is still loading when the package import reaches `features/`), `__init__` → `core.runtime` directly, for HA's typed entry — and only `aspects/statistics.py` importing `utility_meter`); `core/` the contracts and shared helpers, importing only `core/` and `const`; `features/`; `aspects/` (`ASPECTS`, a concern written once and mounted in every builder's block that offers it: `alerts.py`, the ready-made alerts, plus the hand-written ones' device key, with `elapsed.py` and `problem.py` (`ProblemAlert`, and `shared(priority)`, the keys every alert takes: `priority`, `message` and `done_message` (both or neither, `texts_together`), `lights`); `statistics.py`; `notifications.py`, the ready-made notifications; `programs.py`, the detected programs' aspect and the executable programs' device key `PROGRAMS`); `device_keys/` (`DEVICE_KEYS`, reactions; `programs` is `aspects.programs.PROGRAMS`, `alerts` `aspects.alerts.ALERTS`); `outputs/` the steps after the platforms; `setup/` the wiring. `__init__.py` holds only HA's entry points, each calling `setup/lifecycle.py` (applying the YAML, setting the entry up, unload, remove); the registry listener is `setup/listener.py`; the schema in `setup/schema.py`, with `CHECKS`, the rules over the whole house, each `check(house, index, builders)` yielding its refusals with a path (all raised together) and living in its owner's module (`setup/checks.py` for the generic ones — `keys_distinct` among them —, `reactions.check`, `programs.check` (`aspects/programs.py`: a step acts on another feature's key taking its action), `buttons.check` (`features/buttons.py`: a button's program is its device's executable program, and one sensor value presses one button of a device), `alerts.check` (`aspects/alerts.py`: an alert can't watch a ready-made alert), `checks.pururus_own_as_home_assistants` (a reaction's `when` naming as `homeassistant.` what pururu creates or generates, refused with its path), `alert_lights.check`, `places.floors_exist`), the builders, the aspects they mount at their places, and the index of what each device can create in `setup/catalogue.py` (`builders()`, `aspects_of()`, `mount()` — taking the deepest places first and putting the shallowest back first —, `keys()`, each row `(builder, key, platform, by, item, path)`, the path born where its key is (`Nodes`, `Born`, `Item.path`, `Place.leaves`), `index()`, device → path → `Target` (`Target.path`); `Ref(owner, device, path)`, `Owner`, `Target`, `find`, `resolve` (a `Target` or why not), and the forms `path`, `key_alone`, `homeassistant_entity` in `core/resolve.py`; `notify`'s `messages.action`), building and `creatable` in `setup/build.py`, placing devices and removing stale ones in `outputs/devices.py`, each generated kind's `plan()` in its owner (`aspects/programs.py`, `device_keys/reactions.py`, `aspects/notifications.py`), returning a `generated.Planned`, wired by `setup/generate.py`; `PururuConfigEntry` is in `core/runtime.py`, the vocabulary in `core/vocabulary.py` (`Condition`: `state` as text, `above`/`below`, `equals` in code only; `parse`, a validated block's `Condition`; `band`; `trigger`; `period`), the common texts in `core/texts.py`.
  - `async_setup_entry` does all the work, in order. Steps 1–3 are the prelude, which may fail the setup (once the platforms are forwarded, a failure, a cancellation too, in a step as well (`except BaseException` around the steps, which guard `Exception` only), unloads them before raising, as HA unloads a non-loaded entry without `async_unload_entry` and platforms left set up would refuse the entry at every reload; platforms not all unloaded are logged with what to do (HA's `Config entry was never loaded!` means nothing was left), the original error raised); from step 3's events on, each output is a step of `lifecycle.STEPS` (`async_step(hass, entry, built, targets)` in its own module, reading a frozen `runtime.Built` and adding to the shared `targets` the entity IDs whose disabling rebuilds the entry as soon as it knows them, before any part that can fail, since the listener gets the same set whether or not a step failed), run in `try/except` so a failing one is logged (`Step <name> failed`) and the entry stays loaded, as is the registry listener set up after them (`Listener failed`); an autouse fixture in `tests/conftest.py` fails any test that logs either unexpectedly:
    1. Sync floors and areas (`outputs/places.py`).
    2. Build every device's entities.
    3. Hand them to the platforms through `entry.runtime_data`. The platforms (`sensor.py`, `binary_sensor.py`, `button.py`, `switch.py`, `light.py`) only call `async_add_entities`. Right after, `events.async_setup` tracks the created entities, by device, when `pururu: config: events:` enables a class (`outputs/events.py`).
    4. Put each device in its `area:` (a key of `areas:`).
    5. Remove stale entities and devices.
    6. Generate the programs' scripts (`aspects/programs.py`: `programs: executable:`, `script.pururu_<device>_program_executable_<key>`), then the automations: the reactions', then the ready-made notifications' (`core/generated.py`, a `Kind` per domain: `SCRIPTS` and `AUTOMATIONS`, defined there so the device keys and aspects that name their domain import no `setup/`; a reaction's `then` starts its device's program, `script.turn_on` unless it runs, and its `when` may follow one's script (`programs.executable.<key>`, its own device's or another's); both follow it: not generated → not generated, held → held; a reaction on `at` or `sun` can `retry`: more triggers `retry_<k>`, each skipped by a template condition on `last_triggered`, the program's script with `then`, the automation's own `this` without, once the occurrence ran; its `message` is told after it, to its `notify` or `config: notify`, through `core/messages.py`: notify actions in one `parallel`, text escaped, title the device's name, once per occurrence with retry): `pururu/scripts/programs.yaml`, then one automations file, `pururu/automations/automations.yaml`, synced once (one reload, one Repairs issue, IDs in `entry.data["automations"]`) with `reactions.plan`'s items then `notifications.plan`'s (`aspects/notifications.py`), the reactions' held (a kind whose file changed reloads only when it holds items or drops some; an old entry's `notifications` data key is left unread), whose folders `configuration.yaml` includes (`automation pururu: !include_dir_merge_list pururu/automations`, `script pururu: !include_dir_merge_named pururu/scripts`, as a missing folder loads as nothing while a missing file stops HA's configuration), entity IDs pre-registered (an ID the entry doesn't manage is the user's, never taken over), a script in its device's area, the domain reloaded when the file changed or HA doesn't run it (retried at the next reload), in an entry task, a Repairs issue while it isn't included (checked again on the domain's state changes, the warning logged once). A dropped item's registry entry goes once HA no longer runs it: a restored placeholder state doesn't count. A program whose target is disabled is held, not dropped (`async_sync(..., held)`): out of the file, its registry entry and tracked ID stay, and it comes back as the user set it. `reactions` and `programs` (its `executable:` group) are device keys, not features of a device; a feature's `programs: detected:` is an aspect; a program isn't generated while an entity it acts on is not created (dropped) or disabled (held).
    7. Write Alert2's alerts (`outputs/alert2_alerts.py`): `pururu/alert2/alerts.yaml`, one condition alert per created alert with `message` and `done_message`, which the user's `alert2:` block includes as its `alerts` (`!include_dir_merge_list pururu/alert2`); Alert2 reloaded when it changed or doesn't run an alert of it, in an entry task, a Repairs issue while it isn't included. The writer (header, rewrite only on change, logged failure) is shared with `core/generated.py` (`core/files.py`).
    8. Lend lights to the alerts (`outputs/alert_lights.py`): an alert's `lights` (a group's name, `default` included) borrows a group of `config: alerts: lights: groups` (a list of `device.<device>.lights.<key>`, a member that isn't a pururu light refused at its path); a light shows the highest priority's `turn_on` among its alerts on (`repeat` for one-shot effects), `resolved` for its `lasts` once the last ends, then `turn_off` and `pururu_alert_lights_released`. Only `light.turn_on`/`turn_off` on the pururu light, which uses what it has (`Borrowable`: `alert`/`alerts` attributes, `alert` restored, an unknown effect dropped); a change without one of the manager's recent contexts is put back (during `resolved`, one by a person or automation releases it, not turned off); a light without a reading is never called; disabling a followed light or alert reloads the entry; a light restored with `alert` and none of its alerts on goes through `resolved`.
    9. Show the dashboard (`outputs/dashboard.py`).
- **Features** (`core/feature.py`, `features/`):
  - A device is a name plus one or more features. `FEATURES` in `features/__init__.py` maps each config key to a `Feature`. A `Feature` has a `schema`, a `namespace`, the `entity_keys` it can create (entity key → platform), `build()`, an `example` block, and `roles` (`core/roles.py`, asked for by type: `feature.role(Configured)`): `Configured`, `Nodes` (where its fixed keys sit in the block: the carrier at `running_program`, `energy_total` at `energy`; default: the block under the key's name), `Derived`, `Programs`, `Actions`, `Items`, `Counters`, `Refers`, `Presets`, `Happenings`, `Generates`.
  - A validated block can add entity keys beyond `entity_keys` (`Derived(of)`, key → `Born(platform, path)`): the appliance's phases' (`program.keys_of`), listed by `catalogue.keys` so the index knows them only when the block has phases.
  - A builder with `Programs(reading, energy)` (the appliance: `power`, `energy`) takes `programs: detected:` in its block: the programs aspect (`aspects/programs.py`'s `ASPECT`) mounts it (`DETECTED_BLOCK`: `executable:`, or a block without `detected:`, refused), lists each detected program's keys (`Place.derived`, `(key, Born)` pairs from `program.detected_keys`, so `checks.keys_distinct` sees a key two programs, or a program and the appliance, create; a key a phase could take later, `phase[_…]` or `<program>_phase[_…]` beside that program, is refused at once by `DETECTED_BLOCK`'s `program.unreserved`, since phases' keys are listed only once they exist) and builds each with `program.build_detected` (the program with `of`, its item: carrier `<key>`, cycle entities `<key>_<suffix>`, phases `<key>_phase_…`, named `detected_*` with `{item}`, `DETECTED_NAMED`; a configured phase's as the running program's). The builder's `Counters` lists `program.counted_each(program.DETECTED_AT)` (`programs, detected, EACH`): each detected program's own `runtime`, `cycles` and `energy` totals, its phases' and `other`'s.
  - A feature can watch a particular entity of another feature named in its block (an alert's `when: appliance.power`): `Refers(of)` yields `(field path, Ref)`, `checks.references` refuses at that field one that isn't another feature's of this device (another device's and Home Assistant's always), `build.build` passes their current entity IDs in `inputs` by the reference as written (`Ref.text`), and `PururuEntity.follows` (paths) drops the entity when the watched one isn't created (or isn't built by the settings). A reference is the path in the YAML from the block key (`appliance.running_program`, every level written: `appliance.programs.detected.cotton.other.statistics.energy.month`), `device.<device>.<path>` for another device (a reaction's `when`; a light group's member, always), `homeassistant.<domain>.<object_id>` for Home Assistant's; `core/resolve.py`'s `path` validates the form, `Ref.parse` reads it, the checks resolve it (`resolve`: a device naming itself with `device.` refused with the form to write). Home Assistant-only fields (`power`, `energy`, `contact`, the `entity` of switches, lights, buttons and event entities: `homeassistant_entity`; `notify`: `messages.action`) strip `homeassistant.` at the field; a reaction's `when` keeps it (its trigger gets the bare ID) and may follow `programs.executable.<key>` (a script, no `Target`: `programs.named`/`running`), `reactions.<key>` refused for its `triggered_total`. Single-kind fields (`area`, `floor`, `then`, `program`, alert `lights`) take the key alone (`key_alone`).
  - A `Configured` feature (`switches`, `lights`, `buttons`) takes its entity keys from its block's keys, named by the block's `name` (no translation). `alerts` (a device key, not a feature: `aspects/alerts.py`'s `ALERTS`) is `Configured` too, one alert per key of the device's `alerts:` block. A feature standing for real entities of one domain is that domain's HA group entity with one member (`SwitchGroup`, `LightGroup`, as `Mirror` is a `SensorGroup`), one feature per domain. `lights` also takes a `switch.*`, as a `SwitchLight` (on/off). What they share (`{key: {entity, name}}`, `is_pururu`) is in `features/standing.py`. `checks.real_entities_distinct` refuses a real entity in two configured features of one device.
  - `buttons` (`features/buttons.py`) is `Configured` but stands for nothing: each key is a `ButtonEntity` (`{entity: homeassistant.sensor.*, state, name, program?}`), always available, whose state is its last press. A press is `button.press` or the sensor **changing into** `state` (`pressed()`: HA `running`, an old state that isn't missing, restored or `unavailable`, never the same value again, and from `unknown` only after `SETTLE`): no press nobody made. Both go through `_async_press_action`; `async_press` first sends the press (`pressed_signal`) to the button's `TriggeredTotal` (`<key>_triggered_total`, a `CyclesTotal`; `Items` and `Counters` beside `Configured`, `statistics:` in each button, as a reaction's), then starts the button's executable program's script only when it is `off`.
  - A feature can offer ready-made alerts (`Presets`: name → `Preset`), off until its block's `alerts` enables them: entity key `alert_<name>`, added by the alerts aspect (`aspects/alerts.py`'s `ASPECT`, `mount_absent=False`: none enabled, no `alerts` mounted), never in the builder's own `entity_keys`. The aspect validates the block's `alerts` and builds the enabled ones as an `Alert` (a `Condition`) or an `ElapsedAlert` (time since a milestone, kept across restarts), on the shared `ProblemAlert` base (`aspects/problem.py`); default texts in the translations' `common`. The Alert2 file is built from the created alerts (`ProblemAlert`), hand-written (the device key `ALERTS`) or ready-made.
  - A feature can repeat entity keys per item of its block (`Items`: suffixes and items): an executable program's `executable_<key>_<suffix>` (`program_executable_clean_cycles_total`), named by `program_<suffix>` with `{program}` as the item's name (`_identify(..., item=item)`). The cycle code the appliance (its running program and phases), `door`, `window` and the programs share (last cycle, totals, energy) is in `features/cycle/`; every entity that sends a cycle is a `CycleSource` (`features/cycle/__init__.py`): it writes its state, then sends the cycle on its own signal, then on the end signal. `door` and `window` are one package, `features/opening/`, built by one function per namespace: a contact makes the openings (cycles), and user-mapped `event.*` entities (`event_entities`) describe them (who, how, direction), matched by the event's time (its state).
  - **Detected programs** (`features/cycle/program/`): the appliance's required `running_program` is one, built with `key="running"`, so its carrier is `appliance_running` and the appliance's own cycle entities follow it (D1 ruling 13).
    - `schema.py`: `SCHEMA` (a phase keyed `idle`, `other` or `other_…` refused at once: `other`'s meters are listed only once `other:` is written), `DETECTED_SCHEMA` (a detected program needs a `name`), `Program`, `program_of(config, of)`, `phase_keys`, `FIXED`, `NAMED`, `DETECTED_NAMED`, `keys_of(config, of)`, `PHASE_COUNTERS`, `counted(where)` (a running program's places), `DETECTED_AT`, `counted_each(where)` (each detected program's places), `detected_keys(key, config)`.
    - `detector.py`: the pure `Detector`. `read(value, now, kwh)` and `advance(now, kwh)` return `Started`/`Ended`, each delay at its own time. Overlapping bands run at once, a dip waits, an idle gap blocks nothing, and `other` never waits and ends when a phase starts.
    - `entities.py`: `build(hass, device, program, *, key, reading, energy, of=None)`, and `build_detected(hass, device, key, config, *, reading, energy)` (a detected program: `build` with `of`, its item, then its own last cycle and totals). The `Carrier` (a `CycleSource` binary sensor under the builder's key, `running`, or the detected program's) owns and restores the detector, waits for its entry's setup to leave `SETUP_IN_PROGRESS` before its first step, and calls its views with each step's changes (after its own state; before it when the program ends). `PhaseRunning` (`phase_<key>`, or `<program>_phase_<key>` with `of`, a `CycleSource`), `PhaseCurrent` (`idle` while its carrier is disabled; its own restored state until the carrier has restored the detector; a `name` attribute, a configured phase's `name`, None for `idle` and `other`; only `idle` and `other` are translated states), `PhaseLast`, and each phase's cycle entities, named by `NAMED`, which the contract test counts.
    - Its tests: `tests/test_program.py` (pure; 0.1's `modes` and `phases` scenarios; the purifier day's replay, `tests/fixtures/purifier_day.csv`), `tests/test_program_entities.py`, which runs on the real appliance (no test-only builder), and `tests/test_detected_programs.py` (the aspect: IDs, counting apart from the running program, restarts, names, statistics, where programs sit, collisions computed from `catalogue.keys`, phases).
  - **Aspects** (`core/feature.py`'s `Aspect`, `aspects/`): a concern written once, mounted at its places in the block of every builder offering it, instead of copied into each. An `Aspect` has a `key` (the block key it mounts, `"statistics"`, `"alerts"`, `"notifications"`, `"programs"`), `offered(builder)` (whether it applies: the builder has what it needs, `Counters` for statistics, at least one ready-made alert for alerts, the rule `presets_of` reads, at least one `Happening` for notifications, the `Programs` role for detected programs), `places(builder, name)` (the `Place`s where its key sits: `path` from the block, `EACH` for each key of a map, with its `schema`, `keys`, `named`, `example`, `item` (`item(block, path)`, `feature.ItemOf`: the item the container at that concrete path of the builder's validated block is, `feature.at(block, path)` giving the container), `leaves` (each of `keys`' path from the aspect's value: `(<counter>, <period>)`), optional `derived(value)` (the local keys a container's validated value adds beyond `keys`, as `(key, Born)` pairs so a key two add comes twice for `checks.keys_distinct`: a detected program's) and optional `check(block, container)`; `name`: the builder's key in the device, for an aspect whose messages name the builder: the notifications aspect uses it; the alerts and statistics aspects don't need it), `build` (`AspectBuild`: hass, device, builder, its whole validated block — the aspect's value put back at each of its places — texts), and `mount_absent` (`True`: its key absent is validated as `{}` and mounted, as statistics' — no counter asks a period; `False`: left out, as nothing asked, an explicit empty block still refused — the ready-made alerts', notifications' and detected programs', `aspects/alerts.py`'s, `aspects/notifications.py`'s and `aspects/programs.py`'s `ASPECT`). `notifications.ASPECT` adds no entity key and builds no entity: each enabled notification is an automation its `plan` generates. `statistics.ASPECT` (`aspects/statistics.py`) meters a builder with `Counters(places)`, each a `Counted(needs, at, item, named)` (`needs`: counter → the setting it needs, looked up in the builder's whole block, `None` for none; `at`: the path from the block to where `statistics:` sits, `EACH` for each item; `item`: the item a container there is, `item(block, path)` as `Place.item`; `named`: a translation prefix of its own, `other`'s). `ASPECTS` (`aspects/__init__.py`) lists them in build order: the ready-made alerts, then the detected programs, then statistics' meters (after every total they meter), then the ready-made notifications (no entity). `setup/catalogue.mount` takes the key out of each container `walk` finds for each (aspect, place), the deepest places first (places at one depth in `ASPECTS`' order), so an aspect's key can sit inside another aspect's value (`statistics:` in a detected program, in `programs:`), and validates it with that place's schema; that's the first stage, the builder's own schema refusal and each place's raised together. Only once they pass does it put each place's value back along its path, the shallowest first (`programs:` is back before its programs' `statistics:`), and run each place's `check`, those refusals raised together too, separately from the first; the appliance counts at seven places (its block, `running_program`, each phase, `other`, and each detected program, its phases, its `other`). `build.build` builds a device's entities as the builder's own, then each aspect it offers, in `ASPECTS`' order (the ready-made alerts, the detected programs, then the meters; the notifications aspect builds none).
  - A feature's `Actions` (switches and lights: `turn_on`, `turn_off`, `toggle`) are what a program's step can do to its entities; `programs.check` checks them on the step's `Target`.
  - `programs`, `reactions` and `alerts` aren't features, but they're `DEVICE_KEYS` (`device_keys/__init__.py`): `programs`' and `reactions`' statistics are sensors built by a `Feature` each (each program's run is a cycle its `cycles_total`, `Runs`, sends from its script's state; each reaction's `triggered_total` counts `automation_triggered`), and `alerts` is `ALERTS` (`aspects/alerts.py`), the hand-written alerts. `catalogue.builders()` (`FEATURES`, then `DEVICE_KEYS`, read at every call) is what lists, resolves and builds entity keys; `FEATURES` alone makes a device's features.
  - A feature can offer ready-made notifications (`Happenings`: name → `Happening`, the entity key it watches and its `to`/`from_`), enabled in its block's `notifications` (`<feature>: notifications: {<name>: settings}`, as `alerts` for ready-made alerts; the notifications aspect, `aspects/notifications.py`'s `ASPECT`, takes it out before the feature's schema and validates it): no entity, an automation each (`aspects/notifications.py`'s `plan`), default texts in the translations' `common`. An alert is what's critical and lasts; a notification is news told once.
  - `tests/test_features.py` is a contract test over every entry in `FEATURES` and `DEVICE_KEYS`. It checks translations and icons for each entity key, that the example is valid, and more. A new feature gets checked there without changes to the test.
- **Entity IDs are the identity:**
  - Every entity is `<platform>.pururu_<device key>_<namespace>_<entity key>` (a ready-made notification's automation `automation.pururu_<device key>_<namespace>_notification_<name>`, an executable program's script `script.pururu_<device key>_program_executable_<key>`) (no exception, even for a key alike its namespace: a switch keyed `switch` is `switch.pururu_greenhouse_switch_switch`; so a feature's fixed entity keys never repeat its namespace: an `appliance` key `appliance` would read `…_appliance_appliance`), and its unique ID is the part after the platform (`Device.object_id`). `build.build` hands each feature a `Device` in its namespace, so features write local entity keys; the translation key is the key in its namespace (`appliance_running`). `build.build` stamps each entity's `path` from the index (`PururuEntity.path`; `device_key` is set by `_identify`), shown as the `reference` capability attribute `{"inside": <path>, "outside": "device.<device>.<path>"}` (written while unavailable too), unrecorded: `PururuEntity.__init_subclass__` unions `_unrecorded_attributes` over the MRO, as `GroupEntity`'s and `UtilityMeterSensor`'s sit behind it.
  - An ID already held by another integration is logged as an error and not created. Anything that follows it (`sources`) is dropped too (`build.creatable`); IDs are never suffixed with `_2`.
  - A user rename in the UI is followed: `current_entity_id`, plus a registry listener (`setup/listener.py`) that reloads the entry: on the rename of one of its entities, and on the rename of any generated item it tracks in `entry.data` (scripts, reactions' and notifications' automations alike: one rule).
- **Floors and areas** (`outputs/places.py`):
  - HA's registries accept no ID, so a new floor or area is created named after its YAML key (the ID becomes the key), then renamed.
  - Anything with a configured ID is adopted and synced.
  - The IDs the entry manages live in `entry.data` (`{"floors": [...], "areas": [...], "automations": [...], "scripts": [...]}`, the last two the IDs of the reactions' and ready-made notifications' automations and of the programs' scripts). What the YAML drops is deleted, and `async_remove_entry` deletes everything the entry manages.
  - Names HA refuses are logged errors and never fail the setup.
- **Dashboard** (`outputs/dashboard.py`):
  - HA has no public API for an integration's dashboard. A `LovelaceConfig` subclass goes in `hass.data[LOVELACE_DATA].dashboards["pururu"]`, and a `lovelace` panel in `yaml` mode (read-only in the UI) shows it. This is private lovelace API: keep every use of it in this module.
  - The config is built at every fetch from `entry.data` and the registries. A registry change fires `lovelace_updated` twice, because the frontend ignores the first one after a yaml fetch.
  - Anything that prevents it (`/pururu` taken, lovelace changed) is a logged error, never a failed setup.
- **Events** (`outputs/events.py`): `pururu: config: events:` lists `state_changed` and `reading`, none by default. Each state change of an entity the entry created is fired on HA's bus as `pururu_state_changed` (no `state_class`) or `pururu_reading` (one), with `event_id` (ULID), `event_name` (`device.<device>.<path>`), `event_class`, `key` (the path), the change, `attributes` (without `reference`), and `states` (the device's states when fired, keyed by path: flat dotted keys, read with brackets). Not fired: an entity appearing or going, HA's restored placeholder either way (a reload writes one), attributes alone. The path is the one `build.build` stamped on the entity, never parsed from its ID. pururu speaks no HTTP: a user's automation with a `rest_command` posts them (docs: `concepts/events`).
- **Voluptuous gotcha:** `CONFIG_SCHEMA` uses `extra=vol.ALLOW_EXTRA` at the top level. It propagates into plain nested dicts, so a nested mapping that must refuse unknown or non-slug keys needs its own `vol.Schema(...)`.

## Tests

- **`ha` fixture** (`tests/conftest.py`): it freezes time at a fixed Wednesday 10:00 and puts the repo's `custom_components` on HA's loader path.
- **Loading integration modules:** use `helpers.module("<name>")` after the fixture, not a top-level import; the name is dotted from the package root (`"core.feature"`, `"setup.lifecycle"`, `"features"`).
- **Helpers in `tests/helpers.py`:**
  - `setup` and `reload` take devices, plus `floors=`, `areas=`, `events=` (`pururu: config: events:`) and `config=` (`pururu: config:`).
  - `restart` restores saved state (a `(State, extra data)` per entity), plus `config=`.
  - `tick` and `fake` drive time and real-entity states.
  - `device_of` and `held` inspect the registries.
  - `snapshot(since, *, since_energy, until, **phases)` is the carrier's restored extra data: a program run from `since`, and phases' runs by key.
- **Docs tests and shards:** a test that reads `docs/` goes in `tests/docs/` (see Commands). `PURURU_SHARD=i/N` (`tests/sharding.py`, applied in `tests/conftest.py`) keeps one of N sets of whole test files, stable for the same selection, as CI's three test jobs do (without `tests/test_code.py`, which Build's lint job runs: see Commands); a wrong value is a usage error.

## Docs

- **Where:** [docs.page](https://docs.page/thatsnotmynameio/pururu-ha) serves `docs.json` (tabs and sidebar) and `docs/**/*.mdx` from `main`. Only `.mdx` is published, so `docs/superpowers/` (specs and plans) is not.
- **Solutions:** `docs/solutions/` holds documented solutions to past problems (bugs, best practices, workflow patterns), by category with YAML frontmatter (`module`, `tags`, `problem_type`); relevant when implementing or debugging in a documented area. Not published (`.md`, not `.mdx`).
- **Concepts:** `CONCEPTS.md` holds the shared domain vocabulary (entities, named processes, status concepts); relevant when orienting to the codebase or discussing domain concepts.
- **Capturing learnings:** After a solved, verified problem, automatically invoke the `ce-compound` skill with `mode:non-interactive` at the completion checkpoint only when the work produced durable project reasoning that is not readily recoverable from the final code, tests, types, comments, or existing documentation, and losing it would plausibly cause recurrence, material risk, or substantial rediscovery. Apply this counterfactual: if the learning document disappeared, would a future engineer reading the final implementation still be likely to repeat the mistake or redo substantial investigation? If not, do not invoke it. Completion, effort, and diff size alone are not enough. Capture at the checkpoint so a qualifying learning can ship in the PR that produced it, and only where the repository treats captured learnings as tracked, committed knowledge.
- **Two tabs:** `Guide` (`/`) for users (getting started, concepts, one page per feature in `FEATURES`, configuration reference, troubleshooting) and `Develop` (`/develop`) for contributors.
- **Keep it true:** a change in behaviour, configuration, entities or log messages updates the matching pages in the same PR. A new feature gets `docs/features/<feature>.mdx` and a sidebar entry.
- **MDX:** `{` and `<` outside code are JSX, so keep them in backticks or code blocks.
- **Check:** `pnpm install` once, then `pnpm docs:check` (broken links; the Docs workflow runs it, beside the docs tests, on PRs that change docs or code) and `pnpm docs:preview` (live preview). Use pnpm, never npm: `package.json` pins the docs.page CLI and pnpm itself (`packageManager`), and `pnpm-lock.yaml` pins them by hash.

## Releases and CI

- **Releases:** the version is `version` in `custom_components/pururu/manifest.json`. A PR that changes it is a release. After it merges to `main`, the Release workflow tags `vX.Y.Z` and publishes a GitHub release, which HACS offers.
- **CI:** on every PR, `ci.yml` classifies the changed files (`.github/scripts/changes.py`) and calls only the workflows they need: Build (`build.yml`: a lint job with `release.py check` and `tests/test_code.py`, three test shards, then SonarQube on the combined coverage, waiting for the quality gate on PRs) for code or workflows, Docs (`docs.yml`: docs.page check and docs tests) for docs, code or workflows, Validate (`validate.yml`, HACS) for `hacs.json`, the manifest, `README.md` or workflows, Tools (`tools.yml`: `pytest tools`, the repo's own tools apart from the integration; Build's shards run `pytest tests`) for `tools/`, `pyproject.toml`, `uv.lock` or workflows; agent and planning files run none, a file in no group runs all. "CI ok" is the only required Actions check. Build, Docs, Validate and Tools have no `pull_request` trigger of their own; Release on `main` calls Build and Validate in full. CodeQL (default setup) analyses every PR. GitHub Actions are pinned by SHA, Python packages by hash (`uv.lock`), pnpm packages by hash (`pnpm-lock.yaml`).
- **Issues:** GitHub Issues track the work (`project_tracker: github`).
- **Sonar suppressions:** a Sonar finding that conflicts with HA's required signatures or conventions is suppressed in `sonar-project.properties` (`sonar.issue.ignore.multicriteria`), with a comment giving the reason, not in code.

## Writing to the user

Write every report, summary, or handoff to the user through the `ce-noslop` skill. This applies when you are the top-level agent writing to the user, not when you are a subagent reporting to its caller. Do not apply it to code, config, verbatim quotes, or text the user asked to post as written.
